# 도구, 사실, 검사: LLM이 작성한 기하·최적화 코드는 언제 실패하며, 어떤 해법을 써야 하는가

*대학원 NLP 수업 프로젝트 제안서: 계산기하(computational geometry)와 조합 최적화(combinatorial optimization)*

> **번역 안내.** 이 파일은 [PROPOSAL.md](PROPOSAL.md)(영문 원본, 2026-10-14 05:30 UTC 기준)의 한국어 번역본이다. 표·수치·코드·파일 경로는 원본과 동일하며, 내용이 다를 경우 영문 원본이 기준이다.

> **이 파일에 대하여.** 프로젝트의 단일 문서다. 모든 대조군과 수정 사항을 포함한 전체 시간순 기록은 [results/FINDINGS.md](results/FINDINGS.md)에 있으며, 이 파일의 이전 장문 버전은 `results/archive/`에 보관되어 있다.

## 1. 문제 정의

LLM은 알고리즘 문제를 일상적으로 프로그램 작성으로 푼다. 볼록 껍질(convex hull), 점-다각형 포함 판정, 차량 경로 문제를 위한 솔버 모델 등이 그 예다. 이런 프로그램은 겉보기에 맞아 보여도 실패하는 경우가 많으며, 흔한 반사적 대응은 프롬프트에 더 많은 것을 넣는 것이다. 헬퍼, 문서, 추론 토큰 말이다.

**연구 질문.** 어떤 인-컨텍스트(in-context) 추가물이 계산기하(CG)와 조합 최적화(CO)용 LLM 작성 프로그램을 개선하거나 악화시키는가, 그 이유는 무엇인가, 그리고 어떤 실패에 어떤 저비용 해법을 어느 정도의 토큰 비용으로 써야 하는가?

1. **도구.** 정확하지만 불필요한 헬퍼 함수가 코드를 바꾸는가, 바꾼다면 어떻게 바꾸는가? *필요한* 도구도 해를 끼칠 수 있는가?
2. **사실.** 솔버 코드에서 정확한 API 사용법이 전체 매뉴얼, 검색(retrieval), 혹은 더 많은 추론보다 나은가?
3. **해법 선택.** 언제 샘플링해 레이블 없이 검사하고, 언제 추론에 비용을 지불해야 하는가? 강건성을 빠른 모델에 증류(distillation)할 수 있는가?

### 1.1 LLM은 왜 알고리즘 문제를 프로그램으로 푸는가

LLM은 답을 직접 말할 수도 있다("볼록 껍질의 꼭짓점은 7개다"). 그러나 파일럿에서 직접 답변은 크게 실패했다.

| 방식 (추론 모드 끔) | 기하: 8개 버전 모두 정답 | 기하: 동치 입력에 같은 답 | 최적화: 최적해 도달 |
|---|---|---|---|
| 직접 답변 (Qwen3-8B / 32B) | 22% / 23% | 인스턴스의 **0%** | held-out 문제: .06–.19 (Llama-70B .02) |
| 프로그램 작성 후 실행 (Qwen3-8B) | **92–97%** | 과제별 50–100% (점-다각형 포함 판정이 최저) | API 스니펫을 준 솔버 프로그램: .71–.97 |

1. **정확한 계산을 실행에 맡긴다.** 직접 답변의 21%는 산술 도중 토큰이 바닥났다. 넓이의 두 배가 436인 다각형에 대해 Qwen3-8B는 원본, 평행이동, 회전, 대칭 사본에서 각각 436, 2944, 392, 728이라고 답했으며, 실행된 프로그램은 8개 버전 모두에서 정답이다.
2. **프로그램 하나가 모든 입력 크기를 처리한다.** 직접 답변은 크기가 커질수록 나빠진다(배낭 문제 최적 갭: 물건 10개 6% → 80개 48%; TSP: 도시 8개 9% → 20개 139%). ZebraLogic에서도 관찰된 "복잡도의 저주(curse of complexity)"다. 약 350토큰의 OR-Tools 프로그램은 크기와 무관하게 같은 비용이 든다.
3. **프로그램은 정답 레이블 없이 검사할 수 있으며**, 이것이 검증된 샘플링(F4)을 가능하게 한다. 직접 답변은 일관성조차 없다(7개의 동치 버전에서 같은 답을 낸 인스턴스가 하나도 없었다. 꼭짓점이 6개인 볼록 껍질에 대해 직접 답변은 4, 10, 4, 4, 6, 6, 6, 11이었고, 프로그램은 8개 모두에서 6을 출력했다).
4. **솔버는 수십 년의 공학을 재사용한다.** 모델은 문제를 *정식화*하기만 하면 된다. 4색이 필요한 노드 40개 그래프 6개에서 직접 답한 색칠은 모두 유효하지 않았고, CP-SAT 모델은 6개 중 5개에서 최적인 4색을 찾았다.
5. **LLM은 학습에서 풀이 과정보다 훨씬 많은 코드를 보며**, 프로그램 보조 추론(PAL, Program-of-Thoughts, Logic-LM)은 확립된 방법이다.

이 프로젝트가 연구하는 그 대가는 새로운 실패 유형(실행 환경 불일치, 솔버 API 오용, 퇴화 입력, 건전하지 않은 알고리즘)이며, 이 모두가 프롬프트의 영향을 받는다.

## 2. 배경 (관련 연구)

2026-10-13에 발견별로 확인했다. 판정과 링크를 담은 전체 표: `results/RELATED_WORK.md`.

- **코드를 조향하거나 오도하는 컨텍스트** (2606.04057; 2609.14157; 2608.11888; 2503.20589; 2306.03438; CodeCrash 2504.14119; 이전 형태로 GSM-IC, RAG-MCP, ToolRet): 프롬프트의 단서, 불필요한 도구, 그럴듯한 스킬, 오도하는 코드가 생성 코드를 악화시킨다. *본 연구:* 정확하지만 불필요한 헬퍼가 정확도를 무너뜨리며, 로짓 증거, 용량-반응 관계, 추론 모델의 면역, 입력 파싱 경로를 보인다.
- **명세가 부족한 도구와 계약** (2602.14878; DRAFT 2410.08197; ContractEval 2510.12047). *본 연구:* 같은 헬퍼를 전제조건이 있는 경우와 없는 경우로 짝지어 비교하면, 필요한 헬퍼가 헬퍼가 없을 때보다 나쁘며 이는 2개 계열 4개 모델에서 나타난다.
- **솔버 코드를 위한 문서** (DRoC, ICLR 2025; CP-Bench 2506.06052; Jain et al. 2024; 아깝게 빗나간 문서 2401.14887). *본 연구:* 같은 비용에서 정확한 스니펫이 전체 매뉴얼과 추론을 모두 이긴다.
- **명시된 명세보다 사전 지식(prior)을 따르는 현상** (2505.17225; 2507.14417; 2305.15507). *본 연구(정정):* VRPTW 사례는 이렇게 보였지만 실제로는 우리 형식 문자열의 모호한 필드 이름 때문이었다(F3). 남는 것은 진단 방법(반사실적 재실행, 형식 재진술)이다.
- **선택, 확신도, 연산 배분** (MBR-exec, CodeT, S*, incoherence 2507.00057; 메타모픽 프롬프트 2406.06864; 인스턴스 변형 2607.16646; 토큰 확신도 2402.02047, 2610.11300, Coder-Reviewer; DART 2606.23181; 무차별 대입 오라클 ALGO, ExeCRE 2608.04439). *본 연구:* 주어진 인스턴스의 변환 사본에서의 일관성, 헬퍼에 의해 뒤집히는 확신도, 그리고 고정 추론 예산에 지는 검사 게이트 라우팅.
- **망각과 자기 replay** (2510.18874; 2601.19897; 2501.14315; SDFT; RL's Razor). *본 연구:* 같은 프롬프트에서 학생 자신의 프로그램과 같은 가중치의 교사 프로그램을 대비하며, 관용구 표류가 프로그램에서 직접 보인다.
- **LLM 코드의 실패 분류** (2406.08731; 2407.06153; 2403.08937). *본 연구:* 반사실적 재실행에 기반한 행동 라벨과 유형-처방 지도.

**공백.** 개별 메커니즘 대부분에는 반드시 인용해야 할 가까운 선행 연구가 있다. 새로운 것은 조합이다. 정확한 변성(metamorphic) 채점, 하나의 사실(헬퍼, 계약, API 호출, 입력 필드)만 분리하는 짝지은 개입, 그리고 토큰 비용하에서 오류 유형별 처방 비교다.

## 3. 동기

1. **실용성.** 코드 어시스턴트는 도구 카탈로그와 문서 덤프를 받는다. 그럴듯한 도구가 알고리즘을 조용히 바꾼다면, "모델에게 모든 것을 주라"는 잘못된 기본값이다.
2. **측정 가능성.** 정확한 오라클과 증명된 최적해 덕분에 작은 프롬프트 효과도 측정할 수 있다.
3. **파일럿에서 나타난 큰 효과**(4.2절). 헬퍼 하나가 볼록 껍질 정확도를 97%에서 8%로 떨어뜨리고, 5줄짜리 API 스니펫은 차량 경로 문제를 .23에서 .90으로 끌어올린다(추론만으로는 .03).

## 4. 실험 설계

### 4.1 설정

**과제**(모두 정확한 참조 정답과 함께 생성):

| 도메인 | 핵심 | 홀드아웃(첫 발견 이후 설계) | 더 어려운 다단계 과제 |
|---|---|---|---|
| 기하 | 볼록 껍질 꼭짓점 수, 다각형 넓이 ×2, 점-다각형 포함, 선분 교차 개수, 최근접 쌍 | 볼록성 판정, 삼각형 내부 점, 볼록 다각형 겹침; 사전 등록(E2): Delaunay 검사, 가장 먼 점 쌍(farthest pair) | 다각형 내부 격자점(Pick), 직사각형 합집합 넓이(스윕 라인), 다각형 클리핑(정확한 유리수 교차 넓이) |
| 최적화 | 0/1 배낭, TSP, 그래프 색칠, makespan 스케줄링 | 빈 패킹, 정점 덮개 | 용량 제약 차량 경로(CVRP), 시간 창 VRP(VRPTW) |

- **기하 평가:** 인스턴스마다 8개의 동치 버전(평행이동, 회전, 반사, 순열, 스케일, 10^9 오프셋, 퇴화 사례)이 있으며, 프로그램은 8개 모두에서 맞아야만 정답으로 인정된다.
- **최적화 평가:** 증명된 최적해(DP, Held–Karp, 정확한 CP-SAT)까지 푼 비율이며, 솔버 조건은 OR-Tools와 최대 2회의 수리(repair) 라운드를 사용한다.

**개입.** 헬퍼 도구 상자(필요한 헬퍼 = K0, 여기에 추가 헬퍼 K개, K는 최대 10); 숨은 헬퍼 계약; 문서 변형과 BM25 검색; 힌트; 검증된 샘플링; 추론 모드(thinking); LoRA 증류.

**모델.** Qwen3 1.7B / 8B / 14B / 32B-AWQ; Llama-3.1-8B, Llama-3.3-70B; DeepSeek-R1-Distill-Llama-70B; gpt-oss-20b / 120b(low / medium / high 추론 강도). A100에서 vLLM 0.10.2를, 2026-10-13부터는 RTX PRO 6000 Blackwell GPU에서 vLLM 0.22를 사용했으며, 후자는 이전 셀의 개수를 정확히 재현했다(예: VRPTW 27/30, 21/30, 8/30, 18/30, 0/30). 각 비교는 하나의 스택만 사용한다.

**통계와 대조군.** 기하 조건당 300개 프로그램(과제당 60개), 핵심 셀은 2–3 시드, 대응 부트스트랩(paired bootstrap) 95% CI. 헬퍼는 실행 시 미리 정의된다(복사하지 않은 헬퍼 호출은 실패로 집계하지 않는다). 참조 해답은 모든 하네스를 통과하며(480/480), 새로운 모델 계열은 반드시 출력 추출 감사(audit)를 거친다.

메커니즘(오프-이디엄 이탈, off-idiom drift):
- **알고리즘이 바뀐다.** hull 프로그램의 44–75%가 monotone chain에서 제공된 `polar_sort` 위에 구축한, 실패하는 Graham scan으로 전환한다.
- **헬퍼 하나로 충분하다**(사전 등록, `results/PREREG_E4.md`). `polar_sort` + `collinear`는 hull 정확도를 97%에서 8%(8B), 83%에서 6%(32B)로 떨어뜨린다. "암시적이지 않은" 헬퍼는 무해하다는 사전 등록 예측은 빗나갔다(이들도 15–38점을 깎는다).
- **선택은 로짓에서 보인다.** 도구 상자는 각 모델이 직접 샘플링한 헬퍼 경로 프로그램의 가능도를 180개 인스턴스 100%에서 토큰당 0.40–0.71 nats 높이며, 이 이동은 주로 import와 헬퍼 이름에 몰려 있다.
- **도메인 대비.** 최적화에서는 불필요한 API 8줄이 아무것도 바꾸지 않는다. 격자점 과제에서는 추가된 `point_in_polygon`이 오히려 도움이 된다(Llama-70B 60개 중 0 → 45).
- **새 과제에 대한 사전 등록 실험(E2, 가장 먼 점 쌍; `results/PREREG_E2.md`).** `convex_hull` + `polar_sort`를 주면 Qwen3-32B는 프로그램의 97%에서 hull 기반 코드를 작성하고 21.7점을 잃는다(CI [−31.7, −11.7]). 알고리즘을 암시하지 않는 헬퍼는 입력 파싱을 통해 오히려 더 많은 46.7점을 깎는다. 이 조건의 실패 66건 중 64건은 명시된 개수 줄(count line)까지 포함해 모든 입력 줄을 점으로 읽는다. 해당 인스턴스의 실제 입력을 보여 주는 F3의 해법이 이를 없앤다(120개 중 54 → 119). "알고리즘을 암시하는 헬퍼만 해롭다"는 사전 등록 예측은 32B에서 빗나갔다.
- **공개된 컨텍스트 처방은 이를 되돌리지 못한다(B3, 사전 등록).** 도구 범위에 관한 한 문장 지시(2609.14157 방식)는 피해의 2–3%만 회복하고, System 2 Attention은 핵심 과제를 11점 *악화*시키며 입력 형식 경로만 고친다(120개 중 54 → 98).
- **문제 크기가 커지면 더 커진다(H1, 사전 등록):** 점 2,000–20,000개와 10초 제한에서 모든 헬퍼는 Qwen3-8B / 32B를 30 / 35점 떨어뜨린다(hull 80개 중 80 → 14). 작은 입력의 두 배다. gpt-oss는 low 노력에서도 헬퍼 유무와 상관없이 92–98%를 푼다.
- **붙여 넣은 코드가 없어도 일어난다(L1, 사전 등록):** 시그니처와 한 줄 설명만 있는 import 가능한 라이브러리로 제공해도 같은 추가 헬퍼가 Qwen3-32B를 19.3점 떨어뜨린다(hull 120개 중 104 → 32, hull 프로그램 120개 중 84개가 `polar_sort`를 import). Qwen3-8B에서는 새 실패가 더해진다. 라이브러리에 없는 함수를 import한다(실패한 hull 프로그램 54개 중 53개가 `from geomlib import convex_hull`). 한 문장("모듈에는 정확히 이 함수들만 있다", L2)이 그런 import를 없애지만(106 → 3개 프로그램; hull 120개 중 13 → 103) 조향은 없애지 못한다(추가 헬퍼가 있으면 8B는 8.8점, 32B는 20.0점을 잃는다).
- **우리가 만들고 시험한 방법(사전 등록; 실행 전 선행 연구 확인; `results/PREREG_M1.md`, `PREREG_M2_M4.md`).** 모델이 헬퍼 없이 쓴 초안의 확률을 낮추는 헬퍼를 빼는 확률 필터(M1)는 보정 단계에서 실패한다. 필요한 헬퍼도 해로운 헬퍼만큼 강하게 표시한다. 헬퍼를 보기 *전에* 프로그램을 쓰고 그 뒤 헬퍼를 쓰도록 리팩터링하는 방법(M4)은 피해가 조향일 때 저렴하고 강하지만(핵심 과제, 8B: 600개 중 579 대 모든 헬퍼 468, ≈0.8k 토큰), 전체로는 1,024토큰 추론 예산에 진다(통합 8B 89.0 대 94.5%, 32B 85.2 대 90.0%, 토큰은 절반 정도). 알고리즘을 유지하라는 문장 자체는 기여가 없다. 헬퍼마다 프로그램을 써서 탐색하는 방법(M3)은 틀린 프로그램이 일관적인 `polar_sort`를 남기고 6–10k 토큰이 든다. 가장 강한 방법은 공개된 것이다. 도구 상자가 있을 때와 없을 때 쓴 표본에 대한 TroVE 방식 투표(통합 91.2 / 95.0%)로, 두 문맥이 서로 다른 과제에서 실패하기 때문이다. 우리의 저비용 변형(M5: M4의 초안과 리팩터링 결과가 다르면 변성 검사를 통과하는 쪽을 택함)은 32B에서 ≈0.8k 토큰으로 91.5%에 도달해 추론 예산(1.6k 토큰에서 90.0%)보다 높고, 8B에서는 효과가 없다.
- **어려운 벤치마크용 방법(N1–N3, `results/PREREG_N.md`).** 출력을 보존하는 변환으로 문제 본문의 예제를 정답이 붙은 추가 테스트로 바꾸는 방법(N1, 새 방법)은 실패한다. 변환이 올바른 경우에도 예제를 통과한 틀린 프로그램의 6%만 잡아낸다. 대회 문제의 오류는 대칭 변환에서도 그대로 남기 때문이다. 실패한 예제를 보여 주고 한 번 고치게 하는 방법(N2)은 gpt-oss-20b low를 40.2 / 37.0%(시드 1 / 2)에서 45.0 / 44.7%로 올리고(+0.75k 토큰), 두 번째 표본 + 예제 검사와 같은 정확도를 약 25% 적은 토큰으로 낸다(gpt-oss-120b low: 4.6k 토큰에 46.0 → 53.1%, low와 medium 사이). 틀린 답의 13–19%를 고치지만 포기한 경우는 거의 고치지 못하고, 올리기 전에 고치는 조합(N4)은 약 1점만 더한다. 예제를 통과하지 못할 때만 medium으로 올리는 방법(N3, 공개된 아이디어)은 7.6k 토큰에 49.8%로, medium 단독(8.7k 토큰에 47.1%)보다 낫다. 모델이 자기 경로 문제 실패에서 사실을 스스로 캐내게 하면(FM; 가장 가까운 선행 연구: Dynamic Cheatsheet) 필요한 세 사실 중 둘을 찾고, 보지 않은 48개 사례를 7%에서 20–40%로 올린다(손으로 쓴 사실: 100%). 실행 가능성을 높일 때만 사실을 받아들이는 검증은 오히려 해롭다. 사실들이 함께 작동하기 때문이다. 겨냥한 실패를 절반 이상 줄일 때 받아들이면(FM2) 독립 체인 6개에서 17–65%(평균 32.5%; 가장 좋은 체인만 "고객을 선택 사항으로 만들지 말라"를 찾음)이고, gpt-oss-20b에는 도움이 되지 않으며, 검증 없이는 사실 목록이 3–10%로 무너지며, 여섯 체인의 사실을 모아 가지치기해도 나아지지 않는다(21–27%). 부분적 음성 결과다. 프로그램 16개로 하는 검증은 잡음이 너무 크고, 캐낸 사실은 산문 형태의 국소 수정인 반면 손으로 쓴 사실은 작동하는 코드이기 때문이다. CP-SAT를 쓰는 job-shop(H5, 교과서적 API)에서는 사실이 필요 없다. 79–85%가 실행 가능하고, 실행 가능하면 최적이다.

**결론이 그냥 "추론 모드를 쓰라"인가? 아니다.** 추론 모드가 효과가 있는 이유는 모델이 코드를 쓰기 전에 알고리즘을 고르기 때문이다. 그 선택을 고정하는 다른 방법도 훨씬 적은 비용으로 똑같이 효과가 있다(8B):

| 같은 피해에 대한 해법 | 정확도 | 프로그램당 출력 토큰 |
|---|---|---|
| 없음(추가 헬퍼 8개, 추론 모드 없음) | 76–78% (최악의 헬퍼 2개를 준 hull: 7%) | ≈0.8–1.1k |
| 전체 추론 모드 | 97% | ≈6k (예시 인스턴스에서 ≈15k) |
| 한 문장 알고리즘 힌트, 추론 모드 없음(hull, 최악의 헬퍼 2개, 3 시드) | 94% | ≈0.6k |
| 증류된 LoRA, 추론 모드 없음(F5) | 98% | ≈0.35k |
| 추가 헬퍼를 아예 제공하지 않음 | 92–97% | ≈0.3k |

추론 모드는 숨은 계약(F2)이나 누락된 API 사실(F3)은 막지 *못한다*. 실용적 메시지는 **도구 설계**다. 필요한 헬퍼만 제공하고, 의도한 알고리즘을 명시하며, 예시 입력을 하나 보여 주라. 추론은 대비책이다.

![용량-반응: 추가 헬퍼 수에 따라 피해가 커진다](figs/fig2_distractor_dose.png)

> **예시 F1** (Qwen3-8B, 동일 인스턴스, 네 가지 조건). *필요한 헬퍼만*: 교과서적인 monotone chain으로, 8개 버전 모두에서 정답.
> ```python
> points = sorted(set(points))
> for p in points:
>     while len(lower) >= 2 and orient(lower[-2], lower[-1], p) <= 0:
>         lower.pop()
>     lower.append(p)
> … (same for the upper hull)
> return lower[:-1] + upper[:-1]
> ```
> *추가 헬퍼 8개*: 모델은 헬퍼 정의 11개를 모두 복사하고 `polar_sort` 위에 Graham scan을 구성한다(시작점을 리스트 안에 남기고, 불필요한 공선 점 제거 단계를 덧붙임). 8개 모두에서 오답.
> ```python
> left = min(points, key=lambda p: (p[0], p[1]))
> sorted_points = polar_sort(points, left)        # the offered helper decides the algorithm
> hull = [left, sorted_points[0]]                 # sorted_points still contains `left`
> …
> for i in range(len(hull)):                      # extra pass suggested by `collinear`
>     a, b, c = hull[i-2], hull[i-1], hull[i]
>     if orient(a, b, c) != 0:
>         final_hull.append(hull[i])
> ```
> *같은 헬퍼 + "Hint: Andrew's monotone chain …"*: monotone chain, 정답, 563 토큰. *같은 헬퍼 + 추론 모드*: 같은 결과지만 15,168 토큰.

**F2. 필요한 도구라도 숨은 계약(hidden contract)이 있으면 함정이 된다.**
- lattice 과제에 필요한 헬퍼는 *부호 있는* 면적을 반환한다. 모델은 `abs`를 빠뜨리고, 시계 방향 입력에서 Pick 공식이 실패한다. Qwen3-32B는 60개 중 44개에서 9–15개로 떨어진다. 도구를 고치면 46–49개로 회복되지만, docstring 경고로는 회복되지 않는다(17–19개).
- 추론은 위험을 줄이지만 없애지는 못한다(추론 모드의 Qwen3-8B 52 대 60, 부호 있음 대 부호 없음; toolbox를 준 R1-Distill-70B 57 → 42). 헬퍼가 없어도 gpt-oss는 clipping 실패 45건 중 35건에서 반시계 방향 입력을 가정한다.
- **사전 등록 재현(E2, Delaunay 검사: 외접원이 어떤 점을 엄밀히(strictly) 내부에 포함하는 삼각형의 개수를 센다).** 필요한 헬퍼 `in_circle`은 삼각형이 반시계 방향이어야 한다고 짧게만 언급한다. Qwen3-8B / 32B는 이 헬퍼로 120개 중 1 / 3개를 풀고(32B는 헬퍼가 없으면 55), 방향과 무관한(orientation-free) 버전으로는 109 / 106개를 푼다. 실패의 92% / 97%는 대칭 사본이나 꼭짓점 번호를 바꾼(relabelled) 사본에서만 틀린다. 자세히 풀어 쓴 경고는 격차의 16%(8B) / 75%(32B)를 회복한다. Llama-3.3-70B와 Qwen3-14B도 걸려들고(8 → 120, 4 → 120; 헬퍼 없음: 81, 76), gpt-oss-20b는 그렇지 않다(118 대 117). 추론 모드는 32B에서는 함정을 없애지만(118 대 120) 8B에서는 일부만 줄이며(51 대 118), 헬퍼를 고치는 데 드는 ≈0.4k 토큰과 달리 7.8–8.8k 토큰이 든다. 모델이 직접 쓴 헬퍼 문서(DRAFT 방식, B3)는 시계 방향 삼각형을 한 번도 시험하지 않는다(32B: 180개 중 27). 하네스 쪽 탐침이 검증해 넣은 동작 문장("입력을 대칭시키면 결과의 부호가 바뀐다"; M2)도 도움이 되지 않는다(120개 중 0 / 10 대 손으로 쓴 경고 18 / 80).

> **예시 F2** (Qwen3-32B, 다각형 내부 격자점, 필요한 헬퍼만 제공). 대칭(mirrored) 사본과 순서 뒤집은(reversed) 사본에서 틀린다(부호 있는 면적이 음수).
> ```python
> def polygon_area2(poly):        # twice the signed area (shoelace, exact)   <- the offered helper
> …
> area2 = polygon_area2(poly)     # negative for clockwise vertex order; no abs()
> A = area2 // 2
> I = A - boundary_points // 2 + 1
> print(I)
> ```
> 주석에 "NEGATIVE for clockwise; use abs()"라는 경고를 추가하면 60개 프로그램 중 38개가 경계점을 잘못 세는 brute force로 바꾼다.

- 5줄짜리 정확한 스니펫이 모든 크기에서, 그리고 held-out 문제에서도 전체 매뉴얼을 이긴다. **근접 오답 문서(near-miss reference)는 문서가 없는 것만큼 나쁘다.** 전체 시트(용량 제약 없는 TSP 라우팅)를 주면 32B는 CVRP .07에 그치고, CVRP 스니펫은 VRPTW에서 0을 준다.
- **정정(2026-10-13): VRPTW의 "누락된 필드"는 우리 프롬프트의 모호한 헤더 때문이었다.** 우리는 헤더를 `n capacity K service horizon`으로 적었고, gpt-oss-120b는 거의 모든 프로그램에서 이를 `n capacity K horizon`으로 읽었다(30개 중 0–3개만 `service`를 읽음). 그 결과 horizon이 10이 되어 솔버가 실행 불가능(infeasible)을 보고했으며, 필드를 뺀 입력으로 다시 실행하면 49개 중 43개가 최적이다. 필드를 다시 진술하게 하면 모델은 "… maximum route end time (service horizon)"이라고 쓴다. *service horizon*을 하나의 복합 명사로 읽은 것이다. 헤더를 `n capacity K service_time horizon`으로 쓰면 120b low는 30/30, 30/30, 20b low는 29/30, 29/30이 최적이다(F3y). 즉 명확한 명세를 사전 지식이 덮어쓴 것이 아니라 우리 명세의 모호함이었다. 22개 형식 문자열 전체에 대한 감사(A1)에서 체계적으로 잘못 읽힌 것은 이 헤더뿐이었다(gpt-oss-120b, gpt-oss-20b, Qwen3-8B 모두 3번 중 3번).
- **해당 인스턴스의 실제 입력을 보여 주면 모호함이 해소되고 토큰도 줄어든다.** 스니펫과 함께 주면 120b low는 0 → .97–1.00(인스턴스당 4.8k → 1.7k 토큰), 120b medium은 .07 → 1.00(10.7k → 3.7k), 20b low는 .07–.17 → .80–.97이 되며, 필드를 건너뛰는 프로그램은 30개 중 18–29개에서 0–3개로 줄어든다. 필드를 다시 진술하게 하는 것은 도움이 되지 않으며(gpt-oss 30개 중 0–2개), DRoC 방식 검색(B4, 사전 등록)은 단순 top-3보다 낫지만(+.12~+.15) 정확한 스니펫보다는 못하다(−.12~−.40).
- **추론은 사실을 대체할 수 없다.** 문서 없이 추론만 켜면 14B / 32B / R1-Distill-70B가 프로그램당 11–19k 토큰을 쓰고도 CVRP에서 .33 / .03 / .00에 그치며, 스니펫을 주면 .97 / .97 / .90이다. **검색(retrieval)은 정확할 때 효과가 있다.** BM25 top-1은 손으로 쓴 스니펫과 맞먹고(32B .965 대 .956), top-3은 근접 오답을 끌어온다(CVRP .78 → .55).

**F5. 강건성은 과제별로 빠른 모델에 증류(distillation)할 수 있으며, 학생(student) 모델 자신의 프로그램을 replay하면 다른 과제가 보호된다.**
- 같은 모델이 추론을 *켜고* 작성한 검증된 프로그램 600개(추가 헬퍼 0/4/8개 프롬프트)로 Qwen3-8B에 LoRA를 학습하면, 추가 헬퍼 8개 조건에서 77.0 → **98.0**(+21.0 [+17.8, +24.3], 2 seed)이 되며 ≈6k 대신 ≈350 토큰을 쓴다. 깨끗한 프롬프트로만 학습하면 이득이 없다. 모델은 헬퍼를 무시하는 법을 배운 것이다.

- **학생 모델 자신의 프로그램을 replay하면 피해가 사라진다(E4, 사전 등록; `results/PREREG_E4_REPLAY.md`).** hull을 제외하고 학습한(leave-hull-out) LoRA, 깨끗한 프롬프트의 hull 기준: 기본 모델 109/120, replay 없음 48, **+ 다른 과제 5개에 대해 학생 모델 자신이 추론 없이 작성한 검증된 프로그램 270개: 118**, + 정확히 같은 270개 프롬프트에 대한 추론 교사(teacher) 모델의 프로그램: 36(자기 − 교사 +68.3 [+60.0, +76.7]). 과제 내 강건성은 유지된다(240/240). 기본 모델과 자기 replay 모델은 hull 프로그램 120/120에서 monotone chain을 쓰지만, replay 없는 학생과 교사 replay 학생은 각각 59개와 49개에서만 쓴다. 새 Delaunay 과제에서는 두 replay 조건 모두 여전히 떨어진다(60개 중 59 → 47 / 45).
- **기존 처방과의 비교(B2, 사전 등록):** WiSE-FT는 hull과 과제 내 이득을 맞바꾼다(α 0.5: 119 / 240개 중 222; α 0.75: 96 / 236). SDFT는 피해를 절반으로 줄이고(85), 학생 자신의 프로그램만으로 학습하면 104 / 235다. 둘 다 지키는 것은 자기 replay뿐이다(118 / 240). hull도 학습하고 convex를 남겨 둔 E4b에서 자기 replay는 헬퍼 8개 아래의 convex를 기본 수준으로 지키면서(120개 중 81 → 80; replay 없음 55, 교사 replay 42) 큰 과제 내 이득도 유지한다(300개 중 236 → 295). 두 번째 학습 시드(R1)에서도 두 대비가 재현된다. 자기 replay 대 교사 replay는 118 대 28(hull), 85 대 34(convex)다.

## 5. 한계

1. **합성 과제.** 다단계 과제(clipping, VRPTW)가 주요 효과를 재현하지만, 실제 코드베이스는 더 크고 덜 명세된 맥락을 가진다. 더 어려운 점검(H1, H2): 큰 입력(점 20,000개, 시간 제한)은 추론 모델에게 여전히 쉽지만(gpt-oss 92–98%), 실제 Codeforces 기하 문제 31개는 어렵다(추론 모드를 끈 Qwen3 ≤ 10%, gpt-oss-120b medium 66%, 5문제는 아무도 못 풂). 그곳에서(H2b) 가장 싼 이득은 짧은 추론 예산과 문제 본문의 예제를 점검으로 쓰는 것에서 나온다(Qwen3-32B think-1,024, 예제를 통과한 3개 표본 중 첫 번째: 토큰 10k에 38.7%, 전체 추론 14k의 30%보다 높음). gpt-oss-120b는 medium 한 번이 걸러낸 low 표본 8개보다 토큰 1/4로 더 낫다. 강한 모델의 틀린 프로그램도 예제는 많이 통과한다. 검증된 311문제 전체(H2c)에서도 성립한다. Qwen3-32B think-1,024 × 3 + 예제 검사는 전체 추론과 같은 정확도(30.2 대 29.9%)를 토큰 64%로 내고, gpt-oss-120b medium 한 번(6.8k 토큰에 56.8%)이 low 세 번 + 선택(9.7k 토큰에 54.3%)보다 낫고, 2300 이상 문제는 어떤 단일 시도로도 35% 미만이다. 표준 Solomon 경로 문제 56개(H3)에서 Qwen3-32B와 gpt-oss-20b의 프로그램은 파일의 처음 몇 줄을 보여 줘도 대부분 벤치마크 파일 형식을 읽다가 실패한다(112개 중 0–18개만 실행 가능한 해). 실행되는 프로그램은 기준 대비 약 3% 이내이므로, 입력 형식이 첫 번째로 빠진 사실이다. 올바른 입력 읽기 함수와 견고한 솔버 스니펫, 두 사실을 모두 주면 gpt-oss-120b는 low에서 56개 모두 실행 가능한 해를 내고(중앙값 격차 1.5%), gpt-oss-20b는 24–25개다. 어느 한 사실만으로는 부족한데, 세 가지 사실이 합쳐져야 한다. 파일 구조, "OR-Tools는 모든 곳에 정수를 받는다"(모델은 스스로 `1e7` 같은 실수 리터럴을 넣어 이를 어긴다), 그리고 시간 창이 좁을 때도 작동하는 첫 해 전략이다(H3b, H3c). Qwen3-32B는 56개 중 0–3개에 머문다. 주어진 호출을 존재하지 않는 시그니처로 바꿔 쓰기 때문이다. 실제 문제에서 F1의 헬퍼는 다르게 작용한다(H4, 311문제). 추론을 끈 Qwen3-32B에는 영향이 없지만(12.1 → 13.7%), gpt-oss-20b low는 4.3점 잃는다(p ≈ 0.001). 대부분 헬퍼를 전혀 호출하지 않는 프로그램에서이며, 어떤 도구 상자든 프롬프트에 있으면 모델이 덜 추론하기 때문이다(무관한 헬퍼 −2.1, "대부분 필요 없음" 머리말 −2.3, 둘 다 유의하지 않음). gpt-oss-120b는 영향이 없다(−0.8).

2. **부분적으로 사후적인 메커니즘.** 관용구 이탈(off-idiom drift)은 데이터를 본 뒤에 세운 설명이다. 사전 등록 검증이 그 핵심을 확인했지만 유사도 기반 예측은 반박했으며, 새 과제에서는 알고리즘을 암시하지 않는 헬퍼가 대신 입력 파싱을 통해 피해를 주었다.
3. **Oracle 처방.** 스니펫과 힌트는 손으로 작성했다. 검색은 정확한 페이지를 가져올 때만 이에 필적하며, 배포 가능한 레이블 없는 검사는 변환에 불변인 오류를 놓친다(E3).
4. **범위.** 공개 가중치 모델만 다뤘다(세 계열; E5는 실행하지 않음). 일부 부차적 셀은 단일 seed이다.
