# 도구, 사실, 검사: LLM이 작성한 기하·최적화 코드는 언제 실패하며, 어떤 해법을 써야 하는가

*대학원 NLP 수업 프로젝트 제안서: 계산기하(computational geometry)와 조합 최적화(combinatorial optimization)*

> **번역 안내.** 이 파일은 [PROPOSAL.md](PROPOSAL.md)(영문 원본, 2026-10-15 기준)의 한국어 번역본이다. 표·수치·코드·파일 경로는 원본과 동일하며, 내용이 다를 경우 영문 원본이 기준이다.

> **이 파일에 대하여.** 프로젝트 제안서의 요약본이다. 모든 대조군과 수정 사항을 포함한 전체 기록은 [results/FINDINGS.md](results/FINDINGS.md)에 있으며, 이전 장문 버전은 `results/archive/PROPOSAL_ko_before_compact_2026-10-15.md`에 보관되어 있다.

## 0. 입문: LLM은 기하·최적화 문제를 어떻게 푸는가

**문제.**
- **계산기하:** 좌표로부터 정확한 답을 계산한다. 다각형의 넓이, 점 집합의 볼록 껍질(convex hull) 등이다.
- **조합 최적화:** 매우 많은 선택지 중 가장 좋은 것을 고른다. 가장 짧은 배송 경로, 그래프를 칠하는 가장 적은 색 수 등이다. 답이 유효한지 확인하기는 쉽지만, 그것이 최선임을 증명하기는 어렵다.

**LLM이 이런 문제를 푸는 여섯 가지 방식:**

| 방식 | 작동 방식 | 예시 | 대표 연구 |
|---|---|---|---|
| 1. 직접 답하기 | 모델이 글로 답을 계산해 낸다 | "넓이의 두 배는 436이다." | chain-of-thought; 추론 모델 |
| 2. 추측 개선하기 | 모델이 해를 제안하고, 점수를 보고, 더 나은 해를 제안한다 | "경로 1-3-2-4의 길이는 120이다. 더 짧은 경로를 내라." | OPRO |
| 3. 프로그램 작성 | 모델이 코드를 쓰고, 컴퓨터가 실행한다 | `print(abs(sum(x1*y2 - x2*y1 ...)))` (신발끈 공식으로 넓이) | PAL, AlphaCode |
| 4. 솔버 사용 | 모델이 문제를 솔버 코드로 쓰고, 솔버가 최선의 답을 찾는다 | 간선마다 `m.Add(c[a] != c[b])`, 그다음 `m.Minimize(k)` (그래프 색칠) | OptiMUS, ORLM |
| 5. 휴리스틱 진화 | 규칙의 여러 버전을 시험해 가장 좋은 것을 남긴다 | 다음 물건을 어느 빈에 넣을지 정하는 `priority(item, bins)`를 진화 | FunSearch, EoH |
| 6. 증명기 돕기 | 모델이 단계를 제안하고, 기호 엔진이 기하 정리를 증명한다 | "AB의 중점을 추가하라" 이후 엔진이 증명을 마친다 | AlphaGeometry |

방식 1과 2는 문제가 커지면 무너지고, 6은 계산이 아니라 정리를 증명한다. 실제로 기하는 3으로, 최적화는 3과 4로 풀며, 보통 고리 안에서 쓴다. 프로그램을 여러 개 쓰고, 검사를 통과한 것을 남기고, 실패한 것을 고친다.

**예시: 기하.** 꼭짓점 8개 다각형의 넓이의 두 배를 답이 같은 8개 사본(평행이동, 회전, 대칭 등)으로 묻는다. 직접 답하면 Qwen3-8B는 사본마다 436(정답), 2944, 392, 728을 낸다. 이 모델이 쓴 프로그램(신발끈 공식)은 8개 모두에서 정답이다.

**예시: 최적화.** 4색이 필요한 노드 40개 그래프를 칠한다. 직접 답변: 유효한 것이 없다. 직접 짠 휴리스틱: 40색을 쓰는 경우가 많다. 열 줄짜리 솔버 모델: 솔버를 잘못 쓴 데서 오는 오류(솔버 변수에 `max()` 사용)를 최대 두 번의 수정으로 고친 뒤, 6개 중 5개에서 최적인 4색을 찾는다.

**이 프로젝트**는 방식 3과 4를 연구한다. 이런 프로그램이 언제 실패하는지, 어떤 값싼 처방이 통하는지를 묻는다. 실제 대회 기하 문제 311개에서 문제당 프로그램 하나는 여전히 12–57%만 푼다.

## 1. 문제

LLM은 기하·최적화 문제를 주로 **프로그램을 써서** 푼다(위의 방식 3과 4). 이런 프로그램은 겉보기에 맞아 보여도 자주 틀리며, 흔한 대응은 프롬프트에 더 많은 것을 넣는 것이다. 헬퍼 함수, 문서, 더 많은 추론 토큰 말이다.

**연구 질문.** 프롬프트에 무엇을 더하면 LLM이 쓴 CG·CO 프로그램이 좋아지거나 나빠지는가, 왜 그런가, 그리고 어떤 실패에 어떤 값싼 처방을 몇 토큰의 비용으로 써야 하는가?

1. **도구.** 정확하지만 불필요한 헬퍼 함수가 프로그램을 바꾸는가? 필요한 도구도 해가 될 수 있는가?
2. **사실.** 솔버 코드에서 정확한 API 사용법이 전체 매뉴얼, 검색, 더 많은 추론보다 나은가?
3. **처방.** 언제 프로그램 여러 개를 뽑아 정답 없이 검사하고, 언제 추론에 비용을 써야 하는가?

## 2. 관련 연구

코드를 조향하거나 오도하는 프롬프트 맥락(2606.04057; 2609.14157; CodeCrash 2504.14119), 명세가 부족한 도구 계약(DRAFT 2410.08197; ContractEval 2510.12047), 솔버 코드를 위한 문서(DRoC, ICLR 2025; CP-Bench 2506.06052), 정답 없는 선택과 수정(CodeT, MBR-exec, AlphaCode의 거르기, Self-Debugging; Olausson et al., ICLR 2024), 미세조정에서의 망각과 자기 replay(2510.18874; SDFT). 발견별 상세 판정: `results/RELATED_WORK.md`.

**공백.** 이 메커니즘들은 일반 코드에서 하나씩 연구되었다. 우리는 정확한 참조 답이 있는 CG·CO에서, 프롬프트의 사실을 하나씩만 바꾸며 비교하고, 모든 처방에 토큰 비용을 붙인다.

## 3. 방법

- **정확한 답이 있는 과제.** 생성한 기하 과제(볼록 껍질, 넓이, 점-다각형 포함, 선분 교차, 최근접 쌍, 들로네, 격자점, 직사각형 합집합, 다각형 클리핑)와 최적화 과제(배낭, TSP, 색칠, 스케줄링, 빈 패킹, 정점 덮개, CVRP, VRPTW). 표준 벤치마크: Codeforces 기하 문제 311개(CodeContests, 공식 테스트), Solomon VRPTW 56개(고객 100명), job-shop 40개(la01–la40).
- **채점.** 기하: 인스턴스마다 동치 사본 8개(평행이동, 회전, 대칭, 번호 재배열, 10⁹ 이동, 퇴화)를 내고, 8개 모두 맞아야 정답으로 센다. 최적화: 증명된 최적해에 도달한 비율, 또는 실행 가능성과 최고 기록 대비 격차.
- **개입.** 불필요한 헬퍼 함수(0–10개), 숨은 조건이 있는 헬퍼, 문서(정확한 5줄 스니펫, 전체 매뉴얼, 검색), 실제 입력 하나, 정답 없는 검사를 곁들인 샘플링, 추론 예산, 오류로부터의 수정, LoRA 증류.
- **모델.** vLLM으로 로컬에서 돌린 공개 가중치 모델: Qwen3(1.7B–32B), Qwen3.8-27B, Llama-3.1-8B / 3.3-70B, R1-Distill-Llama-70B, gpt-oss-20b / 120b.
- **엄밀성.** 실행 전에 예측을 기록(`results/PREREG_*.md`), 시드 2–3개, 짝지은 부트스트랩 신뢰구간, 점수뿐 아니라 원본 프로그램을 읽음, 정확도는 항상 출력 토큰과 함께 보고.

## 4. 예비 결과

| 발견 | 근거(일부) |
|---|---|
| **F1. 불필요한 헬퍼가 알고리즘을 조향한다.** | 추가 헬퍼 8개: 추론 없이 Qwen3-8B / 32B −14 / −13점. 헬퍼 한 쌍이 볼록 껍질을 97%에서 8%로 떨어뜨린다(모델이 주어진 `polar_sort` 위에 짓는다). 추론이 이를 없애고(≈6k 토큰), 한 문장짜리 알고리즘 힌트도 그렇다(0.6k에 94%). 실제 대회 문제에서는 효과가 줄어든다(gpt-oss-20b −4.3점, 다른 모델은 없음). |
| **F2. 숨은 조건이 있는 필요한 도구는 함정이다.** | 반시계 방향 삼각형을 요구하는 들로네 헬퍼: Qwen3-8B / 32B가 120개 중 1 / 3개를 풀고, 방향과 무관한 버전으로는 109 / 106개를 푼다. 경고문은 차이의 16% / 75%를 되찾는다. |
| **F3. 솔버 코드는 빠진 API 사실 때문에 실패하며, 정확한 사실만 이를 고친다.** | 차량 경로(Qwen3-32B): 문서 없음 .23, 전체 매뉴얼 .07, 정확한 스니펫 .77–.90, 문서 없이 추론 .03. Solomon에서는 세 사실(파일 구조, OR-Tools에 정수, 좁은 시간 창을 위한 첫 해 전략)이 함께 필요하다. 이 사실들이 없으면 낮은 추론 노력에서 실행 가능한 프로그램이 0–6%이고, 있으면 gpt-oss-120b가 100%에 이른다. CP-SAT를 쓰는 job-shop에는 사실이 필요 없다(79–85%). |
| **F4. 오류 유형에 따라 처방을 고른다.** | 표본마다 다른 오류: 3개 중 최선 + 검사가 0.9k 토큰에 100%(추론은 5.5k에 91%). 모든 표본에서 반복되는 오류: 추론이 낫다. 대회 문제 311개에서는 실패한 예제를 보여 주고 한 번 고치는 것이 토큰당 가장 좋은 단계다(gpt-oss-120b low 4.6k 토큰에 46 → 53%). 추론 노력 low / medium / high는 46 / 57 / 66%다(high: 아직 시드 하나, 문제당 30k 토큰). |
| **F5. 강건성은 증류할 수 있고, 자기 replay가 다른 과제를 지킨다.** | 검증된 프로그램으로 LoRA: 헬퍼가 있을 때 77 → 98%, 토큰은 6k 대신 0.35k. 학생 자신의 프로그램을 섞으면 보지 않은 과제가 유지된다(120개 중 118, 섞지 않으면 48, 교사 프로그램이면 36). 대회 기하로는 이어지지 않는다. |

**우리 방법들**(선행 연구를 먼저 확인). *한 번 검증하고 재사용*이 효과가 있다. 훈련용 경로 문제 8개에서 작동하는 프로그램 하나를 골라 그대로 재사용한다. 그러면 gpt-oss-120b가 보지 않은 48개 중 94%에서 실행 가능한 해를 내며, 전체 비용은 28k 토큰이다. 인스턴스마다 프로그램을 쓰면 7%다. 같은 프로그램은 고객 200명과 400명 인스턴스에서도 실행 가능하다(각각 60개 중 60개; 격차 ≈ 4% / ≈ 11%). 작은 이득: 한 번의 수정, 예제를 통과하지 못할 때만 추론을 늘리기, 초안 후 리팩터링하고 변성 검사로 가르는 변형(Qwen3-32B 0.8k 토큰에 91.5%). 음성 또는 부분적: 확률·탐색 기반 헬퍼 필터, 예제의 대칭 변환으로 테스트 생성(틀린 프로그램의 6%만 잡음), 모델이 쓴 오라클, 검색한 예시 문제, 실패에서 사실 캐기(7% → 21–40%, 편차 큼), 대회 문제 증류.

## 5. 계획

1. **높은 추론 노력.** gpt-oss-120b high(66%, 시드 하나)를 시드 3개로 재현한다(실행 중).
2. **실제 과제에서의 숨은 계약.** 표준 벤치마크에서 F2를 직접 시험한다. 지금까지는 자연적 사례 하나뿐이다(실수를 반환한 읽기 함수가 OR-Tools의 정수 계약을 깸).
3. **정리.** 토큰 비용이 붙은 실패-처방 지도: 어떤 실패에 어떤 처방(정확한 스니펫, 실제 입력, 힌트, 샘플링 + 검사, 추론, 수정, 재사용)인가.
4. **선택 사항.** API 접근이 가능하면 폐쇄형 모델.

## 6. 한계

주요 효과는 생성한 과제에서 찾았다. 실제 벤치마크에서 F3와 F4는 성립하고 F1은 줄어든다. 처방(스니펫, 힌트)은 손으로 썼고, 자동 버전(검색, 사실 캐기)은 이를 일부만 재현한다. 공개 가중치 모델만 시험했고, 일부 부차적 결과는 시드 하나다.
