## 0. 배경: LLM은 기하·최적화 문제를 어떻게 푸는가

**문제.**
- **계산기하:** 좌표로부터 정확한 답을 계산한다. 다각형의 넓이, 점 집합의 볼록 껍질(convex hull) 등이다.
- **조합 최적화:** 매우 많은 선택지 중 가장 좋은 것을 고른다. 가장 짧은 배송 경로 등이다. 답이 유효한지 확인하기는 쉽지만, 그것이 최선임을 증명하기는 어렵다.

**LLM이 이런 문제를 푸는 여섯 가지 방식:**

| 방식 | 작동 방식 | 예시 | 대표 연구 |
|---|---|---|---|
| 1. 직접 답하기 | 모델이 글로 답을 계산해 낸다 | "넓이의 두 배는 436이다." | chain-of-thought; 추론 모델 |
| 2. 추측 개선하기 | 모델이 해를 제안하고, 점수를 보고, 더 나은 해를 제안한다 | "경로 1-3-2-4의 길이는 120이다. 더 짧은 경로를 내라." | OPRO |
| 3. 프로그램 작성 | 모델이 코드를 쓰고, 컴퓨터가 실행한다 | `print(abs(sum(x1*y2 - x2*y1 ...)))` (신발끈 공식으로 넓이) | PAL, AlphaCode |
| 4. 솔버 사용 | 모델이 문제를 솔버 코드로 쓰고, 솔버가 최선의 답을 찾는다 | 간선마다 `m.Add(c[a] != c[b])`, 그다음 `m.Minimize(k)` (그래프 색칠) | OptiMUS, ORLM |
| 5. 휴리스틱 진화 | 규칙의 여러 버전을 시험해 가장 좋은 것을 남긴다 | 다음 물건을 어느 빈에 넣을지 정하는 `priority(item, bins)`를 진화 | FunSearch, EoH |
| 6. 증명기 돕기 | 모델이 단계를 제안하고, 기호 엔진이 기하 정리를 증명한다 | "AB의 중점을 추가하라" 이후 엔진이 증명을 마친다 | AlphaGeometry |

실제로 기하는 방식 3으로, 최적화는 3과 4로 푼다. 직접 답변은 실패한다. 한 다각형의 넓이의 두 배를 동치 사본 8개(평행이동, 회전, 대칭 등)로 물으면 Qwen3-8B는 436(정답), 2944, 392, 728이라고 답하지만, 같은 모델이 쓴 프로그램은 8개 모두에서 정답이다.

## 1. 왜 중요한가

1. **이런 코드는 실제 시스템에서 쓰이며, 오류가 조용하다.** 코딩 어시스턴트와 에이전트는 이제 경로 계획, 스케줄러, 기하 루틴(지도, CAD, 로봇)을 쓴다. 틀린 프로그램도 실행되고 답을 출력한다. *예:* 원래 입력에서는 맞지만 대칭 입력에서는 틀리는 볼록 껍질 프로그램, 반올림 오류 때문에 고객의 시간 창이 막 닫힌 뒤에 도착하는 배송 계획.
2. **기본 관행은 "모델에게 더 많이 주라"이며, 그것은 공짜가 아니다.** 에이전트는 큰 도구 카탈로그와 문서 더미(RAG, MCP 서버)를 받고, 추론 모델은 문제당 30k 토큰까지 쓴다. *예:* 차량 경로 문제에서 Qwen3-32B에게 OR-Tools 전체 매뉴얼을 주면 문서가 없을 때보다 *나빠지고*(.07 대 .23이 최적), 정확한 5줄을 주면 맞힌다(.77–.90).
3. **이제 토큰 비용이 LLM 사용의 주된 비용이다.** *예:* 실제 대회 기하 문제 311개에서 gpt-oss-120b는 medium 노력(문제당 6.8k 토큰)으로 57%, high 노력(30k)으로 66%를 푼다. 9점을 더 얻으려고 비용이 4.4배가 된다. 1k 토큰짜리 처방이 30k 토큰짜리 추론과 같은 일을 하는 때를 알면 실제 돈과 시간을 아낀다.

**목표:** *무엇이 잘못되었는지*에서 *통하는 가장 값싼 처방*으로 가는 실용적인 지도를, 표준 벤치마크에서 정확한 답으로 측정해 만든다.

## 2. 질문과 시험 방법

**질문:** 프롬프트에 무엇을 넣어야 하고, 어떤 실패에 어떤 값싼 처방이 몇 토큰의 비용으로 통하는가? (1) 도구: 불필요한 헬퍼가 해가 될 수 있는가? (2) 사실: 전체 매뉴얼인가, 정확한 사용 예 하나인가? (3) 처방: 샘플링과 검사, 수정, 아니면 추론에 비용을 쓸 것인가?

- **정확한 답이 있는 벤치마크:** Codeforces 기하 문제 311개(공식 테스트), Solomon 차량 경로 문제 56개(고객 100명), job-shop 스케줄링 40 + 42개, 그리고 통제된 시험을 위해 우리가 생성한 기하 과제 13개와 최적화 과제 8개.
- **엄격한 채점:** 기하 프로그램은 입력마다 동치 사본 8개에서 모두 맞아야 하고, 경로·스케줄 계획은 실행 가능하며 최고 기록에 가까워야 한다.
- **한 번에 하나만 바꾸고** 그것이 없는 같은 프롬프트와 비교한다. 실행 전마다 예측을 기록하고, 시드 2–3개를 쓰며, 정확도는 항상 토큰 비용과 함께 보고하고, 점수뿐 아니라 프로그램을 읽는다.
- **모델:** 로컬에서 돌린 공개 모델: Qwen3(1.7B–32B), Qwen3.8-27B, Qwen3.6-35B-A3B, Llama 3, gpt-oss-20b / 120b.

## 3. 실제 벤치마크의 주요 결과

**R1. 솔버 코드는 지능이 아니라 사실이 빠져서 실패한다.**
> *예시*(Qwen3-32B, OR-Tools 경로 문제). 전체 매뉴얼을 주면 메서드를 지어낸다: `routing.RegisterUnaryLongLivingCallback(...)` → `AttributeError`. 올바른 호출 `RegisterUnaryTransitCallback`이 담긴 5줄을 주면 증명된 최적해에 도달한다.

Solomon 56개에서는 세 사실이 함께 필요하다. 파일 구조, "OR-Tools는 모든 곳에 정수를 받는다"(모델은 `1e7`을 쓴다), 좁은 시간 창을 위한 시작 전략이다. 이 사실들이 없으면 낮은 노력에서 실행 가능한 계획을 내는 프로그램이 많아야 6%이고, 있으면 gpt-oss-120b가 100%에 이른다(1.5k 토큰). 추론은 이를 대신하지 못한다(문서 없는 경로 문제에서 .03). 숨은 결함이 있는 필요한 헬퍼는 함정이다. 올림 대신 반올림하는 이동 시간 헬퍼는 실행 가능성을 95%에서 69%로 떨어뜨리고(gpt-oss-120b), 경고 주석은 도움이 안 된다(64%).

**R2. 한 번 쓰고, 검증하고, 재사용하라: 검사한 프로그램 하나가 사례마다 새로 쓴 프로그램보다 낫다.**
> *예시*(gpt-oss-120b, 경로 문제). 프로그램 16개를 뽑아 훈련 사례 8개에서 실행 가능한 계획을 내는 하나를 남기고, 새 사례 48개에 그대로 돌린다: 94%가 실행 가능하다(사례마다 새 프로그램을 쓰면 7%). 전체 비용은 28k 토큰이다.

job-shop에서도 통하고(32개 중 32개, 그리고 더 큰 OR-Library 사례 42개 중 42개가 120초 CP-SAT 결과의 4.3% 이내), 경로 프로그램은 고객 200명·400명 사례에서도 실행 가능하다(각각 60개 중 60개). 작동하는 후보가 하나만 있으면 된다. 비용은 대략 후보당 토큰 ÷ 작동하는 후보의 비율이다. 따라서 사례마다 프로그램 하나로 채점하는 벤치마크는 이 모델들의 능력을 과소평가한다.

**R3. 값싼 검사가 실패할 때만 추론에 비용을 써라.** 대회 기하에서는 문제 본문의 예제가 공짜 검사지만 구멍이 있다. 맞는 프로그램은 절대 떨어뜨리지 않지만 틀린 프로그램의 24–37%를 통과시킨다(gpt-oss-120b, 시드 3개; `results/CHECKS.md`). 그래서 성격이 다른 두 번째 검사(작은 입력에서의 완전탐색 프로그램)가 마지막 1점을 되찾는다.

| 정책(gpt-oss-120b, 문제 311개) | 해결 | 문제당 토큰 |
|---|---|---|
| low 노력 | 46% | 3.2k |
| low + 실패한 예제로 한 번 수정 | 53% | 4.6k |
| medium | 57% | 6.8k |
| medium, 예제를 통과 못 할 때만 high | 65% | 20.2k |
| medium, 예제 실패 또는 완전탐색 검사와 불일치할 때 high | 66% | 24.7k |
| 항상 high | 66% | 30.1k |

한 번의 수정이 토큰당 가장 좋은 다음 단계이고, 실패할 때만 노력을 올리면 high 결과의 98%를 토큰 2/3로 얻는다.

**R4. 오류 메시지가 아니라 문제 유형에 따라 처방을 고른다.** Qwen3-32B에서 첫 실패의 오류 신호로 처방을 고르는 것은 가장 좋은 단일 처방보다 낫지 않고(기하 88.9 대 89.8%, 최적화 73.0 대 76.0%), 모델이 스스로 처방을 고르게 하면 더 나쁘다(85.2 / 69.0%). 단순한 기본값이 이긴다. 기하에서는 불필요한 도구를 빼거나(0.4k 토큰에 80.6%) 추론하고(6.1k에 97.2%), 최적화에서는 정확한 스니펫을 준다(0.5k에 70%; Qwen3.6은 전체 매뉴얼 64% 대비 91%). 솔버 라이브러리도 도구 선택이다. 모델은 습관대로 고르고(CP-SAT, 경로 문제엔 routing 라이브러리), 가장 좋은 라이브러리는 모델과 문제마다 다르다(Qwen3-32B 빈 패킹: MIP 24개 중 23개 최적, CP-SAT 1개). 사례마다 모든 라이브러리를 돌려 정답 없이 가장 좋은 실행 가능 해를 고르면 네 모델 모두에서 어떤 단일 라이브러리보다 낫다(예: Qwen3-32B 41.5% → 64.5%, gpt-oss-120b 81.0% → 94.5%), 토큰은 약 4배. 계획이 실행 불가능할 때만 다른 라이브러리로 넘어가면 그 정확도의 96–98%를 토큰 34–84%로 얻는다.

## 4. 생성한 과제에서 본 메커니즘(처방이 왜 통하는가)

**M1. 불필요한 헬퍼가 알고리즘을 바꾼다.**
> *예시*(Qwen3-8B, 볼록 껍질). 불필요한 헬퍼 8개가 있으면 주어진 헬퍼 위에 짓는다: `sorted_points = polar_sort(points, left)` → 8개 사본 모두에서 틀린다.

이런 헬퍼 두 개가 볼록 껍질을 97%에서 8%로 떨어뜨린다. 한 문장짜리 힌트는 0.6k 토큰으로(94%), 추론은 ≈6k로 이를 고친다. 실제 대회 문제에서는 효과가 작다(gpt-oss-20b만 −4점).

**M2. 숨은 조건이 있는 필요한 도구는 함정이다.**
> *예시*(Qwen3-32B, 격자점). 헬퍼가 *부호 있는* 넓이를 반환하고 모델은 `abs()`를 빠뜨린다: `A = polygon_area2(poly) // 2` → 시계 방향 입력이면 음수.

정답이 44개 대신 60개 중 9–15개다. 헬퍼를 고치면 46–49개로 돌아오지만, 경고문으로는 안 된다(17–19개). R1의 반올림 헬퍼는 벤치마크 규모에서의 같은 함정이다.

**M3. 매번 다른 오류는 검사로 잡고, 반복되는 오류에는 추론이 필요하다.**
> *예시*(Qwen3-8B, 다각형 넓이). 프로그램 3개 중 하나가 좌표를 실수로 읽어 10⁹만큼 이동한 사본에서만 틀린다. 각 프로그램을 평행이동·회전·대칭 사본에서 돌려 보면 이를 걸러 낸다.

표본 3개 + 이 검사: 0.9k 토큰에 100%(추론은 5.5k에 91%). 모든 표본이 같은 오류를 공유하면(M1) 검사는 도움이 안 된다.

**M4. 강건성은 작은 모델에 학습시킬 수 있고, 자기 프로그램을 섞으면 다른 과제가 지켜진다.**
> *예시*(Qwen3-8B, 헬퍼 8개가 있는 볼록 껍질). LoRA 전: 1,067 토큰, 틀림. 자기 검증 프로그램으로 LoRA 후: 249 토큰, 정답.

토큰 6k 대신 0.35k에 77 → 98%. 모델 자신의 프로그램을 섞으면 보지 않은 과제가 살아남지만(120개 중 118), 교사 프로그램으로는 그렇지 않다(36). 대회 문제에서는 미세조정이 도움이 되지 않았다.

## 5. 관련 연구의 기준선과 우리 방법(모두 여기서 측정)

| 공개된 기준선 | 우리 과제에서의 측정 |
|---|---|
| CodeT, MBR-exec, 다수결, DeepConf(프로그램 3개 중 1개 고르기) | 깨끗한 프롬프트에서 96.0 / 93.7 / 95.7 / 94.7%(Qwen3-8B); 우리 대칭 검사 99.7% |
| 범위 지시 문장(2609.14157), System 2 Attention | 헬퍼 피해의 2–3%만 되찾음 / 11점 더 나쁨 |
| DRAFT(스스로 쓴 도구 문서) | 11–15%, 고친 헬퍼는 87–92%(들로네) |
| DRoC 방식 검색 | 정확한 스니펫보다 .12–.40 낮음(경로 문제) |
| TroVE 방식 투표 | 헬퍼 피해에 가장 정확(91.2 / 95.0%), ≈2.6k / 1.8k 토큰 |
| WiSE-FT, SDFT, 자기 학습 | 보지 않은 과제 유지: SDFT 85, 자기 학습 104, WiSE-FT 120개 중 119이지만 과제 내 이득이 작음; 자기 replay는 118에 이득 전부 유지 |
| AlphaCode 거르기, Self-Debugging, FrugalGPT 방식 단계적 확대 | R3에서 사용: 예제 검사, 한 번의 수정(+5–7점), 단계적 확대(gpt-oss-20b, 토큰 13% 절약에 +2.7점) |
| Dynamic Cheatsheet 방식 메모리 | 보지 않은 경로 사례의 31–40%(사실 없이 7%) |

| 우리 방법 | 결과 | 판정 |
|---|---|---|
| 한 번 검증, 재사용 | R2 | 효과 있음 |
| 초안 후 리팩터링, 대칭 검사로 결정 | Qwen3-32B 0.8k 토큰에 91.5% | 작은 이득 |

## 6. 관련 연구, 계획, 한계

**관련 연구.** 코드를 오도하는 프롬프트 맥락(2606.04057; 2609.14157; CodeCrash 2504.14119), 계약이 불분명한 도구(DRAFT; ContractEval 2510.12047), 솔버 코드를 위한 문서(DRoC, ICLR 2025; CP-Bench 2506.06052), 정답 없는 선택과 수정(CodeT, MBR-exec, AlphaCode; Self-Debugging; Olausson et al., ICLR 2024), 모든 사례에 프로그램 하나(FunSearch, HeuriGym; 문제군마다 솔버 하나: 2605.14141, 2608.27296). **새로운 점:** 정확한 답이 있는 기하·최적화에서 이 효과들을 비교하고, 한 번에 사실 하나만 바꾸며, 모든 처방에 토큰 비용을 붙인다.

**계획.** 실패 → 처방 지도(`results/FIX_MAP.md`)를 완성한다. 두 프롬프트 변형의 답이 다를 때만 노력을 올리는 무라벨 관문이 유망하다(Qwen3-32B 기하: 시드 3개 모두 99.1%, 항상 추론하는 경우 토큰의 61–79%). 검증된 프로그램을 새 규칙에 맞게 고치는 것은 변경이 국소적이면 모든 모델에 도움이 되고, 새 문제를 스스로 못 쓰는 모델에는 시험한 모든 규칙에서 도움이 되지만, 변경이 솔버 모델의 구조를 바꾸면 강한 모델에는 해가 된다(유연 job-shop, gpt-oss-120b: 80개 중 36개 대 67개 실행 가능) (job-shop + 출시 시각: Qwen3-32B는 '최소한만 고쳐라' 지시로 80개 중 54개 실행 가능, 처음부터 쓰면 4개; gpt-oss-120b는 80개 대 72개이고, 고친 프로그램 하나가 남은 32개 사례를 모두 푼다; CVRP → VRPTW에 코드 조각을 주면 24개 중 18개 최적, 코드 조각만 주면 7개). API 접근이 가능하면 폐쇄형 모델을 더한다.

**한계.** 메커니즘(4절)은 생성한 과제에서 찾았고, 헬퍼 효과는 실제 문제에서 줄어든다. R1의 사실은 손으로 썼으며, 자동 사실 캐기는 그 일부만 되찾는다. 공개 모델만 시험했다.
