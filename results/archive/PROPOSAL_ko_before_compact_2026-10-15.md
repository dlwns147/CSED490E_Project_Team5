# 도구, 사실, 검사: LLM이 작성한 기하·최적화 코드는 언제 실패하며, 어떤 해법을 써야 하는가

*대학원 NLP 수업 프로젝트 제안서: 계산기하(computational geometry)와 조합 최적화(combinatorial optimization)*

> **번역 안내.** 이 파일은 [PROPOSAL.md](PROPOSAL.md)(영문 원본, 2026-10-15 기준)의 한국어 번역본이다. 표·수치·코드·파일 경로는 원본과 동일하며, 내용이 다를 경우 영문 원본이 기준이다.

> **이 파일에 대하여.** 프로젝트의 단일 문서다. 모든 대조군과 수정 사항을 포함한 전체 시간순 기록은 [results/FINDINGS.md](results/FINDINGS.md)에 있으며, 이 파일의 이전 장문 버전은 `results/archive/`에 보관되어 있다.

## 0. 입문: LLM은 기하·최적화 문제를 어떻게 푸는가

**문제.**
- **계산기하:** 좌표로부터 정확한 답을 계산한다. 다각형의 넓이, 점 집합의 볼록 껍질(convex hull) 등이다.
- **조합 최적화:** 매우 많은 선택지 중 가장 좋은 것을 고른다. 가장 짧은 배송 경로, 그래프를 칠하는 가장 적은 색 수 등이다. 답이 유효한지 확인하기는 쉽지만, 그것이 최선임을 증명하기는 어렵다.

**LLM이 이런 문제를 푸는 여섯 가지 방식:**

| 방식 | 작동 방식 | 예시 | 대표 연구 |
|---|---|---|---|
| 1. 직접 답하기 | 모델이 글로 답을 계산해 낸다 | "넓이의 두 배는 436이다." | chain-of-thought; 추론 모델 |
| 2. 추측 개선하기 | 모델이 해를 제안하고, 점수를 보고, 더 나은 해를 제안한다 | "경로 1-3-2-4의 길이는 120이다. 더 짧은 경로를 내라." | OPRO |
| 3. 프로그램 작성 | 모델이 코드를 쓰고, 컴퓨터가 실행한다 | `print(abs(sum(x1*y2 - x2*y1 ...)))` (신발끈 공식으로 넓이) | PAL, AlphaCode |
| 4. 솔버 사용 | 모델이 문제를 솔버 코드로 쓰고, 솔버가 최선의 답을 찾는다 | 간선마다 `m.Add(c[a] != c[b])`, 그다음 `m.Minimize(k)` (그래프 색칠) | OptiMUS, ORLM |
| 5. 휴리스틱 진화 | 규칙의 여러 버전을 시험해 가장 좋은 것을 남긴다 | 다음 물건을 어느 빈에 넣을지 정하는 `priority(item, bins)`를 진화 | FunSearch, EoH |
| 6. 증명기 돕기 | 모델이 단계를 제안하고, 기호 엔진이 기하 정리를 증명한다 | "AB의 중점을 추가하라" 이후 엔진이 증명을 마친다 | AlphaGeometry |

방식 1과 2는 문제가 커지면 무너지고, 6은 계산이 아니라 정리를 증명한다. 실제로 기하는 3으로, 최적화는 3과 4로 풀며, 보통 고리 안에서 쓴다. 프로그램을 여러 개 쓰고, 검사를 통과한 것을 남기고, 실패한 것을 고친다.

**예시: 기하.** 꼭짓점 8개 다각형의 넓이의 두 배를 답이 같은 8개 사본(평행이동, 회전, 대칭 등)으로 묻는다. 직접 답하면 Qwen3-8B는 사본마다 436(정답), 2944, 392, 728을 낸다. 이 모델이 쓴 프로그램(신발끈 공식)은 8개 모두에서 정답이다.

**예시: 최적화.** 4색이 필요한 노드 40개 그래프를 칠한다. 직접 답변: 유효한 것이 없다. 직접 짠 휴리스틱: 40색을 쓰는 경우가 많다. 열 줄짜리 솔버 모델: 솔버를 잘못 쓴 데서 오는 오류(솔버 변수에 `max()` 사용)를 최대 두 번의 수정으로 고친 뒤, 6개 중 5개에서 최적인 4색을 찾는다.

**이 프로젝트**는 방식 3과 4를 연구한다. 이런 프로그램이 언제 실패하는지, 어떤 값싼 처방이 통하는지를 묻는다. 실제 대회 기하 문제 311개에서 문제당 프로그램 하나는 여전히 12–57%만 푼다.

## 1. 문제 정의

LLM은 알고리즘 문제를 일상적으로 프로그램 작성으로 풀지만, 그 프로그램은 겉보기에 맞아 보여도 실패하는 경우가 많다. 흔한 반사적 대응은 프롬프트에 더 많은 것(헬퍼, 문서, 추론 토큰)을 넣는 것이다. **연구 질문:** 어떤 인-컨텍스트 추가물이 LLM이 작성한 CG·CO 프로그램을 개선하거나 악화시키는가, 그 이유는 무엇인가, 그리고 어떤 실패에 어떤 저비용 해법을 어느 정도의 토큰 비용으로 써야 하는가?

1. **도구.** 정확하지만 불필요한 헬퍼가 코드를 바꾸는가? *필요한* 도구도 해를 끼칠 수 있는가?
2. **사실.** 솔버 코드에서 정확한 API 사용법이 전체 매뉴얼, 검색(retrieval), 혹은 더 많은 추론보다 나은가?
3. **해법 선택.** 언제 샘플링해 레이블 없이 검사하고, 언제 추론에 비용을 지불해야 하는가? 강건성을 빠른 모델에 증류할 수 있는가?

### 1.1 왜 직접 답변이 아니라 프로그램인가

| 방식 (추론 모드 끔) | 기하: 8개 버전 모두 정답 | 기하: 동치 입력에 같은 답 | 최적화: 최적해 도달 |
|---|---|---|---|
| 직접 답변 (Qwen3-8B / 32B) | 22% / 23% | 인스턴스의 **0%** | held-out 문제: .06–.19 (Llama-70B .02) |
| 프로그램 작성 후 실행 (Qwen3-8B) | **92–97%** | 과제별 50–100% (점-다각형 포함 판정이 최저) | API 스니펫을 준 솔버 프로그램: .71–.97 |

프로그램은 정확한 계산을 실행에 맡기고(직접 답변의 21%는 산술 도중 토큰이 바닥났다) 모든 입력 크기를 처리한다. 직접 답변은 크기가 커질수록 나빠지지만(배낭 문제 최적 갭: 물건 10개 6% → 80개 48%; TSP: 도시 8개 9% → 20개 139%; ZebraLogic의 "복잡도의 저주" 참고) 약 350토큰의 OR-Tools 프로그램은 크기와 무관하게 같은 비용이 든다. 프로그램은 레이블 없이 검사할 수 있지만(F4), 직접 답변은 일관성조차 없다(꼭짓점이 6개인 볼록 껍질에 대해 8개 동치 버전에서 4, 10, 4, 4, 6, 6, 6, 11). 솔버는 수십 년의 공학을 더하며(예시 B), LLM은 학습에서 풀이 과정보다 훨씬 많은 코드를 본다(프로그램 보조 추론: PAL, Program-of-Thoughts, Logic-LM). 그 대가는 새로운 실패 유형(실행 환경 불일치, 솔버 API 오용, 퇴화 입력, 건전하지 않은 알고리즘)이며, 이 모두가 프롬프트의 영향을 받는다.

## 3. 동기

코드 어시스턴트는 도구 카탈로그와 문서 덤프를 받는다. 그럴듯한 도구가 알고리즘을 조용히 바꾼다면 "모델에게 모든 것을 주라"는 잘못된 기본값이다. 정확한 오라클과 증명된 최적해 덕분에 프롬프트 효과를 측정할 수 있으며, 그 효과는 크다. 헬퍼 하나가 볼록 껍질 정확도를 97%에서 8%로 떨어뜨리고(F1), 5줄짜리 API 스니펫은 차량 경로 문제를 .23에서 .90으로 끌어올린다(F3).

## 4. 실험 설계

### 4.1 설정

**과제**(모두 정확한 참조 정답과 함께 생성):

| 도메인 | 핵심 | 홀드아웃(첫 발견 이후 설계) | 더 어려운 다단계 과제 |
|---|---|---|---|
| 기하 | 볼록 껍질 꼭짓점 수, 다각형 넓이 ×2, 점-다각형 포함, 선분 교차 개수, 최근접 쌍 | 볼록성 판정, 삼각형 내부 점, 볼록 다각형 겹침; 사전 등록(E2): Delaunay 검사, 가장 먼 점 쌍(farthest pair) | 다각형 내부 격자점(Pick), 직사각형 합집합 넓이(스윕 라인), 다각형 클리핑(정확한 유리수 교차 넓이) |
| 최적화 | 0/1 배낭, TSP, 그래프 색칠, makespan 스케줄링 | 빈 패킹, 정점 덮개 | 용량 제약 차량 경로(CVRP), VRPTW |

**채점.** 기하: 인스턴스마다 8개의 동치 버전(평행이동, 회전, 반사, 순열, 스케일, 10^9 오프셋, 퇴화 사례)이 있으며, 8개 모두에서 맞아야만 정답이다. 최적화: 증명된 최적해(DP, Held–Karp, 정확한 CP-SAT)까지 푼 비율이며, 솔버 조건은 OR-Tools와 최대 2회의 수리(repair) 라운드를 쓴다.

**개입.** 헬퍼 도구 상자(필요한 헬퍼 = K0, 여기에 추가 헬퍼 K개, K는 최대 10; "K8" = 추가 8개); 숨은 헬퍼 계약; 문서 변형과 BM25 검색; 힌트; 검증된 샘플링; 추론 모드(thinking); LoRA 증류.

**모델.** Qwen3 1.7B / 8B / 14B / 32B-AWQ; Llama-3.1-8B, Llama-3.3-70B; DeepSeek-R1-Distill-Llama-70B; gpt-oss-20b / 120b(low / medium / high 추론 강도). A100에서 vLLM 0.10.2를, 2026-10-13부터는 RTX PRO 6000 Blackwell GPU에서 vLLM 0.22를 썼으며, 후자는 이전 셀의 개수를 정확히 재현했다(예: VRPTW 27/30, 21/30, 8/30, 18/30, 0/30). 각 비교는 하나의 스택만 쓴다.

**통계와 대조군.** 기하 조건당 300개 프로그램(과제당 60개), 핵심 셀은 2–3 시드, 대응 부트스트랩(paired bootstrap) 95% CI. 헬퍼는 실행 시 미리 정의된다. 참조 해답은 모든 하네스를 통과하며(480/480), 새 모델 계열마다 출력 추출 감사를 한다. "사전 등록": 실행 전에 예측을 적어 둠(`results/PREREG_*.md`).

메커니즘(오프-이디엄 이탈, off-idiom drift; 사전 등록 실험):
- **알고리즘이 바뀐다:** hull 프로그램의 44–75%가 monotone chain에서 제공된 `polar_sort` 위의 실패하는 Graham scan으로 전환한다. 도구 상자는 모델 자신이 쓴 헬퍼 경로 프로그램의 가능도를 180개 인스턴스 100%에서 토큰당 0.40–0.71 nats 높이며, 이 이동은 주로 import와 헬퍼 이름에 몰려 있다.
- **헬퍼 하나로 충분하다**(`results/PREREG_E4.md`): `polar_sort` + `collinear`는 hull을 97%에서 8%(8B), 83%에서 6%(32B)로 떨어뜨린다. 무해하리라 예측한 "암시적이지 않은" 헬퍼도 15–38점을 깎는다. 최적화에서는 불필요한 API 줄이 아무것도 바꾸지 않고, 격자점 과제에서는 추가된 `point_in_polygon`이 도움이 된다(Llama-70B 60개 중 0 → 45).
- **새 과제(E2, 가장 먼 점 쌍; `results/PREREG_E2.md`):** `convex_hull` + `polar_sort`는 Qwen3-32B를 21.7점 떨어뜨린다(CI [−31.7, −11.7]). 알고리즘을 암시하지 않는 헬퍼는 입력 파싱을 통해 46.7점을 깎는다(실패 66건 중 64건이 개수 줄까지 점으로 읽음). 실제 입력을 보여 주면 고쳐진다(120개 중 54 → 119).
- **강건하다(B3, H1, L1):** 도구 범위에 관한 한 문장 지시(2609.14157 방식)는 피해의 2–3%만 회복하고, System 2 Attention은 핵심 과제를 11점 *악화*시킨다. 점 2,000–20,000개 입력에서는 피해가 두 배가 된다(Qwen3-8B / 32B −30 / −35; low 추론 강도의 gpt-oss는 헬퍼 유무와 상관없이 92–98%). 시그니처만 있는 import 가능한 라이브러리로 제공해도 Qwen3-32B는 19.3점을 잃으며, Qwen3-8B가 라이브러리에 없는 함수를 import하지 못하게 하는 한 문장(L2)을 넣어도 마찬가지다(8B −8.8, 32B −20.0).
- 이 피해에 대한 우리 자신의 방법(M1–M5): 4.4절.

**결론이 그냥 "추론 모드를 쓰라"인가? 아니다.** 추론 모드가 효과가 있는 이유는 모델이 코드를 쓰기 전에 알고리즘을 고르기 때문이다. 그 선택을 고정하는 다른 방법도 훨씬 적은 비용으로 똑같이 효과가 있다(8B):

| 같은 피해에 대한 해법 | 정확도 | 프로그램당 출력 토큰 |
|---|---|---|
| 없음(추가 헬퍼 8개, 추론 모드 없음) | 76–78% (최악의 헬퍼 2개를 준 hull: 7%) | ≈0.8–1.1k |
| 전체 추론 모드 | 97% | ≈6k (예시 인스턴스에서 ≈15k) |
| 한 문장 알고리즘 힌트, 추론 모드 없음(hull, 최악의 헬퍼 2개, 3 시드) | 94% | ≈0.6k |
| 증류된 LoRA, 추론 모드 없음(F5) | 98% | ≈0.35k |
| 추가 헬퍼를 아예 제공하지 않음 | 92–97% | ≈0.3k |

추론 모드는 숨은 계약(F2)이나 누락된 API 사실(F3)은 막지 *못한다*. 실용적 메시지는 **도구 설계**다. 필요한 헬퍼만 제공하고, 의도한 알고리즘을 명시하며, 예시 입력을 하나 보여 주라. 추론은 대비책이다.

**F2. 필요한 도구라도 숨은 계약(hidden contract)이 있으면 함정이 된다.**
- lattice 과제에 필요한 헬퍼는 *부호 있는* 면적을 반환한다. 모델은 `abs`를 빠뜨리고(`A = polygon_area2(poly) // 2`), 시계 방향 입력에서 Pick 공식이 실패한다. Qwen3-32B는 60개 중 44개에서 9–15개로 떨어진다. 도구를 고치면 46–49개로 회복되지만 docstring 경고로는 회복되지 않는다(17–19개; "NEGATIVE for clockwise; use abs()" 경고를 주면 60개 중 38개가 경계점을 잘못 세는 brute force로 바꾼다). 추론은 위험을 줄이지만 없애지는 못한다(Qwen3-8B 52 대 60, 부호 있음 대 부호 없음). 헬퍼가 없어도 gpt-oss는 clipping 실패 45건 중 35건에서 반시계 방향 입력을 가정한다.
- **재현(E2, 사전 등록; Delaunay 검사: 외접원이 어떤 점을 엄밀히 내부에 포함하는 삼각형의 개수를 센다).** 필요한 헬퍼 `in_circle`은 삼각형이 반시계 방향이어야 한다고 짧게만 언급한다. Qwen3-8B / 32B는 이 헬퍼로 120개 중 1 / 3개를, 방향과 무관한 버전으로는 109 / 106개를 푼다. 실패의 92% / 97%는 대칭 사본이나 꼭짓점 번호를 바꾼 사본에서만 틀린다. 자세히 풀어 쓴 경고는 격차의 16% / 75%를 회복한다. Llama-3.3-70B와 Qwen3-14B도 걸려들고(헬퍼를 주면 120개 중 8개, 4개), gpt-oss-20b는 그렇지 않다(118 대 117). 추론 모드는 32B에서는 함정을 없애지만(118 대 120) 8B에서는 일부만 줄이며(51 대 118), 헬퍼를 고치는 데 드는 ≈0.4k 토큰과 달리 7.8–8.8k 토큰이 든다. 모델이 직접 쓴 문서(B3)도, 검증된 동작 문장(M2)도 도움이 되지 않는다.

- 5줄짜리 정확한 스니펫이 모든 크기에서, 그리고 held-out 문제에서도 전체 매뉴얼을 이긴다. **근접 오답 문서는 문서가 없는 것만큼 나쁘다.** 전체 시트(용량 제약 없는 TSP 라우팅)를 주면 Qwen3-32B는 존재하지 않는 `RegisterUnaryLongLivingCallback`을 지어내고(CVRP .07), 스니펫의 `RegisterUnaryTransitCallback`은 최적해에 이른다. CVRP 스니펫은 VRPTW에서 0(Llama-70B, Qwen3-32B)과 .07(gpt-oss-20b low)을 준다.
- **정정(2026-10-13): VRPTW의 "누락된 필드"는 우리 프롬프트의 모호한 헤더 때문이었다.** 우리는 헤더를 `n capacity K service horizon`으로 적었고, gpt-oss-120b는 이를 `n capacity K horizon`으로 읽었다(30개 중 0–3개만 `service`를 읽음; 필드를 다시 진술하게 하면 "service horizon"을 하나의 복합 명사로 다룬다). 그 결과 horizon이 10이 되어 솔버가 실행 불가능을 보고했다. 필드를 뺀 입력에서는 49개 중 43개가 최적이고, 헤더를 `n capacity K service_time horizon`으로 쓰면 120b low는 30/30, 30/30, 20b low는 29/30, 29/30이다(F3y). 명확한 명세를 사전 지식이 덮어쓴 것이 아니라 우리 명세의 모호함이었다. 22개 형식 문자열 전체 감사(A1)에서 체계적으로 잘못 읽힌 것은 이 헤더뿐이었다(gpt-oss-120b, gpt-oss-20b, Qwen3-8B 모두 3번 중 3번).
- **실제 입력을 보여 주면 모호함이 해소되고 토큰도 줄어든다.** 스니펫과 함께 주면 120b low는 0 → .97–1.00(인스턴스당 4.8k → 1.7k 토큰), 120b medium은 .07 → 1.00(10.7k → 3.7k), 20b low는 .07–.17 → .80–.97이 되고, 필드를 건너뛰는 프로그램은 30개 중 18–29개에서 0–3개로 준다. 필드를 다시 진술하게 하는 것은 도움이 되지 않는다(gpt-oss 30개 중 0–2개).
- **추론은 사실을 대체할 수 없다.** 문서 없이 추론만 켜면 14B / 32B / R1-Distill-70B가 프로그램당 11–19k 토큰을 쓰고도 CVRP에서 .33 / .03 / .00에 그친다(스니펫을 주면 .97 / .97 / .90). **검색은 정확할 때만 효과가 있다.** BM25 top-1은 손으로 쓴 스니펫과 맞먹고(32B .965 대 .956), top-3은 근접 오답을 끌어온다(CVRP .78 → .55). DRoC 방식 검색(B4)은 단순 top-3보다 낫지만(+.12~+.15) 스니펫보다는 못하다(−.12~−.40).
- *채점 점검:* 출발 도시로 돌아오는 TSP 실패 293개(그중 281개는 최적)를 인정하면 Qwen3-32B(문서 없음)는 .70 → .83, Llama-70B(문서 없음 / 전체 시트 / 스니펫)는 .33 / .55 / .87 → .54 / .73 / .99가 되며, 순서는 유지된다.

- **예산:** 기하에서는 약 1k 추론 토큰으로 정확도 대부분을 회복한다(lattice 8B 60개 중 12 → 58). 최적화는 훨씬 많이 필요하다(TSP는 2k에서도 0). 낮은 effort의 gpt-oss-20b는 ≈0.4–0.9k 토큰으로 ≈99%이며, 높은 effort에서는 프로그램의 27%가 24k 안에 끝나지 않는다.
- **공개된 선택 기법(B1):** 같은 후보 3개에서(Qwen3-8B; 깨끗한 프롬프트 / 추가 헬퍼 8개 / 어려운 과제) 우리 변성 검사는 올바른 프로그램을 99.7 / 83.3 / 33.3% 고르고, CodeT는 96.0 / 82.7 / 26.7, 주어진 입력에서의 다수결·MBR-exec·DeepConf는 그보다 낮다. 새 무작위 입력은 주어진 인스턴스의 대칭 사본이 드러내는 부호·방향 오류를 놓친다(누출 아님: 새 인스턴스 5개에서도 같다).
- **확신도는 검사를 대체할 수 없다(C1):** 3개 중 확신도가 가장 높은 것을 고르면 +1.0 [−1.1, +3.1], 검사는 +7.0이다. 로그 확률은 헬퍼가 있을 때 틀린 Graham scan을 선호한다(AUROC 0.43; 깨끗한 프롬프트 0.68, 어려운 과제 0.40). Qwen3-32B에서도 재현된다(검사가 6.7–22.5점 앞섬).
- **검사 게이트 파이프라인은 체계적 오류에서 진다(E3, `results/PREREG_E3.md`):** 프로그램 하나, 검사에 실패하면 샘플 3개 + 검사, 그다음 1,024토큰 추론 예산. 필요한 헬퍼만 줄 때(Qwen3-8B): 인스턴스당 365 토큰으로 98.0%(전체 추론 모드 3,792 토큰에서 100%). 추가 헬퍼 8개 / 어려운 과제에서는 84.7% / 53.3%에 그쳐 **고정 1,024토큰 예산보다 낮다**(거의 같은 1.6k / 1.7k 토큰에서 93.0% / 80.8%). 검사는 모든 사본에서 같은 방식으로 틀리는 프로그램을 통과시킨다. 같은 모델이 쓴 무차별 대입 참조(E3b)는 이 중 86–90%를 잡지만 예산만큼 비용이 들고 가장 어려운 과제에서 틀린다(격자점 60개 중 1개).

> **예시 F4a: 실수** (Qwen3-8B, 다각형 면적, 깨끗한 프롬프트): 샘플 3개 중 하나가 좌표를 `float()`로 파싱해(1e18 근처의 곱에서 정밀도 손실) 10^9만큼 평행이동한 사본에서만 틀린다. *주어진* 인스턴스의 변환 사본에서 샘플들이 불일치하므로 검사는 정수 프로그램을 남긴다(3 × ≈0.3k 토큰). **F4b: 체계적 오류** (F1 인스턴스, 추가 헬퍼 8개): 샘플 3개 모두 `polar_sort` 경로를 택해 고를 수 있는 올바른 프로그램이 없다. **F4c: 처방의 합성** (낮은 effort의 gpt-oss-20b, 다각형 clipping): `cross(cp1, cp2, e) >= 0`은 clipping 다각형이 반시계 방향이라고 가정하므로 대칭 사본과 순서 뒤집은 사본에서 0을 출력한다. 샘플 하나는 60개 중 14개, 검사는 28개, "orient both polygons counter-clockwise first" 힌트는 44개, 힌트 + 검사한 샘플 3개는 **59**개를 푼다(총 ≈2.8k 토큰).

**F5. 강건성은 과제별로 빠른 모델에 증류할 수 있으며, 학생 모델 자신의 프로그램을 replay하면 다른 과제가 보호된다.** 사전 등록 실험.
- 같은 모델이 추론을 *켜고* 작성한 검증된 프로그램 600개(추가 헬퍼 0/4/8개)로 Qwen3-8B에 LoRA를 학습하면, 추가 헬퍼 8개 조건에서 77.0 → **98.0**(+21.0 [+17.8, +24.3], 2 시드)이 되며 ≈6k 대신 ≈350 토큰을 쓴다(예시 F1: 249 토큰의 monotone chain 대 기본 모델의 1,067 토큰짜리 틀린 `polar_sort` hull). 깨끗한 프롬프트로만 학습하면 이득이 없다. **부수 피해:** 보지 못한 과제는 약간 나빠지고(58.6 → 52.2), 보지 못한 취약한 과제는 깨끗한 프롬프트에서조차 붕괴할 수 있다(hull 97 → 28–34, 대부분 Graham scan 변형).
- **학생 자신의 프로그램을 replay하면 피해가 사라진다(E4, `results/PREREG_E4_REPLAY.md`):** hull을 제외하고 학습한 LoRA, 깨끗한 프롬프트의 hull: 기본 모델 109/120, replay 없음 48, **+ 다른 과제 5개에서 학생 자신이 추론 없이 쓴 검증된 프로그램 270개: 118**, + 같은 270개 프롬프트에 대한 추론 교사 모델의 프로그램: 36(자기 − 교사 +68.3 [+60.0, +76.7]). 과제 내 강건성은 유지된다(240/240). hull 프로그램 120/120에서 monotone chain을 쓴다(replay 없음 59, 교사 replay 49). 새 Delaunay 과제에서는 두 replay 조건 모두 여전히 떨어진다(60개 중 59 → 47 / 45).
- **기존 처방과의 비교(B2):** WiSE-FT는 hull과 과제 내 이득을 맞바꾸고, SDFT는 피해를 절반으로 줄이며(85), 자기 학습만으로는 104 / 235다. 둘 다 지키는 것은 자기 replay뿐이다(118 / 240). convex를 남겨 둔 경우(E4b: 120개 중 81 → 80; 교사 replay 42)와 두 번째 학습 시드(R1: 자기 대 교사 replay, hull 118 대 28, convex 85 대 34)에서도 재현된다.

**요약:** V1 재사용은 후보 하나가 작동하고 믿을 만한 선택 기준이 있으면 효과가 있으며(따라서 사례별 생성은 이 모델들의 능력을 과소평가한다), N2 수정, N3 단계적 상향, M5-V2(작음, 32B만), 자기 replay(F5)도 효과가 있다. M1–M3, N1, N5, N6, V2/V3, 대회 문제 증류는 음성, 사실 캐기는 부분적 음성이며, V1A는 더 강한 모델에서만 작동한다.

## 5. 한계

1. **합성 과제.** 주요 효과는 생성한 과제에서 찾았다. 표준 벤치마크(4.4절)에서 F3와 F4는 성립하고, F1은 한 모델의 작은 효과로 줄어들며, F2는 직접 다시 시험하지 않았다(자연스러운 사례 하나: 우리가 준 읽기 함수가 실수를 반환해 OR-Tools의 정수 계약을 깼다).
2. **부분적으로 사후적인 메커니즘.** 관용구 이탈(off-idiom drift)은 데이터를 본 뒤에 세운 설명이다. 사전 등록 검증이 그 핵심을 확인했지만 유사도 기반 예측은 반박했다.
3. **Oracle 처방.** 스니펫과 힌트는 손으로 작성했다. 검색은 정확한 페이지를 가져올 때만 이에 필적하며, 레이블 없는 검사는 변환에 불변인 오류를 놓친다(E3).
4. **범위.** 공개 가중치 모델만 다뤘다(세 계열; E5는 실행하지 않음). 일부 부차적 셀은 단일 seed이다.
