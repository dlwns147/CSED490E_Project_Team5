## 0. 배경: LLM은 기하·최적화 문제를 어떻게 푸는가

**문제.**
- **계산기하:** 좌표로부터 정확한 답을 계산한다. 다각형의 넓이, 점 집합의 볼록 껍질(convex hull) 등이다.
- **조합 최적화:** 매우 많은 선택지 중 가장 좋은 것을 고른다. 가장 짧은 배송 경로 등이다. 답이 유효한지 확인하기는 쉽지만, 그것이 최선임을 증명하기는 어렵다.

**LLM이 이런 문제를 푸는 여섯 가지 방식:**

| 방식 | 작동 방식 | 예시 | 대표 연구 |
|---|---|---|---|
| 1. 직접 답하기 | 모델이 글로 답을 계산해 낸다 | "넓이의 두 배는 436이다." | chain-of-thought; 추론 모델 |
| 2. 추측 개선하기 | 모델이 해를 제안하고, 점수를 보고, 더 나은 해를 제안한다 | "경로 1-3-2-4의 길이는 120이다. 더 짧은 경로를 내라." | OPRO |
| 3. 프로그램 작성 | 모델이 코드를 쓰고, 컴퓨터가 실행한다 | `print(abs(sum(x1*y2 - x2*y1 ...)))` (신발끈 공식으로 넓이) | PAL, AlphaCode |
| 4. 솔버 사용 | 모델이 문제를 솔버 코드로 쓰고, 솔버가 최선의 답을 찾는다 | 간선마다 `m.Add(c[a] != c[b])`, 그다음 `m.Minimize(k)` (그래프 색칠) | OptiMUS, ORLM |
| 5. 휴리스틱 진화 | 규칙의 여러 버전을 시험해 가장 좋은 것을 남긴다 | 다음 물건을 어느 빈에 넣을지 정하는 `priority(item, bins)`를 진화 | FunSearch, EoH |
| 6. 증명기 돕기 | 모델이 단계를 제안하고, 기호 엔진이 기하 정리를 증명한다 | "AB의 중점을 추가하라" 이후 엔진이 증명을 마친다 | AlphaGeometry |

방식 1과 2는 문제가 커지면 무너지고, 6은 계산이 아니라 정리를 증명한다. 실제로 기하는 3으로, 최적화는 3과 4로 풀며, 보통 고리 안에서 쓴다. 프로그램을 여러 개 쓰고, 검사를 통과한 것을 남기고, 실패한 것을 고친다.

**왜 프로그램인가.** 꼭짓점 8개 다각형의 넓이의 두 배를 동치 사본 8개(평행이동, 회전, 대칭 등)로 물으면, 직접 답하는 Qwen3-8B는 사본마다 436(정답), 2944, 392, 728이라고 답한다. 같은 모델이 쓴 프로그램은 8개 모두에서 정답이다.
```python
s = sum(x1 * y2 - x2 * y1 for (x1, y1), (x2, y2) in zip(pts, pts[1:] + pts[:1]))
print(abs(s))   # 정수 연산이라 정확함
```
마찬가지로 노드 40개 그래프 색칠에서 직접 답변은 모두 유효하지 않지만, 열 줄짜리 솔버 모델은 그래프 6개 중 5개에서 최적인 4색을 찾는다.

## 1. 질문

LLM이 쓴 프로그램은 겉보기에 맞아 보여도 자주 틀린다. 흔한 대응은 프롬프트에 더 많은 것을 넣는 것이다. 헬퍼 함수, 문서, 더 많은 추론 말이다. **우리는 프롬프트에 무엇을 넣어야 하는지, 그리고 어떤 실패에 어떤 값싼 처방이 통하는지를 토큰 비용과 함께 묻는다.**

1. **도구:** 정확하지만 불필요한 헬퍼 함수가 해가 될 수 있는가?
2. **사실:** 솔버 코드에 필요한 것은 전체 매뉴얼인가, 정확한 사용 예 하나인가?
3. **처방:** 언제 프로그램 여러 개를 뽑아 검사하고, 언제 더 많은 추론에 비용을 써야 하는가?

## 2. 시험 방법

- **정확한 답이 있는 과제:** 우리가 생성한 기하 과제 9개(볼록 껍질, 넓이, 교차, 들로네 등)와 최적화 문제 8개(배낭, TSP, 차량 경로 등), 그리고 표준 벤치마크 세 가지: Codeforces 기하 문제 311개, Solomon 경로 문제 56개(고객 100명), job-shop 스케줄링 40개.
- **엄격한 채점:** 기하 프로그램은 입력마다 동치 사본 8개(평행이동, 회전, 대칭 등)에서 모두 맞아야 한다. 최적화 프로그램은 최적해에 도달하거나, 최고 기록에 가까운 실행 가능한 계획을 내야 한다.
- **한 번에 하나만 바꾸기:** 헬퍼, 문서, 예시 입력 하나, 샘플링, 추론, 수정, 미세조정 중 하나를 더하고, 그것이 없는 같은 프롬프트와 비교한다.
- **모델:** 로컬에서 돌린 공개 모델: Qwen3(1.7B–32B), Qwen3.8-27B, Qwen3.6-35B-A3B, Llama 3, gpt-oss-20b / 120b.
- **신중함:** 실행 전마다 예측을 기록하고, 시드 2–3개를 쓰고, 정확도는 항상 토큰 비용과 함께 보고하며, 점수뿐 아니라 프로그램 자체를 읽는다.

## 3. 지금까지의 발견

**F1. 불필요한 헬퍼가 알고리즘을 바꾼다.** 정확하지만 불필요한 기하 헬퍼 8개를 프롬프트에 넣으면, 모델은 그 위에 프로그램을 짓는다.
> *예시*(Qwen3-8B, 볼록 껍질). 헬퍼가 없으면 표준 monotone chain을 쓰고 정답이다. 헬퍼가 있으면 주어진 `polar_sort` 위에 짓고 8개 사본 모두에서 틀린다.
> ```python
> sorted_points = polar_sort(points, left)   # 주어진 헬퍼가 알고리즘을 정한다
> ```

이런 헬퍼 두 개가 볼록 껍질 정답률을 97%에서 8%로 떨어뜨린다. 추론은 프로그램당 ≈6k 토큰으로 이를 고치고, 한 문장짜리 힌트("monotone chain을 써라")는 0.6k 토큰으로 고친다(94%). 실제 대회 문제에서는 피해가 작다(gpt-oss-20b −4점, 다른 모델은 없음).

**F2. 숨은 조건이 있는 필요한 도구는 함정이다.**
> *예시*(Qwen3-32B, 다각형 안의 격자점 세기). 주어진 헬퍼는 *부호 있는* 넓이를 반환하며, 시계 방향 다각형이면 음수다. 모델은 `abs()`를 빠뜨린다.
> ```python
> A = polygon_area2(poly) // 2        # 시계 방향 입력이면 음수
> I = A - boundary_points // 2 + 1    # Pick 공식이 이제 틀린다
> ```

Qwen3-32B는 60개 중 44개에서 9–15개로 떨어진다. 헬퍼를 고치면 46–49개로 돌아오지만, 주석의 경고문으로는 안 된다(17–19개). 반시계 방향 삼각형이 필요한 들로네 헬퍼에서도 같은 함정이 나타난다(그 헬퍼로 120개 중 1–3개, 방향과 무관한 버전으로 106–109개). Solomon 벤치마크에서도 성립한다. 이동 시간을 올림 대신 반올림하는 헬퍼를 주면 gpt-oss-120b와 Qwen3.8의 실행 가능 비율이 95% / 94%에서 69% / 60%로 떨어지고, 실패는 거의 모두 시간 창 위반이며, 문제를 밝힌 주석은 도움이 안 된다(64% / 65%).

**F3. 솔버 코드에는 정확한 API 사실이 필요하다.**
> *예시*(Qwen3-32B, OR-Tools로 차량 경로). 전체 매뉴얼을 주면 존재하지 않는 메서드를 지어낸다.
> ```python
> routing.RegisterUnaryLongLivingCallback(demand_callback)   # AttributeError
> ```
> 올바른 호출 `routing.RegisterUnaryTransitCallback(demand_callback)`이 담긴 5줄 스니펫을 주면 증명된 최적해에 도달한다.

경로 문제를 최적으로 푼 비율: 문서 없음 .23, 전체 매뉴얼 .07, 정확한 스니펫 .77–.90, 문서 없이 추론 .03. Solomon 56개에서는 세 사실이 함께 필요하다. 파일 구조, "OR-Tools는 모든 곳에 정수를 받는다"(모델은 `1e7`을 쓴다), 그리고 좁은 시간 창을 위한 시작 전략이다. 이 사실들이 없으면 낮은 추론 노력에서 실행 가능한 계획을 내는 프로그램이 많아야 6%이고, 있으면 gpt-oss-120b가 100%에 이른다.

**F4. 오류의 유형에 따라 처방을 고른다.**
> *예시*(Qwen3-8B, 다각형 넓이). 뽑은 프로그램 3개 중 하나가 좌표를 실수로 읽고(`x = float(data[idx])`) 10⁹만큼 이동한 사본에서만 틀린다. 우리 검사는 각 프로그램을 입력의 평행이동·회전·대칭 사본에서 실행해 답이 일관된 것을 남기므로, 실수로 읽은 프로그램을 걸러 낸다.

표본마다 오류가 다르면, 표본 3개 + 이 검사가 0.9k 토큰에 100%에 이른다(추론: 5.5k에 91%). 모든 표본이 같은 실수를 하면(F1처럼) 검사는 도움이 안 되고 추론이 낫다. 대회 문제 311개에서는 실패한 예제를 보여 주고 한 번 고치는 것이 토큰당 가장 좋은 다음 단계다(gpt-oss-120b 4.6k 토큰에 46 → 53%). 추론 노력을 늘리면 더 좋아지지만 비용도 커진다(low / medium / high 46 / 57 / 66%; high는 문제당 30k 토큰, 시드 3개 평균 66.2%; 2300 이상 문제에서는 medium 35% 대 49%).

**F5. 강건성은 작은 모델에 학습시킬 수 있고, 자기 프로그램을 섞으면 다른 과제가 지켜진다.**
> *예시*(Qwen3-8B, 헬퍼 8개가 있는 볼록 껍질). 미세조정 전: 1,067 토큰, 헬퍼를 전부 복사하고 틀린다. 자기 검증 프로그램으로 LoRA 미세조정한 뒤: 249 토큰, monotone chain, 정답.

헬퍼가 있을 때 정확도가 77%에서 98%로 오르고, 토큰은 6k 대신 0.35k다. 미세조정만 하면 보지 않은 과제가 망가진다(볼록 껍질 120개 중 109 → 48). 다른 과제에서 모델 자신이 쓴 프로그램 270개를 섞으면 유지되지만(118), 같은 수의 교사 프로그램을 섞으면 그렇지 않다(36). 실제 대회 문제에서는 미세조정이 도움이 되지 않았다.

## 4. 관련 연구의 기준선과 우리 방법(모두 우리 과제에서 측정)

**여기서 다시 돌린 공개된 방법:**

| 기준선(출처) | 측정한 것 | 결과 |
|---|---|---|
| CodeT, MBR-exec, 다수결, DeepConf | 프로그램 3개 중 맞는 것 고르기(Qwen3-8B; 깨끗한 프롬프트 / 헬퍼 8개 / 어려운 과제) | CodeT 96.0 / 82.7 / 26.7%, MBR-exec 93.7 / 80.3 / 25.0%, 다수결 95.7 / 81.3 / 21.7%, DeepConf 94.7 / 79.3 / 13.3%; 우리 대칭 검사 99.7 / 83.3 / 33.3% |

| Self-Debugging(한 번의 수정) | 실패한 대회 프로그램을 한 번 고치기 | 토큰당 가장 좋은 다음 단계: +0.8–1.4k 토큰에 +5–7점 |
| FrugalGPT 방식 단계적 확대 | 처음엔 낮은 노력, 예제를 통과 못 할 때만 더 큰 노력 | gpt-oss-20b가 토큰 13%를 덜 쓰고 +2.7점 |
| Dynamic Cheatsheet 방식 메모리 | 모델이 제안한 사실을 모두 유지(경로 문제) | 보지 않은 사례의 31–40% 실행 가능(사실 없이 7%) |

**우리 방법**(각각 실행 전에 선행 연구 확인):

| 방법 | 아이디어 | 결과 | 판정 |
|---|---|---|---|
| 한 번 검증, 재사용 | 훈련 사례 8개에서 작동하는 프로그램 하나를 골라 어디서나 재사용 | 경로 문제: gpt-oss-120b가 보지 않은 48개 중 94%에서 실행 가능, 전체 28k 토큰(사례마다 새 프로그램: 7%); 고객 200명·400명 사례에서도 실행 가능; job-shop: 보지 않은 32개 중 32개, 더 큰 OR-Library 사례 42개 중 42개(120초 CP-SAT 대비 4.3% 이내) | 효과 있음 |
| 초안 후 리팩터링 | 헬퍼 없이 쓰고 나서 헬퍼를 더함; 검사를 통과한 버전을 남김 | Qwen3-32B 0.8k 토큰에 91.5%(1k 추론 예산보다 높고 TroVE 투표보다 낮음) | 작은 이득 |
| 검증된 사실 캐기 | 모델이 자기 오류에서 사실을 쓰고, 재실행으로 확인된 것만 남김 | 보지 않은 경로 사례의 21–40%, 실행마다 불안정; 모든 사실을 유지하는 것보다 낫지 않음 | 부분적 |

## 5. 관련 연구

## 6. 계획과 한계

**계획.** (1) 완료: 높은 추론 노력 결과는 시드 3개에서도 유지된다(66.2%; 311개 중 206 / 204 / 208). (2) 완료: F2는 Solomon 경로 문제에서도 성립한다(위). (3) 실패 유형 → 처방 지도(토큰 비용 포함): 초안 `results/FIX_MAP.md`. (4) API 접근이 가능하면 폐쇄형 모델을 더한다.

**한계.** 주요 효과는 생성한 과제에서 찾았다. 실제 벤치마크에서 F3와 F4는 성립하고 F1은 줄어든다. 처방(스니펫, 힌트)은 손으로 썼고, 자동 버전은 이를 일부만 되찾는다. 공개 모델만 시험했다.
