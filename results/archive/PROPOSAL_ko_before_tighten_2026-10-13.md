# 도구, 사실, 검사: LLM이 작성한 기하·최적화 코드는 언제 실패하며, 어떤 해법을 써야 하는가

*대학원 NLP 수업 프로젝트 제안서: 계산기하(computational geometry)와 조합 최적화(combinatorial optimization)*

## 1. 문제 정의

LLM은 알고리즘 문제를 프로그램 작성으로 풀도록 일상적으로 요청받는다. 볼록 껍질(convex hull), 점-다각형 포함 판정, TSP나 차량 경로 문제를 위한 솔버 모델 등이 그 예다. 이런 프로그램은 겉보기에 맞아 보여도 실패하는 경우가 많으며, 흔한 반사적 대응은 프롬프트에 더 많은 것을 넣는 것이다. 더 많은 헬퍼 함수, 더 많은 문서, 더 많은 추론 토큰 말이다.

**연구 질문.** 어떤 인-컨텍스트(in-context) 추가물이 계산기하(CG)와 조합 최적화(CO)용 LLM 작성 프로그램을 개선하거나 악화시키는가, 그 이유는 무엇인가, 그리고 어떤 실패에 어떤 저비용 해법을 어느 정도의 토큰 비용으로 써야 하는가?

1. **도구.** 정확하지만 불필요한 헬퍼 함수가 생성 코드를 바꾸는가? 어떤 메커니즘을 통해서인가? *필요한* 도구도 해를 끼칠 수 있는가?
2. **사실.** 솔버 코드에서 정확한 API 사용법을 명시하는 것이 전체 매뉴얼, 검색(retrieval), 혹은 더 많은 추론보다 나은가?
3. **해법 선택.** 언제 여러 프로그램을 샘플링해 레이블 없이 검사해야 하고, 언제 추론에 비용을 지불해야 하는가? 추론 모델의 강건성을 빠른 모델에 증류(distillation)할 수 있는가?

### 1.1 LLM은 왜 알고리즘 문제를 프로그램으로 푸는가

LLM은 답을 직접 말할 수도 있다("볼록 껍질의 꼭짓점은 7개다", "도시를 이 순서로 방문한다"). 그러나 파일럿에서 직접 답변은 구조적인 이유로 크게 실패했다.

| 방식 (추론 모드 끔) | 기하: 8개 버전 모두 정답 | 기하: 동치 입력에 같은 답 | 최적화: 최적해 도달 |
|---|---|---|---|
| 직접 답변 (Qwen3-8B / 32B) | 22% / 23% | 인스턴스의 **0%** | held-out 문제: .06–.19 (Llama-70B .02) |
| 프로그램 작성 후 실행 (Qwen3-8B) | **92–97%** | 과제별 50–100% (점-다각형 포함 판정이 최저) | API 스니펫을 준 솔버 프로그램: .71–.97 |

1. **정확한 계산을 실행에 맡긴다.** 다음 토큰 예측기는 계산기가 아니다. 10^9 규모 좌표의 외적이나 물건 80개의 가치 합은 텍스트로 계산하다 틀리기 쉽고, 직접 답변의 21%는 산술 도중 토큰이 바닥났다. 실행되는 코드는 이를 정확히 계산한다.

   > *예시* (Qwen3-8B, 넓이의 두 배가 436인 꼭짓점 8개 다각형). 직접 답변: 원본에서는 436(정답)이지만 평행이동한 사본에서 2944, 회전 사본에서 392, 대칭 사본에서 728을 냈고, 10^9만큼 이동한 사본에서는 산술 도중 2,048토큰 한도에 걸렸다. 실행된 신발끈 공식 프로그램은 8개 버전 모두에서 정답을 출력했다. 최근접 점 쌍은 더 심하다. 직접 답변 160개 중 79개가 점 쌍 거리를 나열하다 토큰이 바닥났다.

2. **프로그램 하나가 모든 입력 크기를 처리한다.** 직접 답변은 크기가 커질수록 나빠진다(배낭 문제 최적 갭: 물건 10개 6% → 80개 48%; TSP: 도시 8개 9% → 20개 139%, 40개에서는 실행 불가능한 해). ZebraLogic에서 관찰된 "복잡도의 저주(curse of complexity)"와 같은 현상이다. 올바른 알고리즘은 입력 크기와 무관하게 같은 비용으로 작성된다.

   > *예시* (Qwen3-8B, 0/1 배낭 문제). 물건 10개에서는 직접 답변이 최적이다(162). 물건 80개에서는 2,697이 가능한데 1,997어치를 고르고(26% 부족), 물건 20개짜리 한 인스턴스에서는 최적값이 669인데 730이라고 답한다. 즉 고른 물건이 용량을 넘는다. 같은 모델이 작성한 약 350토큰의 OR-Tools 프로그램은 크기와 무관하게 길이가 같고 n = 80에서도 2,697에 도달한다.

3. **프로그램은 정답 레이블 없이 검사할 수 있다.** 코드는 입력을 변환한 사본에서 실행해 보거나(기하), 실행 가능성과 목적 함수 값을 확인할 수 있다(최적화). 직접 답변은 일관성조차 없다. 7개의 동치 버전에서 같은 답을 낸 인스턴스가 하나도 없었다. 이 검사 가능성 덕분에 검증된 샘플링(F4)이 가능하다.

   > *예시* (볼록 껍질 꼭짓점이 6개인 점 10개 집합). 8개 동치 사본에 대한 Qwen3-8B의 직접 답변: 4, 10, 4, 4, 6, 6, 6, 11 (Qwen3-32B: 9, 8, 9, 6, 6, 7, 6, 7). 레이블 없이는 어느 것이 맞는지 알 수 없다. 8B가 작성한 프로그램은 8개 모두에서 6을 출력했다. 만약 결과가 서로 달랐다면 그 불일치만으로 버그를 잡아낼 수 있다.

4. **솔버는 수십 년의 공학을 재사용한다.** NP-난해 문제에서 모델은 문제를 *정식화*하기만 하면 되고, 탐색은 CP-SAT나 라우팅 라이브러리가 맡는다. 대신 휴리스틱을 직접 작성한 프로그램은 대개 실행 가능한 해를 내지만 작은 크기를 넘어서면 교과서적 탐욕 알고리즘을 거의 이기지 못한다(노드 40개 그래프 색칠: 최적보다 467% 많음).

   > *예시* (Qwen3-8B, 4색이 필요한 노드 40개 그래프 6개). 직접 답한 색칠: 6개 모두 유효한 색칠이 아님. 직접 작성한 휴리스틱: 6개 중 3개에서 노드마다 다른 색, 즉 40색. CP-SAT 모델(최대 2회 수정 후): 6개 중 5개에서 최적인 4색.

5. **LLM은 풀이 과정보다 훨씬 많은 코드로 학습되었고**, 프로그램 보조 추론(PAL, Program-of-Thoughts, Logic-LM)은 언어 이해와 정확한 실행을 결합하는 확립된 방법이다.

그 대가로 새로운 실패 유형이 생기며, 이것이 이 프로젝트의 연구 대상이다. 프로그램은 실행 환경과 맞아야 하고, 솔버 API를 올바르게 써야 하며, 퇴화 입력을 처리하고, 건전한 알고리즘을 골라야 한다. 이 모두가 프롬프트에 무엇을 넣느냐에 영향을 받는다.

## 2. 배경 (관련 연구)

2026-10-13에 발견별로 확인했다. 판정과 링크를 담은 전체 표는 `results/RELATED_WORK.md`에 있다.

- **코드를 조향하거나 오도하는 컨텍스트.** 프롬프트의 부수적 단서가 모델이 작성하는 알고리즘 계열을 바꾸고(2606.04057), 필요 없는 도구가 제공되기만 해도 호출되지 않은 채 해를 끼치며(2609.14157), 그럴듯한 에이전트 스킬은 과신되고(2608.11888), 유사하거나 버그가 있거나 오도하는 코드 컨텍스트는 코드 정확도를 떨어뜨린다(2503.20589; 2306.03438; CodeCrash 2504.14119). 수학의 무관한 컨텍스트(GSM-IC)와 에이전트의 도구 과부하(RAG-MCP, ToolRet)는 그 이전 형태다. *본 연구:* 모델이 복사해 쓰는 정확하지만 불필요한 헬퍼 코드가 (스타일만이 아니라) 정확도를 무너뜨리며, 경로 전환의 토큰 수준 증거, 용량-반응 관계, 추론 모델의 면역, 그리고 입력 파싱을 통한 두 번째 경로를 보인다.
- **명세가 부족한 도구와 계약.** 도구 설명은 자주 불완전하고, 더 자세한 설명은 오용의 일부만 바로잡으며(2602.14878; DRAFT 2410.08197), 모델은 명시된 계약을 거의 지키지 않는다(ContractEval 2510.12047). *본 연구:* 같은 헬퍼를 방향 전제조건이 있는 경우와 없는 경우로 짝지어 비교하며, 필요한 헬퍼가 헬퍼가 없을 때보다 나쁘다는 것을 4개 모델, 2개 계열에서 보인다.
- **솔버 코드를 위한 문서.** 분해된 문서 검색을 쓰는 OR-Tools 경로 코드(DRoC, ICLR 2025), CPMpy에는 도움이 되지만 OR-Tools에는 그렇지 않은 API 문서(CP-Bench 2506.06052), 간결한 API 명세와 선택적 검색(Jain et al. 2024), 해가 되는 아깝게 빗나간 문서(2401.14887). *본 연구:* 같은 비용에서 정확한 스니펫이 전체 매뉴얼과 추론을 모두 이기며, 아깝게 빗나간 스니펫은 문서가 없는 것과 같다.
- **명시된 명세보다 사전 지식(prior)을 따르는 현상.** 추론 모델은 명시된 조건보다 익숙한 패턴으로 돌아가고(2505.17225; 2507.14417), 재정의된 내장 함수는 규모가 클수록 더 틀린다(2305.15507). *본 연구(정정):* VRPTW 사례는 이렇게 보였지만 실제로는 우리 형식 문자열의 모호한 필드 이름 때문이었다(F3). 본 연구에 남는 것은 진단 방법(반사실적 재실행, 모델에게 형식을 다시 진술하게 하기)과, 기하에서 무관한 헬퍼가 일으키는 입력 형식 실패다.
- **선택, 확신도, 연산 배분.** 새 입력에서의 일치에 기반한 선택(MBR-exec, CodeT, S*, incoherence 2507.00057), 프롬프트 쪽 메타모픽 테스트(2406.06864), 최적화 모델을 위한 유효한 인스턴스 변형(2607.16646); 코드에서 토큰 확신도는 보정이 나쁘고(2402.02047; 2610.11300) 반복적인 프로그램을 선호하며(Coder-Reviewer), 초안 일치에 따라 추론으로 넘기는 라우팅(DART 2606.23181)과 무차별 대입 오라클(ALGO; ExeCRE 2608.04439)이 있다. *본 연구:* 주어진 인스턴스의 변환 사본에서 한 프로그램의 일관성으로 선택하고, 오도하는 헬퍼가 확신도를 뒤집으며, 같은 토큰에서 검사 게이트 라우팅이 작은 고정 추론 예산에 진다는 것을 보인다.
- **망각과 자기 replay.** 모델 자신의 출력으로 학습하면 덜 잊는다(2510.18874; 2601.19897; 2501.14315; SDFT; RL's Razor). *본 연구:* 같은 프롬프트에서 학생 자신의 프로그램과 같은 가중치의 교사 프로그램을 대비하고, 이웃한 미학습 코드 과제에서 관용구 표류를 프로그램에서 직접 보인다.
- **LLM 코드의 실패 분류**(2406.08731; 2407.06153; 2403.08937). *본 연구:* 기하와 최적화, 반사실적 재실행을 쓴 행동 기반 라벨, 재샘플링 대조군 대비 유형-처방 지도.

**공백.** 이 프로젝트에 고유한 것은 조합이다. 기하 코드의 정확한 변성(metamorphic) 채점, 하나의 사실(헬퍼, 계약, API 호출, 입력 필드)만 분리하는 짝지은 개입, 그리고 토큰 비용하에서 오류 유형별 처방 비교다. 개별 메커니즘 대부분에는 반드시 인용해야 할 가까운 선행 연구가 있다.

## 3. 동기

1. **실용성.** 코드 어시스턴트는 도구 카탈로그, 문서 덤프, 유틸리티 라이브러리를 받는다. 그럴듯한 도구가 모델이 작성하는 알고리즘을 조용히 바꾼다면, "모델에게 모든 것을 주라"는 잘못된 기본값이다.
2. **측정 가능성.** 알고리즘 코드에는 정확한 정답 검사(정확한 기하 오라클, 증명된 최적해)가 있으므로, 작은 프롬프트 변화도 정밀하게 측정할 수 있다.
3. **파일럿에서 이미 크고 메커니즘이 분명한 효과가 나타난다**(4.2절). 다른 알고리즘을 지칭하는 헬퍼 하나가 볼록 껍질 정확도를 97%에서 8%로 떨어뜨리고, 한 문장짜리 힌트가 이를 94%로 되돌린다. 5줄짜리 API 스니펫은 차량 경로 문제를 .23에서 .90으로 끌어올리는데, 추론만으로는 .03에 그친다.

## 4. 실험 설계

### 4.1 설정

**과제.** 모든 인스턴스는 정확한 참조 정답과 함께 프로그램적으로 생성된다.

| 도메인 | 핵심 | 홀드아웃(첫 발견 이후 설계) | 더 어려운 다단계 과제 |
|---|---|---|---|
| 기하 | 볼록 껍질 꼭짓점 수, 다각형 넓이 ×2, 점-다각형 포함, 선분 교차 개수, 최근접 쌍 | 볼록성 판정, 삼각형 내부 점, 볼록 다각형 겹침; 사전 등록(E2): Delaunay 검사, 가장 먼 점 쌍(farthest pair) | 다각형 내부 격자점(Pick), 직사각형 합집합 넓이(스윕 라인), 다각형 클리핑(정확한 유리수 교차 넓이) |
| 최적화 | 0/1 배낭, TSP, 그래프 색칠, makespan 스케줄링 | 빈 패킹, 정점 덮개 | 용량 제약 차량 경로(CVRP), 시간 창 VRP(VRPTW) |

- **기하 평가:** 모든 인스턴스는 8개의 동치 버전(평행이동, 회전, 반사, 순열, 스케일, 10^9 오프셋, 그리고 퇴화 사례)으로 제공되며, 프로그램은 8개 모두에서 맞아야만 정답으로 인정된다.
- **최적화 평가:** 증명된 최적해(DP, Held–Karp, 정확한 CP-SAT 모델)까지 푼 인스턴스의 비율이며, 솔버 조건은 OR-Tools와 최대 2회의 수리(repair) 라운드를 사용한다.

**개입.** 헬퍼 도구 상자(필요한 헬퍼만 = K0, 여기에 관련된 추가 헬퍼 K개, K는 최대 10); 숨은 계약(hidden contract)이 있거나 없는 필요한 헬퍼; 문서(없음, 전체 OR-Tools 시트, 문제별 스니펫, near-miss 스니펫, BM25 검색); 한 문장 알고리즘 힌트(수작업, 자기 생성, 검색); 검증된 샘플링(verified sampling, k개 프로그램, 레이블 없는 선택: 기하는 메타모픽 일관성, 최적화는 실행 가능성 + 최고 목적값); 추론 모드(thinking), 추론 예산, 추론 강도(reasoning effort); LoRA 증류.

**모델.** Qwen3 1.7B / 8B / 14B / 32B-AWQ; Llama-3.1-8B, Llama-3.3-70B; DeepSeek-R1-Distill-Llama-70B; OpenAI gpt-oss-20b / 120b(low / medium / high 추론 강도). vLLM으로 로컬 서빙한다(A100, vLLM 0.10.2; 2026-10-13부터는 RTX PRO 6000 Blackwell GPU와 vLLM 0.22를 사용했으며, 이 환경에서 이전 셀을 재실행하면 정확히 같은 개수가 재현되었다. 예: 네 모델의 VRPTW 27/30, 21/30, 8/30, 18/30, 0/30. 이 문서의 각 비교는 하나의 서빙 스택만 사용한다).

**통계와 대조군.** 기하 조건당 300개 프로그램(과제당 60개), 핵심 셀은 2–3 시드, 인스턴스에 대한 대응 부트스트랩(paired bootstrap) 95% CI. 헬퍼 효과는 실행 시 헬퍼를 미리 정의해 둔 상태로 보고한다(따라서 헬퍼를 복사하지 않고 호출만 한 모델은 실패로 집계되지 않는다). 참조 해답을 모든 하네스에 통과시켰으며(모든 과제에서 480/480), 새로운 모델 계열은 수치를 사용하기 전에 반드시 출력 추출 감사(audit)를 거친다.

### 4.2 파일럿 결과

각 결과는 파일럿 실행의 실제 예시로 끝난다(출력은 축약했으며, `…`는 생략된 줄을 표시한다). F1, F4, F5 예시는 동일한 볼록 껍질 인스턴스(점 10개, Qwen3-8B)를 사용하므로 해법들을 직접 비교할 수 있다.

**F1. 추가 헬퍼는 알고리즘 선택을 조향한다. 추론 모드는 하나의 해법이지만, 비싸고 유일한 해법도 아니다.**

관련은 있지만 불필요한 헬퍼 8개를 추가했을 때의 정답률(%) 변화(기하, n = 300; 모든 행은 제공된 헬퍼를 실행 시 미리 정의한 상태로 채점했으므로, 헬퍼를 복사하지 않고 호출만 한 프로그램도 그 논리로 판정된다; `poc/rescore_figs.py`):

| 모델 | 추론 모드 없음 | 추론 모드 / 추론 사용 |
|---|---|---|
| Qwen3-1.7B | +0.3, 단 과제별로 방향이 반대: hull −53, area2 −28, closest pair +47, segments +28 | −4.7 |
| Qwen3-8B | −14.3 (프롬프트에서도 헬퍼를 미리 정의: −12.3) | −1.5 |
| Qwen3-14B | −7.7 | −0.5 |
| Qwen3-32B | −13.3 (프롬프트에서도 헬퍼를 미리 정의: −15.0) | −3.0 |
| Llama-3.1-8B | −35.2 | – |
| Llama-3.3-70B | +0.8 | – |
| R1-Distill-Llama-70B | – | 0.0 |

(측정 그대로 채점하면 Qwen3-1.7B는 −35.7이었지만, 실행 오류(crash) 214건 중 185건은 헬퍼를 복사하지 않고 호출한 경우였다.)

![그럴듯한 헬퍼에 대한 강건성이 나타나는 지점](figs/fig7_distractor_by_model.png)

메커니즘(오프-이디엄 이탈, off-idiom drift)에 대한 증거:
- **코드가 알고리즘을 바꾼다.** 추가 헬퍼가 있으면 볼록 껍질 프로그램의 44–75%가 monotone chain에서 제공된 `polar_sort` 위에 구축한 Graham scan으로 전환하며, 실패하는 프로그램이 바로 이것들이다.
- **헬퍼 하나로 충분하다**(사전 등록 실험, `results/PREREG_E4.md`). `polar_sort` + `collinear`를 제공하면 hull 정확도가 97%에서 8%(8B), 83%에서 6%(32B)로 떨어진다. "암시적이지 않은" 헬퍼는 무해하다는 사전 등록 예측은 빗나갔으며(일부는 의존성을 통해 여전히 15–38점을 깎는다), 따라서 사전적인 유사성 레이블로는 피해를 예측할 수 없다.
- **선택은 로짓에서 보인다.** 각 모델이 직접 샘플링한 프로그램을 두 프롬프트하에서 채점하면, 도구 상자는 헬퍼 경로 프로그램의 가능도를 토큰당 0.40–0.71 nats 높이며, 이는 180개 인스턴스 100%에서 나타나고 모델 크기가 커질수록 줄어든다. 이 이동은 프로그램의 처음 ~10%(import와 헬퍼 이름)에 몰려 있다.
- **도메인 대비.** 최적화에서는 불필요한 API 8줄이나 다른 문제의 스니펫이 아무것도 바꾸지 않는다. 모델은 자신이 아는 정식화를 작성하고 추가 텍스트는 무시한다.
- **같은 메커니즘이 도움이 될 수도 있다.** 격자점 과제에서 추가 헬퍼에는 경계 위의 점을 정확히 판별하는 `point_in_polygon`이 포함되는데, 모델들은 이를 이용한 전수 계산으로 전환하고 Llama-70B는 60개 중 0개에서 45개로 올라간다.
- **새 과제에 대한 사전 등록 실험(E2, 가장 먼 점 쌍; `results/PREREG_E2.md`).** `convex_hull` + `polar_sort`를 제공하면 Qwen3-32B는 프로그램의 97%에서 hull 기반 코드로 전환하고 21.7점을 잃는다(CI [−31.7, −11.7]). 그런데 다른 알고리즘을 암시하지 않는 헬퍼(`point_in_polygon`, `segments_intersect`)는 두 번째 경로를 통해 오히려 더 많은 46.7점을 깎는다. 이 조건의 실패 66건 중 64건은 모든 입력 줄을 점으로 읽고 명시된 개수 줄(count line)을 무시하며(그 줄을 제거하면 정답을 출력한다), 66건 중 53건은 헬퍼를 하나도 호출하지 않는다. F3의 해법인, 프롬프트에 해당 인스턴스의 실제 입력을 보여 주는 방법은 이 실패를 모두 없앤다(120개 중 54 → 119). Qwen3-8B는 두 도구 상자 모두에서 brute force 프로그램을 유지해 영향을 받지 않으며, gpt-oss는 −3.3이다. 즉 추가 헬퍼는 알고리즘을 탈선시킬 수도, *혹은* 명시된 입력 형식에 대한 주의를 탈선시킬 수도 있으며, "알고리즘을 암시하는 헬퍼만 해롭다"는 사전 등록 예측은 32B에서 빗나갔다.
- **공개된 컨텍스트 처방은 조향을 되돌리지 못한다(B3, 사전 등록).** 도구 범위에 관한 한 문장 지시(2609.14157 방식)는 헬퍼 사용을 3분의 1 줄이지만 8B와 32B에서 피해의 2–3%만 회복한다. System 2 Attention(모델이 먼저 프롬프트를 다시 씀)은 핵심 과제를 11점 *악화*시키는데, 다시 쓴 프롬프트가 세부 사항을 잃거나(실수형 출력, 부호 있는 넓이) 32B에서는 프로그램이 없는 답을 낳기 때문이다. 다만 입력 형식 경로는 고친다(가장 먼 점 쌍 120개 중 54 → 98). 불필요한 헬퍼를 빼는 것이 여전히 효과가 있는 유일한 저비용 처방이다.

**결론이 그냥 "추론 모드를 쓰라"인가? 아니다.** 추론 모드가 피해를 없애는 이유는 모델이 코드를 쓰기 전에 알고리즘을 고르게 해 주기 때문이다. 알고리즘 선택을 고정하는 다른 방법도 훨씬 적은 비용으로 똑같이 효과가 있다(8B):

| 같은 피해에 대한 해법 | 정확도 | 프로그램당 출력 토큰 |
|---|---|---|
| 없음(추가 헬퍼 8개, 추론 모드 없음) | 76–78% (최악의 헬퍼 2개를 준 hull: 7%) | ≈0.8–1.1k |
| 전체 추론 모드 | 97% | ≈6k (예시 인스턴스에서 ≈15k) |
| 한 문장 알고리즘 힌트, 추론 모드 없음(hull, 최악의 헬퍼 2개, 3 시드) | 94% | ≈0.6k |
| 증류된 LoRA, 추론 모드 없음(F5) | 98% | ≈0.35k |
| 추가 헬퍼를 아예 제공하지 않음 | 92–97% | ≈0.3k |

또한 추론 모드는 나머지 두 실패 유형은 막지 *못한다*. 숨은 계약이 있는 필요한 도구(F2: 추론 모델 R1도 격자점 과제에서 여전히 걸려들고, 추론 모드를 켠 Qwen3-8B도 Delaunay 함정의 대부분을 그대로 갖는다)와 누락된 API 사실(F3: 문서 없이 추론 모드만 쓰면 .03에 그친다)이다. 따라서 F1의 실용적 메시지는 **도구 설계**에 관한 것이다. 과제에 필요한 헬퍼만 제공하고(불필요한 헬퍼는 알고리즘이나 입력 파싱을 탈선시킬 수 있다), 의도한 알고리즘을 명시하며, 예시 입력을 하나 보여 주라. 추론은 도구 상자를 통제할 수 없을 때의 대비책이다.

![용량-반응: 추가 헬퍼 수에 따라 피해가 커진다](figs/fig2_distractor_dose.png)

> **예시 F1** (Qwen3-8B, 동일한 점 10개 볼록 껍질 인스턴스, 네 가지 조건).
>
> *필요한 헬퍼만*: 교과서적인 monotone chain으로, 8개 버전 모두에서 정답.
> ```python
> points = sorted(set(points))
> for p in points:
>     while len(lower) >= 2 and orient(lower[-2], lower[-1], p) <= 0:
>         lower.pop()
>     lower.append(p)
> … (same for the upper hull)
> return lower[:-1] + upper[:-1]
> ```
> *추가 헬퍼 8개*: 모델은 헬퍼 정의 11개를 모두 복사하고, `polar_sort` 기반 Graham scan으로 전환하며, 시작점을 정렬된 리스트 안에 그대로 두고, 불필요한 "공선 점 제거" 단계를 덧붙인다. 8개 버전 모두에서 오답.
> ```python
> left = min(points, key=lambda p: (p[0], p[1]))
> sorted_points = polar_sort(points, left)        # the offered helper decides the algorithm
> hull = [left, sorted_points[0]]                 # sorted_points still contains `left`
> for p in sorted_points[1:]:
>     while len(hull) >= 2 and orient(hull[-2], hull[-1], p) <= 0:
>         hull.pop()
>     hull.append(p)
> …
> for i in range(len(hull)):                      # extra pass suggested by `collinear`
>     a, b, c = hull[i-2], hull[i-1], hull[i]
>     if orient(a, b, c) != 0:
>         final_hull.append(hull[i])
> ```
> *같은 헬퍼 + "Hint: Andrew's monotone chain …"*: 다시 monotone chain을 쓴다. `polar_sort`는 복사되지만 한 번도 호출되지 않는다. 정답, 563 토큰.
>
> *같은 헬퍼 + 추론 모드*: monotone chain, 정답이지만 15,168 토큰.

**F2. 필요한 도구라도 숨은 계약(hidden contract)이 있으면 함정이 된다.**
- lattice 과제에 필요한 헬퍼는 *부호 있는* 면적을 반환한다. 모델은 이를 `abs` 없이 사용하고, 시계 방향 입력에서 Pick 공식이 실패한다. Qwen3-32B는 60개 중 44개에서 9–15개로 떨어진다.
- 도구를 고치면(절댓값 반환) 46–49개로 회복되지만, docstring에 위험을 적는 것으로는 회복되지 않는다(17–19개). 모델이 헬퍼를 버리고 버그 있는 brute force로 갈아타기 때문이다.
- 추론은 위험을 줄이지만 없애지는 못한다. 추론 모드(thinking)의 Qwen3-8B는 52 대 60(부호 있음 대 부호 없음)이고, R1-Distill-70B는 toolbox를 주면 57 → 42이며 방향(orientation) 실패는 모두 `abs` 누락이다.
- 같은 숨은 가정은 헬퍼 없이도 나타난다. 다각형 clipping에서 gpt-oss는 실패 45건 중 35건에서 반시계 방향 입력을 가정한다.
- **새로운 사전 등록 과제에서도 재현된다(E2, Delaunay 검사: 주어진 삼각분할(triangulation)에서 외접원이 어떤 점을 엄밀히(strictly) 내부에 포함하는 삼각형의 개수를 센다).** 필요한 헬퍼 `in_circle`은 주석에서 삼각형이 반시계 방향이어야 한다고 짧게만 언급한다. 이 헬퍼를 주면 Qwen3-8B / 32B는 120개 중 1 / 3개를 풀고, 같은 헬퍼를 방향과 무관하게(orientation-free) 고치면 109 / 106개를 푼다(+90 / +86점). 실패의 92% / 97%는 방향을 보존하는 모든 사본에서는 맞고 대칭 사본이나 꼭짓점 번호를 바꾼(relabelled) 사본에서만 틀린다. 즉 프로그램이 삼각형의 방향을 한 번도 맞추지 않는다. 자세히 풀어 쓴 경고는 8B에서는 격차의 16%를, 32B에서는 75%를 회복한다. 32B에게는 간결한 헬퍼가 헬퍼가 없는 것보다 훨씬 나쁘며(120개 중 3 대 55), gpt-oss-20b(low effort)는 영향을 받지 않는다(118 대 117). 사전 등록한 확장 실험에서는 Llama-3.3-70B와 Qwen3-14B에서도 같은 함정이 나타난다(120개 중 8 → 120, 4 → 120; 둘 다 헬퍼가 없을 때보다 나쁘다, 81과 76). 추론 모드는 32B에서는 함정을 없애지만(118 대 120) 8B에서는 일부만 줄이며(51 대 118), 헬퍼를 고치는 데 드는 ≈0.4k 토큰과 달리 프로그램당 7.8–8.8k 토큰이 든다. 모델이 헬퍼를 직접 탐색해 문서를 쓰게 하는 방법(DRAFT 방식, B3)도 도움이 되지 않는다. 탐색 호출에서 시계 방향 삼각형을 한 번도 시험하지 않아 문서가 전제조건을 되풀이할 뿐이다(32B: 180개 중 27 대 손으로 쓴 경고 60개 중 43).

- **근접 오답 문서(near-miss reference)는 문서가 없는 것만큼 나쁘거나 더 나쁘다.** 전체 시트는 용량 제약 없는 TSP 라우팅을 보여 주고, 32B는 나머지를 지어낸다(CVRP .07). 시간 차원이 빠진 CVRP 스니펫은 VRPTW에서 0을 준다.
- **모호한 형식 문자열로 인한 입력 필드 누락(2026-10-13 정정).** VRPTW 프롬프트는 헤더를 `n capacity K service horizon`으로 적었고, gpt-oss-120b(low, medium 모두)는 거의 모든 프로그램에서 이를 `n capacity K horizon`으로 읽었다(30개 중 0–3개만 `service`를 읽음). 그 결과 horizon이 10이 되어 솔버가 실행 불가능(infeasible)을 보고했다. 필드를 뺀 입력으로 같은 프로그램을 다시 실행하면 49개 중 43개가 최적이다. 즉 경로 모델은 맞았고, 트레이스백을 준 수리로는 원인을 찾지 못한다. 필드를 다시 진술하라고 하면 모델은 "`n capacity K horizon` … maximum route end time (service horizon)"이라고 쓴다. *service horizon*을 하나의 복합 명사로 읽은 것이다. 헤더를 `n capacity K service_time horizon`으로 모호함 없이 쓰면 같은 서술형 프롬프트에서 120b low는 30/30, 30/30, 20b low는 29/30, 29/30이 최적이다(F3y). 따라서 이것은 명확한 명세를 사전 지식이 덮어쓴 것이 아니라 우리 명세의 모호함이었고, 더 큰 모델이 그것을 더 일관되게 한쪽으로 해석했을 뿐이다. 22개 형식 문자열 전체에 대한 행동 기반 감사(각 모델이 형식마다 파싱만 하는 프로그램을 작성; A1)에서 다른 모호한 형식은 없었다. 옛 VRPTW 헤더만 체계적으로 잘못 읽혔다(gpt-oss-120b, gpt-oss-20b, Qwen3-8B 모두 3번 중 3번).
- **해당 인스턴스의 실제 입력을 보여 주면 모호함이 해소되어 모든 gpt-oss 설정에서 해결되며, 토큰도 훨씬 적게 든다.** 스니펫과 함께 주면 120b low는 0에서 .97–1.00으로(인스턴스당 4.8k → 1.7k 토큰), 120b medium은 .07에서 1.00으로(10.7k → 3.7k), 20b low는 .07–.17에서 .80–.97로, 20b medium은 .57–.70에서 .90–1.00으로 오른다. 필드를 건너뛰는 프로그램은 30개 중 18–29개에서 0–3개로 줄어든다(필드를 제거하고 다시 실행한 반사실적(counterfactual) 재실행으로 측정). Qwen3-32B와 Llama-70B는 필드를 거의 건너뛰지 않으며, 이들에게 예시 입력은 .10–.23을 더해 준다. 이들의 실패는 스니펫만이 고칠 수 있는 API 오류이기 때문이다(스니펫 없이는 0에 머무는 반면, gpt-oss는 .50–.77에 도달한다). 같은 해법이 기하에서도 통한다(F1, E2). 무관한 헬퍼가 Qwen3-32B에서 일으키는 개수 줄 실패를 없앤다. 모델에게 필드를 먼저 다시 진술하게 하는 것은 도움이 되지 않는다(gpt-oss 30개 중 0–2개; 자신의 오독을 그대로 진술한다). 라우팅 문서 기반에 대한 DRoC 방식의 분해 검색(B4, 사전 등록)은 단순 top-3 검색보다 낫지만(+.12~+.15) 정확한 스니펫보다는 못하다(−.12~−.40; VRPTW에서 .03 대 .23–.63). 모델이 검색된 조각들 사이에서 인자 패턴을 뒤섞기 때문이다. 형식에 관한 사실 → 입력을 보여 주고 모호하지 않은 필드 이름을 쓰라. API에 관한 사실 → 조립된 스니펫을 보여 주라. 두 처방은 합성된다.
- **추론은 사실을 대체할 수 없다.** 추론은 켜고 문서는 주지 않으면 14B / 32B / R1-Distill-70B가 프로그램당 11–19k 토큰을 쓰고도 CVRP에서 .33 / .03 / .00에 그치며, 스니펫을 주면 .97 / .97 / .90이다.

- **예산:** 기하에서는 약 1k 추론 토큰으로 정확도 대부분을 회복한다(lattice 8B 60개 중 12 → 58). 최적화는 훨씬 많이 필요하다(TSP는 2k에서도 0에 머물고, bin packing은 ≈6k에서야 .87에 도달한다).
- **가장 어려운 과제에서는 처방들이 합성된다** (다각형 clipping, 낮은 effort의 gpt-oss-20b): 14 → 한 문장 힌트로 44 → 힌트 + 검사한 샘플 3개로 **60개 중 59**, 총 ≈2.8k 토큰. 검사는 한 번도 틀린 프로그램을 고르지 않았다. 비추론 Qwen/Llama는 어떤 조건에서도 180개 중 0–2개만 푼다.
- **네이티브 추론 모델은 경계(frontier)를 옮긴다.** 낮은 effort의 gpt-oss-20b는 헬퍼 유무와 관계없이 ≈0.4–0.9k 토큰으로 ≈99%이다. 높은 effort는 역효과를 낸다. 프로그램의 27%가 24k 토큰 안에 끝나지 않는다.
- **공개된 레이블 없는 선택 기법과의 비교(B1, 사전 등록; 인스턴스당 같은 후보 3개, Qwen3-8B):** 변성 검사는 인스턴스의 99.7 / 83.3 / 33.3%(깨끗한 프롬프트 / 추가 헬퍼 8개 / 어려운 과제)에서 올바른 프로그램을 고르며, CodeT(모델이 작성한 테스트와 기대 출력)는 96.0 / 82.7 / 26.7, 주어진 입력에서의 단순 다수결은 95.7 / 81.3 / 21.7, 모델이 쓴 입력이나 새 무작위 입력에서의 MBR-exec는 93.7 / 80.3 / 21.7–25.0, 토큰 확신도 선택기(DeepConf)는 최대 95.3 / 80.0 / 15.0이다. 같은 분포에서 뽑은 새 입력은 주어진 인스턴스의 대칭·확대 사본이 드러내는 부호와 방향 오류를 놓치며, 검사에는 생성 토큰이 들지 않는다.
- **검증된 샘플링(verified sampling)의 이득은 누출(leakage)이 아니다:** 주어진 인스턴스로 선택하고 새 인스턴스 5개로 채점하면 98.2 / 97.7 / 93.9(8B / 14B / 32B)이고, 같은 인스턴스 내 채점은 98.7 / 97.7 / 94.3이다.
- **모델 자신의 확신도(confidence)는 검사를 대체할 수 없다(C1, 사전 등록; Qwen3-8B, 인스턴스당 샘플 3개).** 프로그램 토큰의 평균 로그 확률은 생성과 함께 공짜로 얻어진다. 깨끗한 프롬프트에서는 이것이 맞는 프로그램과 틀린 프로그램을 실제로 구별하지만(AUROC 0.68), 3개 프로그램 중 확신도가 가장 높은 것을 고르면 단일 샘플 대비 +1.0점 [−1.1, +3.1]만 얻으며, 메타모픽 검사는 +7.0점을 얻는다. 추가 헬퍼 8개 조건에서는 틀린 hull 프로그램(제공된 `polar_sort` 위의 Graham scan)이 맞는 프로그램보다 *더* 확률이 높으며(AUROC 0.43), 이는 로짓 프로브(logit probe)가 예측한 대로다. 어려운 과제에서는 확신도가 정답 여부와 역상관하고(0.40), 확신도가 가장 높은 프로그램을 고르면 3.6점을 잃는다(확신도가 가장 높은 틀린 프로그램은 반복 루프와 판에 박힌(boiler-plate) brute force이다). Qwen3-32B에서도 재현되며(최고 확신도 선택 대 단일 샘플 +0.0 ~ +1.9, 유의하지 않음; 검사가 확신도를 6.7–22.5점 앞선다), 확신하면서 틀리는 경우는 32B가 헬퍼에 피해를 입는 과제(area2, AUROC 0.33)로 옮겨 간다. 확신도는 프로그램이 모델에게 얼마나 전형적인지를 측정할 뿐 맞는지를 측정하지 않으며, 샘플링 + 검사도 고전하는 바로 그 체계적 오류에서 실패한다.
- **검사 게이트(check-gated) 파이프라인은 실수에는 효율적이지만 체계적 오류는 보지 못한다(E3, 사전 등록; `results/PREREG_E3.md`).** 먼저 프로그램 하나를 생성하고, 메타모픽 검사에 실패할 때만 샘플 3개 + 검사를, 그중 일관된 것이 하나도 없을 때만 1,024토큰 추론 예산으로 프로그램 하나를 생성한다. 필요한 헬퍼만 줄 때(Qwen3-8B): 인스턴스당 출력 토큰 365개로 98.0%이며, 이는 best-of-3 + 검사(938 토큰)와 같은 정확도이고 전체 추론 모드(3,792 토큰에서 100%)에 근접한다. 추가 헬퍼 8개 조건 / 어려운 과제에서는 84.7% / 53.3%에 그쳐, 모든 인스턴스에 단순히 1,024토큰 추론 예산을 주는 것(거의 같은 토큰 1.6k / 1.7k에서 93.0% / 80.8%)보다 낮다. 원인은 검사의 사각지대다. 검사는 변환된 모든 사본에서 같은 방식으로 틀리는 프로그램을 통과시키며(K8에서 통과된 첫 프로그램 264개 중 28개, 어려운 과제에서 40개 중 21개), 잘못된 알고리즘은 대개 변환과 무관하게 똑같이 틀린다. 검사가 걸러 내 다음 단계로 보내는 것은 무작위 실수이지 체계적 오류가 아니다. 체계적 오류에는 작은 고정 추론 예산이 저렴한 기본값이다. 같은 모델이 작성한 무차별 대입(brute-force) 참조 프로그램(E3b, 사전 등록)은 검사가 놓친 오류의 86–90%를 잡아내지만, 그것을 작성하는 비용이 추론 예산만큼 들고 가장 어려운 과제에서는 참조 프로그램 자체가 틀리므로(격자점 60개 중 1개) 절약되는 것이 없다.

> x = float(data[idx]); y = float(data[idx + 1])     # products near 1e18 lose precision
> print(int(2 * area))

**F5. 강건성은 과제별로 빠른 모델에 증류(distillation)할 수 있으며, 학생(student) 모델 자신의 프로그램을 replay하면 다른 과제가 보호된다.**
- 같은 모델이 추론을 *켜고* 작성한 검증된 프로그램 600개로, 추가 헬퍼 0/4/8개 프롬프트에서 Qwen3-8B에 LoRA를 학습하면, 추가 헬퍼 8개 조건에서 77.0 → **98.0**(+21.0 [+17.8, +24.3], 2 seed)이 된다. ≈6k 대신 ≈350 토큰으로 추론 수준의 정확도를 낸다. 이 이득은 보지 못한 프롬프트 형식(다른 헤더, 헬퍼 10개)에서도 유지된다.
- 깨끗한 프롬프트로만(같은 크기) 학습하면 헬퍼 조건에서 이득이 없다. 모델은 단순히 더 나은 코드가 아니라 헬퍼를 무시하는 법을 배운 것이다.
- **전이 없음, 그리고 부수 피해:** 보지 못한 과제에서 증류 모델은 약간 나빠지고(58.6 → 52.2), 다른 과제 4개나 9개로 학습해도 도움이 되지 않으며, 보지 못한 취약한 과제는 깨끗한 프롬프트에서조차 붕괴할 수 있다(hull 97 → 28–34). 더 가벼운 학습은 이득을 없애는 대가로만 피해를 없앤다.
- **학생 모델 자신의 프로그램을 replay하면 피해가 사라진다(E4, 사전 등록; `results/PREREG_E4_REPLAY.md`).** hull을 제외하고 학습한(leave-hull-out) LoRA, 깨끗한 프롬프트의 hull 기준: 기본 모델 109/120, replay 없음 48, **+ 다른 과제 5개에 대해 학생 모델 자신이 추론 없이 작성한 검증된 프로그램 270개: 118**, + 정확히 같은 270개 프롬프트에 대한 추론 교사(teacher) 모델의 프로그램: 36(자기 replay − 교사 replay +68.3 [+60.0, +76.7]). 과제 내 강건성은 유지된다(헬퍼 8개 조건에서 240/240). 프로그램을 보면 이유가 드러난다. 기본 모델과 자기 replay 학생은 hull 프로그램 120/120에서 monotone chain을 쓰지만, replay 없는 학생과 교사 replay 학생은 각각 59개와 49개에서만 쓴다. 교사로부터 증류하면 학생은 한 번도 학습하지 않은 과제에서도 자신의 관용구(idiom)를 벗어나며, 자신의 프로그램이 그 관용구를 붙잡아 둔다. 모든 것이 보호되지는 않는다. 새 Delaunay 과제에서는 두 replay 조건 모두 떨어지므로(60개 중 59 → 47 / 45), 두 데이터 출처 어디에도 없는 과제는 여전히 재검증이 필요하다. 기존 처방과 비교하면(B2, 사전 등록): 튜닝된 가중치와 기본 가중치를 평균하는 WiSE-FT는 과제 내 이득을 포기해야만 hull을 지키거나(α 0.5: 119 / 240개 중 222) 그 반대이고(α 0.75: 96 / 236), SDFT(학생이 교사의 프로그램을 다시 쓰기)는 피해를 절반으로 줄이며(85) 헬퍼 8개 아래의 hull을 개선하는 유일한 방법이다(58 대 23–31). 학생 자신의 프로그램만으로 학습하면 104 / 235다. 둘 다 지키는 것은 자기 replay뿐이다(118 / 240). 그 학습 과제들은 개선 여지가 작았으므로(기본 225 / 240), E4b(사전 등록)에서는 hull도 학습하고 convex를 남겨 두었다. 과제 내 이득이 크고(헬퍼 8개 아래 5개 과제 236 → 300개 중 295, hull 60개 중 11 → 55), 자기 replay는 미학습 convex 과제를 헬퍼 아래에서 기본 수준으로 지키는 반면(120개 중 81 → 80), replay 없음은 55, 교사 replay는 42로 떨어진다.

> **예시 F5** (추가 헬퍼 8개가 있는 F1 hull 인스턴스, 추론 없음).
>
> *기본 Qwen3-8B* (1,067 토큰): 제공된 헬퍼 11개(`point_in_polygon`, `polar_sort`, `dist2`, `is_convex`, …)를 모두 복사하고 `polar_sort` 위에 hull을 구성한다. 틀림.
>
> *증류된 LoRA* (249 토큰): 필요한 것만 복사하고 monotone chain을 작성한다. 8개 버전 모두에서 맞음.
> ```python
> def orient(a, b, c):
>     return (b[0]-a[0])*(c[1]-a[1]) - (b[1]-a[1])*(c[0]-a[0])
>
> def convex_hull(points):
>     points = sorted(points)
>     …
>     for p in points:
>         while len(lower) >= 2 and orient(lower[-2], lower[-1], p) <= 0:
>             lower.pop()
>         lower.append(p)
>     …
>     return lower[:-1] + upper[:-1]
> ```
> *반대 측면*: 같은 방식으로 학습했지만 hull 데이터가 *전혀 없는* LoRA는 깨끗한 프롬프트 hull 과제의 정답률을 97%에서 28–34%로 떨어뜨린다. 실패 대부분은 미세조정 전에 작성하던 monotone chain 대신 Graham scan 변형과 즉흥적인 루프이다.

**E1. 실패는 어디서 오며, 어떤 처방이 어떤 유형을 고치는가 (저장된 모든 프로그램).** 주요 실행(388개 실행, 프로그램 47,868개)의 실패 프로그램 14,822개 각각에 행동만으로 정확히 하나의 유형을 부여했다. 즉 8개 버전 중 어느 것을 틀리는지, 재실행 시 어떤 예외를 내는지, 그리고 반사실적(counterfactual) 재실행(다른 입력 배치, 건너뛴 필드를 뺀 VRPTW 헤더, 제공된 헬퍼를 미리 정의)으로 판정했다. 유형마다 무작위 프로그램 8개를 직접 읽어 확인한 결과 기하 라벨 128개 중 127개, 최적화 라벨 97개 중 85개가 맞았다(`poc/analyze_e1_taxonomy.py`, `results/E1_TAXONOMY_DRAFT.md`).

각 실패를 처방 하나를 적용한 뒤의 같은 인스턴스와 짝지으면(대조군: 같은 조건을 다시 샘플링, 유형에 따라 9–52%를 구제) 처방 지도가 나온다. **API 사실 → 정확한 스니펫**(1,042개 중 618개 구제; 추론 모드는 240개 중 91개), **입력 형식 → 실제 입력 예시 하나**(94개 중 75개; 추론 노력 상향은 178개 중 44개), **방향 → 한 문장 힌트**(221개 중 188개) 또는 추론 노력 상향, **논리 → 추론 모드**(544개 중 476개) 또는 힌트(1,204개 중 810개)이며 이때 샘플링 + 검사는 재샘플링과 다르지 않다(914개 중 204개), **정밀도 → 샘플링 + 변성 검사**(55개 중 46개), **퇴화 경우 → 추론 모드**(27개 중 23개)이고 검사는 퇴화 사본을 아예 실행하지 않으므로 70개 중 0개를 구제한다, **헬퍼 호출 시그니처 오류 → API 계약 한 문장**(83개 중 61개), **복사하지 않은 헬퍼 → 미리 정의**(같은 프로그램이 630개 중 329개에서 성공; Qwen3-14B는 162개 중 125개지만 8B는 12개 중 3개로, 8B의 프로그램은 어차피 틀렸다).

채점 방식 하나가 중요하다. TSP 실패 293개는 요구된 "각 도시를 정확히 한 번"과 달리 출발 도시로 돌아오는 도시까지 출력한다(`0 … 0`). 그중 281개는 최적 경로다. 이를 인정하면 예컨대 문서 없는 Qwen3-32B는 .70에서 .83으로, Llama-70B(문서 없음 / 전체 시트 / 스니펫)는 .33 / .55 / .87에서 .54 / .73 / .99로 오른다. F3의 순서는 바뀌지 않고 격차만 줄어든다. 이 문서의 수치는 명시된 형식을 기준으로 한다.

## 5. 한계

1. **합성 과제.** 문제는 정확한 참조 답과 함께 생성된다. 현실적인 다단계 과제(clipping, VRPTW)가 주요 효과를 재현하지만, 실제 코드베이스는 더 크고 덜 명세된 맥락을 가진다.
2. **부분적으로 사후적인 메커니즘.** 관용구 이탈(off-idiom drift)은 데이터를 본 뒤에 세운 설명이다. 두 번의 사전 등록 검증이 그 핵심을 확인했지만(알고리즘 이름을 담은 헬퍼 하나가 hull 알고리즘을 뒤집는다; 숨은 계약 함정이 새 과제에서 재현된다) 유사도 기반 예측은 반박했으며, 새 과제에서는 알고리즘을 암시하지 않는 헬퍼가 대신 입력 파싱을 통해 피해를 주었다.
3. **Oracle 처방.** 스니펫과 힌트는 손으로 작성했다. 검색은 정확한 페이지를 가져올 때만 이에 필적하고, 자기 생성 힌트는 모델이 이미 알고리즘을 알 때만 도움이 된다. 배포된 시스템이 쓸 수 있는 레이블 없는 검사는 변환에 대해 불변인 오류를 놓친다(E3).
4. **범위.** 공개 가중치 모델만 다뤘다(세 계열; E5는 실행하지 않음). 일부 부차적 셀은 단일 seed이다. 2026-10-13 이후의 실행은 더 새로운 서빙 스택을 사용했다. 이전 셀을 재실행하면 정확히 같은 개수가 재현되었으며, 두 스택을 섞은 비교는 없다.
