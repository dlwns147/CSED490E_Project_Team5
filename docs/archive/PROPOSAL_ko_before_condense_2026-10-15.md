## 0. 입문: LLM은 기하·최적화 문제를 어떻게 푸는가

*이 분야가 처음인 독자를 위한 배경이다. 문서의 나머지는 이 내용을 전제로 한다.*

**두 문제 계열.**
- **계산기하(CG)** 는 좌표로부터 정확한 답을 계산한다. 점 집합의 볼록 껍질(convex hull), 다각형의 넓이, 두 선분의 교차 여부, 다각형 안에 있는 점, 들로네 삼각분할(Delaunay triangulation) 등이다. 답은 정확하고 검증할 수 있으며, 어려운 부분은 퇴화 입력(한 직선 위의 점, 중복된 점)과 방향(시계 방향 대 반시계 방향)이다.
- **조합 최적화(CO)** 는 지수적으로 많은 이산 선택지 중 가장 좋은 것을 고른다. 배낭 문제(어떤 물건을 넣을지), 외판원 문제(TSP, 가장 짧은 순회 경로), 용량과 시간 창이 있는 차량 경로 문제(VRPTW), 그래프 색칠, job-shop 스케줄링 등이다. 대부분 NP-난해다. 해가 *실행 가능한지*(제약을 지키는지) 확인하기는 쉽지만, *최적임*을 증명하기는 어렵다.

**LLM이 이런 문제에 접근하는 여섯 가지 방식.** 실제 계산을 누가 하느냐가 다르다.

| # | 방식 | LLM이 만드는 것 | 답을 계산하는 주체 | 대표 연구 | 전형적 약점 |
|---|---|---|---|---|---|
| 1 | 직접 답변 | 답 자체(단계별 추론을 거칠 수도 있음) | LLM | chain-of-thought (Wei et al., NeurIPS 2022); 추론 모델(o1, DeepSeek-R1, gpt-oss) | 산술 실수; 입력이 커질수록 정확도 하락 |
| 2 | 최적화기로서의 LLM | 후보 해를 내고, 점수를 보며 회차마다 개선 | 점수의 안내를 받는 LLM | OPRO (Yang et al., ICLR 2024; TSP 사례 연구) | 작은 인스턴스에서만 작동 |
| 3 | 답을 계산하는 프로그램 | Python으로 쓴 알고리즘 | Python 인터프리터 | PAL (Gao et al., ICML 2023); Program-of-Thoughts (Chen et al., TMLR 2023); 대회 코드: AlphaCode (Li et al., Science 2022) | 겉보기에 맞는 잘못된 알고리즘이나 놓친 경계 사례 |
| 4 | 솔버를 위한 정식화 | 솔버 코드로 쓴 변수, 제약, 목적함수 | 솔버(CP-SAT, MILP, OR-Tools routing) | Logic-LM (Pan et al., EMNLP Findings 2023); 최적화 모델링: NL4Opt (NeurIPS 2022 대회), Chain-of-Experts (ICLR 2024), OptiMUS (ICML 2024), ORLM (arXiv 2405.17743); 경로 문제: DRoC (ICLR 2025) | 솔버 API 오용; 잘못 모델링한 제약 |
| 5 | 진화시킨 휴리스틱 | 평가기가 남기거나 버리는 휴리스틱 함수의 여러 버전 | 가장 좋은 진화 프로그램 | FunSearch (Nature 2024); EoH (ICML 2024); ReEvo (NeurIPS 2024); AlphaEvolve (arXiv 2506.13131); 벤치마크: HeuriGym (arXiv 2506.07972) | 문제 유형 하나에 LLM 호출 수천 번 |
| 6 | LLM + 기호 증명기 | 증명을 위한 보조선·보조점 작도 | 기호 연역 엔진 | AlphaGeometry (Trinh et al., Nature 2024): 올림피아드 기하, IMO 문제 30개 중 25개 | 도형에 대한 증명이지 좌표 계산이 아님 |

- **방식 3–5는 표본–검사–수정 고리로 감싼다.** 프로그램을 여러 개 뽑고, 검사(문제 본문의 예제, 프로그램 간 출력 일치, 출력의 실행 가능성)를 통과한 것을 남기고, 오류를 되돌려 주어 고치게 한다(self-consistency, ICLR 2023; CodeT, ICLR 2023; AlphaCode의 거르기와 군집화; Self-Debugging, ICLR 2024).
- **방식 6은 다른 과제다.** 뉴스에서 말하는 "기하를 푸는 LLM"은 대개 올림피아드 정리 증명을 뜻하며, 좌표 계산이 아니다. 방식 2는 LLM이 최적화를 *할 수 있음*을 보여 주지만 규모가 커지면 작동하지 않는다.
- **실제로는** CG 문제는 방식 3으로, CO 문제는 방식 3과 4로 푼다. 이것이 이 프로젝트의 무대다.

**예시 A: 기하.** *과제: 꼭짓점 8개 다각형의 넓이의 두 배를 출력하라*(정확한 정수다. 파일럿은 각 인스턴스를 답이 같은 8개 사본으로 낸다: 평행이동, 회전, 대칭, 번호 재배열, 10⁹만큼 이동).
- *방식 1* (Qwen3-8B, 직접 답변, 추론 끔): 원본에서 **436**(정답), 평행이동 사본에서 **2944**, 회전 사본에서 **392**, 대칭 사본에서 **728**. 10⁹만큼 이동한 사본에서는 산술 도중 2,048토큰 한도에 걸린다.
- *방식 3* (같은 모델이 프로그램을 씀): Python이 실행한 신발끈 공식(shoelace formula)은 **8개 사본 모두에서** 정답이다. 요약하면:
  ```python
  pts = [(x[i], y[i]) for i in range(n)]
  s = sum(x1 * y2 - x2 * y1 for (x1, y1), (x2, y2) in zip(pts, pts[1:] + pts[:1]))
  print(abs(s))   # 넓이의 두 배, 정수 연산이라 정확함
  ```
- *그래도 틀리는 곳*(이 프로젝트의 주제): 표본 3개 중 하나는 좌표를 실수로 읽는다(예시 F4a). 그럴듯하지만 불필요한 헬퍼 함수 8개를 프롬프트에 넣으면, 모델은 주어진 `polar_sort` 위에 볼록 껍질을 만들고 모든 사본에서 틀린다(예시 F1).

**예시 B: 최적화.** *과제: 이웃한 노드끼리 색이 다르도록, 가능한 한 적은 색으로 노드 40개 그래프를 칠하라*(Qwen3-8B, 각각 4색이 필요한 그래프 6개).
- *방식 1* (직접 답변): 6개 색칠 중 유효한 것이 없다. 배낭 문제에서 직접 답변의 최적해와의 격차는 물건 10개에서 6%, 80개에서 48%로 커진다.
- *방식 3* (직접 짠 휴리스틱, 솔버 라이브러리 금지): 대체로 유효하지만 질이 낮다. 그래프 6개 중 3개에서 노드마다 한 색씩, 40색을 쓴다.
- *방식 4* (CP-SAT 모델): 모델은 열 줄 남짓을 쓰고, 솔버가 탐색해 최적임을 증명한다(요약):
  ```python
  from ortools.sat.python import cp_model
  m = cp_model.CpModel()
  c = [m.NewIntVar(0, n - 1, f"c{i}") for i in range(n)]   # 노드 i의 색
  for a, b in edges:
      m.Add(c[a] != c[b])                                    # 이웃은 다른 색
  k = m.NewIntVar(0, n - 1, "k")
  m.AddMaxEquality(k, c)                                     # k = 사용한 가장 큰 색 번호
  m.Minimize(k)
  cp_model.CpSolver().Solve(m)
  ```
  최대 두 번의 수정 후 그래프 6개 중 5개에서 최적인 4색을 찾는다. 첫 시도들은 `model.Minimize(max(colors))`에서 실패한다. 솔버 변수에 Python의 `max`를 쓴 것이다. 이렇게 빠진 API 사실이 발견 F3이다.
- *방식 2와 5* (선행 연구, 여기서는 실행하지 않음): OPRO는 이전 경로들과 그 길이를 보여 주고 더 짧은 경로를 요청한다. 작은 TSP에서는 최적해에 이르지만 도시 수가 늘면 단순한 휴리스틱에 뒤처진다. FunSearch는 점수 함수 하나만 진화시킨다. 예를 들어 온라인 빈 패킹(bin packing)에서 다음 물건을 어느 빈에 넣을지 정하는 `priority(item, bins)`다. 평가기가 각 버전을 생성된 인스턴스에서 돌리며, 진화한 규칙은 표준 규칙인 first-fit과 best-fit을 이긴다.

**벤치마크 규모에서는**(4.4절) 방식 3과 4가 풀린 문제와 거리가 멀다. 문제당 프로그램 하나로 실제 Codeforces 기하 문제 311개 중 모델에 따라 12–57%를 푼다. 고객 100명인 Solomon 경로 문제에서는 프롬프트에 세 가지 사실(파일 구조, "OR-Tools는 모든 곳에 정수를 받는다", 좁은 시간 창을 위한 첫 해 전략)이 없으면, 낮은 추론 노력에서 실행 가능한 계획을 내는 프로그램이 0–6%다(gpt-oss-120b medium은 46–50%).

**이 프로젝트의 위치.** 우리는 표본–검사–수정 고리를 포함한 방식 3과 4를 연구하며, 프롬프트에 무엇을 넣어야 하는지(헬퍼 함수, API 사실)와 어떤 처방에 얼마의 토큰 비용을 써야 하는지를 묻는다. 직접 답변보다 프로그램을 택한 근거가 되는 파일럿 결과는 1.1절에 있다.

## 1. 문제 정의

LLM은 알고리즘 문제를 일상적으로 프로그램 작성으로 푼다. 볼록 껍질(convex hull), 점-다각형 포함 판정, 차량 경로 문제를 위한 솔버 모델 등이 그 예다. 이런 프로그램은 겉보기에 맞아 보여도 실패하는 경우가 많으며, 흔한 반사적 대응은 프롬프트에 더 많은 것을 넣는 것이다. 헬퍼, 문서, 추론 토큰 말이다.

**연구 질문.** 어떤 인-컨텍스트(in-context) 추가물이 계산기하(CG)와 조합 최적화(CO)용 LLM 작성 프로그램을 개선하거나 악화시키는가, 그 이유는 무엇인가, 그리고 어떤 실패에 어떤 저비용 해법을 어느 정도의 토큰 비용으로 써야 하는가?

1. **도구.** 정확하지만 불필요한 헬퍼 함수가 코드를 바꾸는가, 바꾼다면 어떻게 바꾸는가? *필요한* 도구도 해를 끼칠 수 있는가?
2. **사실.** 솔버 코드에서 정확한 API 사용법이 전체 매뉴얼, 검색(retrieval), 혹은 더 많은 추론보다 나은가?
3. **해법 선택.** 언제 샘플링해 레이블 없이 검사하고, 언제 추론에 비용을 지불해야 하는가? 강건성을 빠른 모델에 증류(distillation)할 수 있는가?

### 1.1 LLM은 왜 알고리즘 문제를 프로그램으로 푸는가

LLM은 답을 직접 말할 수도 있다("볼록 껍질의 꼭짓점은 7개다"). 그러나 파일럿에서 직접 답변은 크게 실패했다.

| 방식 (추론 모드 끔) | 기하: 8개 버전 모두 정답 | 기하: 동치 입력에 같은 답 | 최적화: 최적해 도달 |
|---|---|---|---|
| 직접 답변 (Qwen3-8B / 32B) | 22% / 23% | 인스턴스의 **0%** | held-out 문제: .06–.19 (Llama-70B .02) |
| 프로그램 작성 후 실행 (Qwen3-8B) | **92–97%** | 과제별 50–100% (점-다각형 포함 판정이 최저) | API 스니펫을 준 솔버 프로그램: .71–.97 |

1. **정확한 계산을 실행에 맡긴다.** 직접 답변의 21%는 산술 도중 토큰이 바닥났다. 넓이의 두 배가 436인 다각형에 대해 Qwen3-8B는 원본, 평행이동, 회전, 대칭 사본에서 각각 436, 2944, 392, 728이라고 답했으며, 실행된 프로그램은 8개 버전 모두에서 정답이다.
2. **프로그램 하나가 모든 입력 크기를 처리한다.** 직접 답변은 크기가 커질수록 나빠진다(배낭 문제 최적 갭: 물건 10개 6% → 80개 48%; TSP: 도시 8개 9% → 20개 139%). ZebraLogic에서도 관찰된 "복잡도의 저주(curse of complexity)"다. 약 350토큰의 OR-Tools 프로그램은 크기와 무관하게 같은 비용이 든다.
3. **프로그램은 정답 레이블 없이 검사할 수 있으며**, 이것이 검증된 샘플링(F4)을 가능하게 한다. 직접 답변은 일관성조차 없다(7개의 동치 버전에서 같은 답을 낸 인스턴스가 하나도 없었다. 꼭짓점이 6개인 볼록 껍질에 대해 직접 답변은 4, 10, 4, 4, 6, 6, 6, 11이었고, 프로그램은 8개 모두에서 6을 출력했다).
4. **솔버는 수십 년의 공학을 재사용한다.** 모델은 문제를 *정식화*하기만 하면 된다. 4색이 필요한 노드 40개 그래프 6개에서 직접 답한 색칠은 모두 유효하지 않았고, CP-SAT 모델은 6개 중 5개에서 최적인 4색을 찾았다.
5. **LLM은 학습에서 풀이 과정보다 훨씬 많은 코드를 보며**, 프로그램 보조 추론(PAL, Program-of-Thoughts, Logic-LM)은 확립된 방법이다.

이 프로젝트가 연구하는 그 대가는 새로운 실패 유형(실행 환경 불일치, 솔버 API 오용, 퇴화 입력, 건전하지 않은 알고리즘)이며, 이 모두가 프롬프트의 영향을 받는다.

## 2. 배경 (관련 연구)

2026-10-13에 발견별로 확인했다. 판정과 링크를 담은 전체 표: `docs/notes/RELATED_WORK.md`.

- **코드를 조향하거나 오도하는 컨텍스트** (2606.04057; 2609.14157; 2608.11888; 2503.20589; 2306.03438; CodeCrash 2504.14119; 이전 형태로 GSM-IC, RAG-MCP, ToolRet): 프롬프트의 단서, 불필요한 도구, 그럴듯한 스킬, 오도하는 코드가 생성 코드를 악화시킨다. *본 연구:* 정확하지만 불필요한 헬퍼가 정확도를 무너뜨리며, 로짓 증거, 용량-반응 관계, 추론 모델의 면역, 입력 파싱 경로를 보인다.
- **명세가 부족한 도구와 계약** (2602.14878; DRAFT 2410.08197; ContractEval 2510.12047). *본 연구:* 같은 헬퍼를 전제조건이 있는 경우와 없는 경우로 짝지어 비교하면, 필요한 헬퍼가 헬퍼가 없을 때보다 나쁘며 이는 2개 계열 4개 모델에서 나타난다.
- **솔버 코드를 위한 문서** (DRoC, ICLR 2025; CP-Bench 2506.06052; Jain et al. 2024; 아깝게 빗나간 문서 2401.14887). *본 연구:* 같은 비용에서 정확한 스니펫이 전체 매뉴얼과 추론을 모두 이긴다.
- **명시된 명세보다 사전 지식(prior)을 따르는 현상** (2505.17225; 2507.14417; 2305.15507). *본 연구(정정):* VRPTW 사례는 이렇게 보였지만 실제로는 우리 형식 문자열의 모호한 필드 이름 때문이었다(F3). 남는 것은 진단 방법(반사실적 재실행, 형식 재진술)이다.
- **선택, 확신도, 연산 배분** (MBR-exec, CodeT, S*, incoherence 2507.00057; 메타모픽 프롬프트 2406.06864; 인스턴스 변형 2607.16646; 토큰 확신도 2402.02047, 2610.11300, Coder-Reviewer; DART 2606.23181; 무차별 대입 오라클 ALGO, ExeCRE 2608.04439). *본 연구:* 주어진 인스턴스의 변환 사본에서의 일관성, 헬퍼에 의해 뒤집히는 확신도, 그리고 고정 추론 예산에 지는 검사 게이트 라우팅.
- **망각과 자기 replay** (2510.18874; 2601.19897; 2501.14315; SDFT; RL's Razor). *본 연구:* 같은 프롬프트에서 학생 자신의 프로그램과 같은 가중치의 교사 프로그램을 대비하며, 관용구 표류가 프로그램에서 직접 보인다.
- **LLM 코드의 실패 분류** (2406.08731; 2407.06153; 2403.08937). *본 연구:* 반사실적 재실행에 기반한 행동 라벨과 유형-처방 지도.

**공백.** 개별 메커니즘 대부분에는 반드시 인용해야 할 가까운 선행 연구가 있다. 새로운 것은 조합이다. 정확한 변성(metamorphic) 채점, 하나의 사실(헬퍼, 계약, API 호출, 입력 필드)만 분리하는 짝지은 개입, 그리고 토큰 비용하에서 오류 유형별 처방 비교다.

## 3. 동기

1. **실용성.** 코드 어시스턴트는 도구 카탈로그와 문서 덤프를 받는다. 그럴듯한 도구가 알고리즘을 조용히 바꾼다면, "모델에게 모든 것을 주라"는 잘못된 기본값이다.
2. **측정 가능성.** 정확한 오라클과 증명된 최적해 덕분에 작은 프롬프트 효과도 측정할 수 있다.
3. **파일럿에서 나타난 큰 효과**(4.2절). 헬퍼 하나가 볼록 껍질 정확도를 97%에서 8%로 떨어뜨리고, 5줄짜리 API 스니펫은 차량 경로 문제를 .23에서 .90으로 끌어올린다(추론만으로는 .03).

메커니즘(오프-이디엄 이탈, off-idiom drift):
- **알고리즘이 바뀐다.** hull 프로그램의 44–75%가 monotone chain에서 제공된 `polar_sort` 위에 구축한, 실패하는 Graham scan으로 전환한다.
- **헬퍼 하나로 충분하다**(사전 등록, `docs/prereg/PREREG_E4.md`). `polar_sort` + `collinear`는 hull 정확도를 97%에서 8%(8B), 83%에서 6%(32B)로 떨어뜨린다. "암시적이지 않은" 헬퍼는 무해하다는 사전 등록 예측은 빗나갔다(이들도 15–38점을 깎는다).
- **선택은 로짓에서 보인다.** 도구 상자는 각 모델이 직접 샘플링한 헬퍼 경로 프로그램의 가능도를 180개 인스턴스 100%에서 토큰당 0.40–0.71 nats 높이며, 이 이동은 주로 import와 헬퍼 이름에 몰려 있다.
- **도메인 대비.** 최적화에서는 불필요한 API 8줄이 아무것도 바꾸지 않는다. 격자점 과제에서는 추가된 `point_in_polygon`이 오히려 도움이 된다(Llama-70B 60개 중 0 → 45).
- **새 과제에 대한 사전 등록 실험(E2, 가장 먼 점 쌍; `docs/prereg/PREREG_E2.md`).** `convex_hull` + `polar_sort`를 주면 Qwen3-32B는 프로그램의 97%에서 hull 기반 코드를 작성하고 21.7점을 잃는다(CI [−31.7, −11.7]). 알고리즘을 암시하지 않는 헬퍼는 입력 파싱을 통해 오히려 더 많은 46.7점을 깎는다. 이 조건의 실패 66건 중 64건은 명시된 개수 줄(count line)까지 포함해 모든 입력 줄을 점으로 읽는다. 해당 인스턴스의 실제 입력을 보여 주는 F3의 해법이 이를 없앤다(120개 중 54 → 119). "알고리즘을 암시하는 헬퍼만 해롭다"는 사전 등록 예측은 32B에서 빗나갔다.
- **공개된 컨텍스트 처방은 이를 되돌리지 못한다(B3, 사전 등록).** 도구 범위에 관한 한 문장 지시(2609.14157 방식)는 피해의 2–3%만 회복하고, System 2 Attention은 핵심 과제를 11점 *악화*시키며 입력 형식 경로만 고친다(120개 중 54 → 98).
- **문제 크기가 커지면 더 커진다(H1, 사전 등록):** 점 2,000–20,000개와 10초 제한에서 모든 헬퍼는 Qwen3-8B / 32B를 30 / 35점 떨어뜨린다(hull 80개 중 80 → 14). 작은 입력의 두 배다. gpt-oss는 low 노력에서도 헬퍼 유무와 상관없이 92–98%를 푼다.
- **붙여 넣은 코드가 없어도 일어난다(L1, 사전 등록):** 시그니처와 한 줄 설명만 있는 import 가능한 라이브러리로 제공해도 같은 추가 헬퍼가 Qwen3-32B를 19.3점 떨어뜨린다(hull 120개 중 104 → 32, hull 프로그램 120개 중 84개가 `polar_sort`를 import). Qwen3-8B에서는 새 실패가 더해진다. 라이브러리에 없는 함수를 import한다(실패한 hull 프로그램 54개 중 53개가 `from geomlib import convex_hull`). 한 문장("모듈에는 정확히 이 함수들만 있다", L2)이 그런 import를 없애지만(106 → 3개 프로그램; hull 120개 중 13 → 103) 조향은 없애지 못한다(추가 헬퍼가 있으면 8B는 8.8점, 32B는 20.0점을 잃는다).
- **우리가 만들고 시험한 방법(사전 등록; 실행 전 선행 연구 확인; `docs/prereg/PREREG_M1.md`, `PREREG_M2_M4.md`).** 모델이 헬퍼 없이 쓴 초안의 확률을 낮추는 헬퍼를 빼는 확률 필터(M1)는 보정 단계에서 실패한다. 필요한 헬퍼도 해로운 헬퍼만큼 강하게 표시한다. 헬퍼를 보기 *전에* 프로그램을 쓰고 그 뒤 헬퍼를 쓰도록 리팩터링하는 방법(M4)은 피해가 조향일 때 저렴하고 강하지만(핵심 과제, 8B: 600개 중 579 대 모든 헬퍼 468, ≈0.8k 토큰), 전체로는 1,024토큰 추론 예산에 진다(통합 8B 89.0 대 94.5%, 32B 85.2 대 90.0%, 토큰은 절반 정도). 알고리즘을 유지하라는 문장 자체는 기여가 없다. 헬퍼마다 프로그램을 써서 탐색하는 방법(M3)은 틀린 프로그램이 일관적인 `polar_sort`를 남기고 6–10k 토큰이 든다. 가장 강한 방법은 공개된 것이다. 도구 상자가 있을 때와 없을 때 쓴 표본에 대한 TroVE 방식 투표(통합 91.2 / 95.0%)로, 두 문맥이 서로 다른 과제에서 실패하기 때문이다. 우리의 저비용 변형(M5: M4의 초안과 리팩터링 결과가 다르면 변성 검사를 통과하는 쪽을 택함)은 32B에서 ≈0.8k 토큰으로 91.5%에 도달해 추론 예산(1.6k 토큰에서 90.0%)보다 높고, 8B에서는 효과가 없다.

**결론이 그냥 "추론 모드를 쓰라"인가? 아니다.** 추론 모드가 효과가 있는 이유는 모델이 코드를 쓰기 전에 알고리즘을 고르기 때문이다. 그 선택을 고정하는 다른 방법도 훨씬 적은 비용으로 똑같이 효과가 있다(8B):

| 같은 피해에 대한 해법 | 정확도 | 프로그램당 출력 토큰 |
|---|---|---|
| 없음(추가 헬퍼 8개, 추론 모드 없음) | 76–78% (최악의 헬퍼 2개를 준 hull: 7%) | ≈0.8–1.1k |
| 전체 추론 모드 | 97% | ≈6k (예시 인스턴스에서 ≈15k) |
| 한 문장 알고리즘 힌트, 추론 모드 없음(hull, 최악의 헬퍼 2개, 3 시드) | 94% | ≈0.6k |
| 증류된 LoRA, 추론 모드 없음(F5) | 98% | ≈0.35k |
| 추가 헬퍼를 아예 제공하지 않음 | 92–97% | ≈0.3k |

추론 모드는 숨은 계약(F2)이나 누락된 API 사실(F3)은 막지 *못한다*. 실용적 메시지는 **도구 설계**다. 필요한 헬퍼만 제공하고, 의도한 알고리즘을 명시하며, 예시 입력을 하나 보여 주라. 추론은 대비책이다.

![용량-반응: 추가 헬퍼 수에 따라 피해가 커진다](figs/fig2_distractor_dose.png)

> **예시 F1** (Qwen3-8B, 동일 인스턴스, 네 가지 조건). *필요한 헬퍼만*: 교과서적인 monotone chain으로, 8개 버전 모두에서 정답.
> ```python
> points = sorted(set(points))
> for p in points:
>     while len(lower) >= 2 and orient(lower[-2], lower[-1], p) <= 0:
>         lower.pop()
>     lower.append(p)
> … (same for the upper hull)
> return lower[:-1] + upper[:-1]
> ```
> *추가 헬퍼 8개*: 모델은 헬퍼 정의 11개를 모두 복사하고 `polar_sort` 위에 Graham scan을 구성한다(시작점을 리스트 안에 남기고, 불필요한 공선 점 제거 단계를 덧붙임). 8개 모두에서 오답.
> ```python
> left = min(points, key=lambda p: (p[0], p[1]))
> sorted_points = polar_sort(points, left)        # the offered helper decides the algorithm
> hull = [left, sorted_points[0]]                 # sorted_points still contains `left`
> …
> for i in range(len(hull)):                      # extra pass suggested by `collinear`
>     a, b, c = hull[i-2], hull[i-1], hull[i]
>     if orient(a, b, c) != 0:
>         final_hull.append(hull[i])
> ```
> *같은 헬퍼 + "Hint: Andrew's monotone chain …"*: monotone chain, 정답, 563 토큰. *같은 헬퍼 + 추론 모드*: 같은 결과지만 15,168 토큰.

**F2. 필요한 도구라도 숨은 계약(hidden contract)이 있으면 함정이 된다.**

- **부수 피해:** 보지 못한 과제는 약간 나빠지고(58.6 → 52.2), 보지 못한 취약한 과제는 깨끗한 프롬프트에서조차 붕괴할 수 있다(hull 97 → 28–34; 예시 F5).
- **학생 모델 자신의 프로그램을 replay하면 피해가 사라진다(E4, 사전 등록; `docs/prereg/PREREG_E4_REPLAY.md`).** hull을 제외하고 학습한(leave-hull-out) LoRA, 깨끗한 프롬프트의 hull 기준: 기본 모델 109/120, replay 없음 48, **+ 다른 과제 5개에 대해 학생 모델 자신이 추론 없이 작성한 검증된 프로그램 270개: 118**, + 정확히 같은 270개 프롬프트에 대한 추론 교사(teacher) 모델의 프로그램: 36(자기 − 교사 +68.3 [+60.0, +76.7]). 과제 내 강건성은 유지된다(240/240). 기본 모델과 자기 replay 모델은 hull 프로그램 120/120에서 monotone chain을 쓰지만, replay 없는 학생과 교사 replay 학생은 각각 59개와 49개에서만 쓴다. 새 Delaunay 과제에서는 두 replay 조건 모두 여전히 떨어진다(60개 중 59 → 47 / 45).
- **기존 처방과의 비교(B2, 사전 등록):** WiSE-FT는 hull과 과제 내 이득을 맞바꾼다(α 0.5: 119 / 240개 중 222; α 0.75: 96 / 236). SDFT는 피해를 절반으로 줄이고(85), 학생 자신의 프로그램만으로 학습하면 104 / 235다. 둘 다 지키는 것은 자기 replay뿐이다(118 / 240). hull도 학습하고 convex를 남겨 둔 E4b에서 자기 replay는 헬퍼 8개 아래의 convex를 기본 수준으로 지키면서(120개 중 81 → 80; replay 없음 55, 교사 replay 42) 큰 과제 내 이득도 유지한다(300개 중 236 → 295). 두 번째 학습 시드(R1)에서도 두 대비가 재현된다. 자기 replay 대 교사 replay는 118 대 28(hull), 85 대 34(convex)다.

> **예시 F5** (F1 hull 인스턴스, 추가 헬퍼 8개, 추론 없음). *기본 Qwen3-8B* (1,067 토큰)는 헬퍼 11개를 모두 복사하고 `polar_sort` 위에 hull을 구성한다. 틀림. *증류된 LoRA* (249 토큰)는 필요한 것만 복사하고 monotone chain을 작성한다. 맞음.

>     return (b[0]-a[0])*(c[1]-a[1]) - (b[1]-a[1])*(c[0]-a[0])
>
> def convex_hull(points):
>     points = sorted(points)
>     …
>     return lower[:-1] + upper[:-1]
> ```

- **처방 선택(F4)은 성립한다.** 문제 본문의 예제가 값싼 무라벨 검사다. 표본 3개에서 최선의 표본과의 차이를 대부분 메우고, 출력 일치(MBR-exec)는 약 1점을 더한다. gpt-oss-20b에서는 표본 + 검사나 한 번의 수정이 medium 비용보다 낫고, gpt-oss-120b에서는 medium 한 번이 low 세 번보다 낫다. Qwen의 think-1,024 × 3 + 검사는 전체 추론과 같은 정확도를 토큰 64%로 낸다(그림 9).
- **사실(F3)은 성립하고 함께 작동한다.** 파일 구조, "OR-Tools는 모든 곳에 정수를 받는다"(모델은 `1e7`을 쓴다), 좁은 시간 창에서도 작동하는 첫 해 전략이 각각 필요하며, 하나만으로는 효과가 작다(그림 10). Qwen3-32B는 주어진 호출을 존재하지 않는 시그니처로 바꿔 쓴다. 교과서적인 CP-SAT job-shop에는 사실이 필요 없다.
- **헬퍼(F1)의 효과는 줄어든다.** gpt-oss-20b low는 관련 헬퍼 8개로 4.3점 잃는데(p = 0.001), 주로 덜 추론하기 때문이다. 무관한 헬퍼나 "대부분 필요 없음" 머리말은 약 2점(유의하지 않음)이고, Qwen3-32B와 gpt-oss-120b는 영향이 없다(그림 11).
- **방법.** 예제를 대칭 변환해 새 테스트를 만드는 방법(N1, 새 방법)은 예제를 통과한 틀린 프로그램의 6%만 잡는다. 대회 문제의 오류는 대칭 변환에서도 남는다. 실패한 예제로 한 번 고치게 하는 방법(N2)은 토큰당 가장 좋은 다음 단계다(gpt-oss-120b low 4.6k 토큰에 46.0 → 53.1%). 예제를 통과하지 못할 때만 올리는 방법(N3, 공개된 아이디어)은 gpt-oss-20b에서 토큰 13%를 덜 쓰고 2.7점을 더하며, 먼저 고치는 조합(N4)은 약 1점을 더한다. 실행으로 검증하는 사실 캐기(FM, 새 방법; 가장 가까운 선행 연구: Dynamic Cheatsheet)는 파일 구조와 정수 사실을 찾고 gpt-oss-120b를 보지 않은 Solomon 사례에서 7%에서 21–40%로 올리지만(한 체인 65%), 체인 간 편차가 크고 gpt-oss-20b에는 도움이 안 되며 여러 체인을 모아도 나아지지 않는다. 부분적 음성 결과다(프로그램 16개로 하는 검증은 잡음이 크고, 캐낸 사실은 산문 형태의 국소 수정이며 손으로 쓴 사실은 작동하는 코드다).
- **한 번 검증하고 재사용(V1).** Solomon 사례는 모두 같은 형식이므로 프로그램 하나로 모두를 풀 수 있다. 훈련 사례 8개에 대해 쓴 프로그램 16개 중 (라벨 없이 실행 가능성으로) 고른 최선의 프로그램은 보지 않은 48개 중 45개(94%, 격차 중앙값 1.4%)에서 실행 가능한 해를 낸다. 사례마다 새로 쓴 프로그램은 7%만 실행 가능한 gpt-oss-120b에서, 사례당 1.8k 토큰 대신 전체 28k 토큰으로다. 읽기 함수와 견고한 스니펫이 있으면 두 gpt-oss 모델 모두 48개 중 48개에 이른다. 뽑은 프로그램 중 작동하는 후보가 하나는 있어야 한다. 사실 없는 gpt-oss-20b(사례별로는 112개 중 0개 실행 가능)는 64개 중에서 하나를 찾고(94%, 격차 5.9%, 107k 토큰), 읽기 함수 + 견고한 스니펫을 준 Qwen3.8은 16개 중에서 찾으며(100%, 격차 1.3%), Qwen3-32B는 찾지 못한다. 훈련 사례에서 먼저 고치면(V2) gpt-oss-20b는 94%에서 실행 가능한 프로그램(격차 6%)을 얻지만, Qwen3.8은 솔버를 탐욕 휴리스틱으로 바꿔 "고쳤다"(어디서나 실행 가능, 경로 56% 더 김). 실행 가능성만 보는 검사는 최적화를 포기하는 쪽에 보상을 준다. 품질 기준(V3)은 이를 막지만 더 나은 프로그램을 찾지 못하고, 20b의 수정 성공은 재현되지 않았다. 검색한 풀이된 기하 문제 하나를 예시로 주는 방법(N6; 선행 연구 SolveRank, USACO)은 gpt-oss-120b에서 시드 하나로는 유의해 보였지만(132 → 147, p = 0.03) 시드 세 개에서는 +1.2점(p = 0.39)에 그치고, gpt-oss-20b는 2.0점 잃는다(p = 0.14). 시드 하나의 p값은 재현되지 않았다. 대회 기하용 근사 brute-force 오라클(N5, ALGO를 연속값 답으로 확장)은 예제를 통과한 틀린 프로그램의 53–68%를 약 4%의 오경보로 잡지만, 선택이나 수정 계기로 쓰면 1점도 더하지 못한다. 대회 기하에서 병목은 맞는 프로그램을 알아보는 것이 아니라 만드는 것이다. 같은 절차는 두 gpt-oss 모델 모두에서 보지 않은 job-shop 32개(CP-SAT)를 모두 풀고, 합성 과제에서는 F1의 헬퍼 피해를 없앤다. 헬퍼 8개 아래에서 hull은 사례별 17–21%에서, 답을 아는 사례 5개로 표본 10개 중 하나를 고르면 보지 않은 55개에서 100%가 된다(무라벨 변성 검사로는 부족하다: 일관되지만 틀린 hull 프로그램을 고른다). 문제당 해법 하나를 만드는 방식은 휴리스틱 설계 벤치마크의 표준이며, 사례별 생성은 이 모델들의 능력을 과소평가한다.
- **실제 문제에서의 증류(D1).** 훈련 문제 206개에 대한 검증된 교사 프로그램 431개로 Qwen3-8B를 LoRA 학습하면 보지 않은 대회 문제 정확도가 12.1%에서 4.8%로 떨어진다(자기 재연습을 더하면 3.5%; 그래도 합성 과제는 보호한다: hull 120개 중 118 대 77). 학생은 교사의 간결한 코드를 따라 하며 자신의 단계별 주석을 버린다(주석 12 → 5줄). 대신 자기 자신의 정답 63개로 학습하면 12.9%에서 15.2%가 된다(깨끗한 시험 문제 88개; CodeContests에서 시험 문제 17개의 본문이 훈련 문제와 같다). 교사 프로그램에 주석을 되살려도 피해는 사라지지 않는다(6.8%, 기본 대비 p = 0.007). 학생이 이미 푸는 문제로 교사 프로그램을 제한해도 마찬가지다(5.3%). 학생은 교사의 관용구를 받아들이고 쉬운 문제에서도 새 오류를 만든다. 실제 문제에서의 F5 관용구 표류다(Li et al. 2025의 학습 가능성 격차 참고). 자기 자신의 검증된 프로그램이나, 교사의 풀이를 자기 방식으로 다시 쓴 풀이(D3)는 해도 득도 없다(11.0–15.2% 대 시드 8개 기본 평균 14.6%). 값싼 증류는 어려운 문제의 처방이 아니다.

## 5. 한계

1. **합성 과제.** 주요 효과는 생성한 과제에서 찾았다. 표준 벤치마크(4.4절)에서 F3와 F4는 성립하고, F1은 한 모델의 작은 효과로 줄어들며, F2는 직접 다시 시험하지 않았다(자연스러운 사례 하나: 우리가 준 읽기 함수가 실수를 반환해 OR-Tools의 정수 계약을 깼다).

2. **부분적으로 사후적인 메커니즘.** 관용구 이탈(off-idiom drift)은 데이터를 본 뒤에 세운 설명이다. 사전 등록 검증이 그 핵심을 확인했지만 유사도 기반 예측은 반박했으며, 새 과제에서는 알고리즘을 암시하지 않는 헬퍼가 대신 입력 파싱을 통해 피해를 주었다.
3. **Oracle 처방.** 스니펫과 힌트는 손으로 작성했다. 검색은 정확한 페이지를 가져올 때만 이에 필적하며, 배포 가능한 레이블 없는 검사는 변환에 불변인 오류를 놓친다(E3).
4. **범위.** 공개 가중치 모델만 다뤘다(세 계열; E5는 실행하지 않음). 일부 부차적 셀은 단일 seed이다.
