# 사실, 도구, 검사: LLM은 왜 틀린 기하·최적화 코드를 작성하는가, 그리고 과제를 모른 채 이를 어떻게 고칠 것인가

*대학원 NLP 수업 프로젝트 제안서: 계산기하(computational geometry)와 조합 최적화(combinatorial optimization)*

> **번역 안내.** 이 파일은 [PROPOSAL.md](PROPOSAL.md)(영문 원본, 2026-10-13 기준)의 한국어 번역본이다. 표·수치·코드·파일 경로는 원본과 동일하며, 내용이 다를 경우 영문 원본이 기준이다.

> **이 파일에 대하여.** 이 문서는 프로젝트의 유일한 문서로, 제안서(1–4절), 부록 A(코드, 실행 방법, 진행 상황), 부록 B(제공된 도구와 올바른 프로그램 및 실패한 프로그램의 실제 예시), 부록 C(문제, 풀이, 진단의 추가 예시), 그리고 5절(파일럿에 대한 비판적 검토)로 구성된다. 모든 파일럿 결과, 수정 사항, 주의점을 담은 전체 시간순 실험 기록은 [docs/FINDINGS.md](docs/FINDINGS.md)이며, 최종 표는 그 끝에 있다. 코드와 최종 결과는 2026-10-11에 `/NAS/SJ/llm_algo_poc`에서 복사했으며, 코드 내부 경로는 이 폴더를 가리킨다.

## 1. 문제 정의

이제 대규모 언어 모델(LLM)에게 프로그램을 작성해 알고리즘 문제를 풀게 하는 일은 흔하다. 볼록 껍질(convex hull), 점-다각형 포함 판정(point-in-polygon), 최적화 솔버용 배낭 문제(knapsack)나 TSP 모델 등이 그 예다. 이런 프로그램은 겉보기에는 *그럴듯하지만* 실패하는 경우가 많다. 존재하지 않는 라이브러리 호출에서 크래시가 나기도 하고, 공선(collinear) 점, 중복 점, 변 위에 놓인 질의 점 같은 퇴화(degenerate) 입력에서 깨지기도 하며, 실행 가능(feasible)하지만 최적과는 거리가 먼 해를 내기도 한다.

일반적인 대응은 프롬프트에 더 많은 것을 넣는 것이다. 더 많은 문서, 더 많은 헬퍼 함수, "견고하게 작성하라"는 지시, 혹은 더 많은 추론 토큰이다. 그러나 이러한 맥락 내(in-context) 추가 요소 중 무엇이 도움이 되고 무엇이 해가 되는지, 그리고 그 이유는 무엇인지에 대해서는 알려진 바가 거의 없다.

**연구 질문.** 프롬프트 속 어떤 정보가 계산기하(CG)와 조합 최적화(CO)용 LLM 작성 프로그램을 실패하게 만드는가? 과제마다 적합한 도구를 손으로 골라주지 *않고도* 효과가 있는 해결책은 무엇인가?

다음 네 가지 세부 질문을 다룬다.

1. **실패 원인.** 실패 중 얼마만큼이 진짜 알고리즘 오류가 아니라 누락된 사실로 설명되는가? 누락된 사실에는 실행 환경(어떤 라이브러리가 존재하는가)과 라이브러리/API 계약(솔버 상태 코드, 콜백 규약, 인자 타입)이 포함된다.
2. **불필요한 도구.** 올바르지만 필요 없는 헬퍼 함수나 API 문서가 생성 코드의 품질을 떨어뜨리는가? 그렇다면 그 피해는 추가 요소의 개수에 따라 어떻게 커지는가, 모델이 그것을 *사용*해야만 피해가 생기는가, 그리고 "이 중 대부분은 필요 없다"는 지시로 이를 제거할 수 있는가?
3. **과제 불문(task-agnostic) 해결책.** 두 가지 저비용 개입이 손으로 고른 과제별 도구에 필적할 수 있는가? (a) 모델이 틀리는 사실을 명시한다. (b) 프로그램을 몇 개 샘플링한 뒤 레이블 없는 검사를 통과한 것 하나를 남긴다. 기하에서는 메타모픽 일관성(metamorphic consistency), 최적화에서는 실행 가능성과 목적함수 값이 그 검사다. 각각은 언제 효과가 있는가?
4. **누가 이득을 보는가.** 이러한 효과는 모델 크기(1.7B–72B), 모델 계열, 추론 모드(thinking)에 따라 어떻게 달라지는가?

## 2. 배경 (관련 연구)

**무관한 맥락은 LLM 추론을 해친다.**
- Shi et al. (2023, GSM-IC)은 수학 문장제에 무관한 문장을 추가하면 정확도가 급격히 떨어짐을 보였다.
- 이후의 통제된 연구들은 정확도가 방해 요소(distractor) 개수에 대해 대략 거듭제곱 법칙(power law)을 따라 떨어짐을 보인다("How Is LLM Reasoning Distracted by Irrelevant Context?", EMNLP 2025).

이 연구들은 자연어 추론을 다룬다. 우리는 같은 질문을 *코드 수준* 맥락, 즉 모델이 자기 프로그램에 복사해 넣을 수 있는 헬퍼 함수와 API 문서에 대해 던진다.

**LLM 에이전트의 도구 과부하.** 함수 호출(function-calling) 에이전트에서는 도구 카탈로그가 커질수록 도구 선택 정확도가 떨어진다. 제안된 대응은 다음과 같다.
- 관련된 작은 부분집합만 검색해 제공하기(RAG-MCP; ToolRet, 2025);
- 보여줄 도구 수를 적응적으로 조절하기("How Many Tools Should an LLM Agent See?", 2026);
- 최소한의 인과적 도구 경계(causal tool frontier)만 노출하기(ToolChoiceConfusion, 2026).

관련 연구는 모든 도구가 무관할 때의 불필요한 도구 호출(spurious tool invocation)과, 의미적 방해 요소 아래에서의 "도구 사용세(tool-use tax)"를 측정한다. 이들은 모두 *에이전트가 어떤 도구를 호출하는가*에 관한 것이다. 우리는 *생성된 프로그램 안에 삽입되는* 도구를 연구하며, 추가 도구가 한 번도 호출되지 않을 때에도 발생하는 피해를 찾는다.

**문서 증강 코드 생성(documentation-augmented code generation).** Jain et al. (2024)은 검색된 API 문서가 드물게 쓰이는 API에서는 도움이 되지만, 검색이 무관한 문서를 가져올 경우 자주 쓰이는 API에서는 정확도를 떨어뜨림을 발견했다. 이들의 해결책은 필요할 때만 검색하는 것이다. 우리의 CO 결과는 이를 보완하는 사례를 보여준다. 짧은 문제별 스니펫이 완전한 치트시트보다 낫다.

**솔버 및 코드와 결합한 LLM.**
- 프로그램 보조 추론(PAL, Program-of-Thoughts)과 솔버 증강 추론(Logic-LM, SatLM, LINC)은 문제를 코드나 솔버 모델로 변환한다.
- NL4Opt와 OptiMUS는 최적화 문제를 솔버 정식화(formulation)로 변환한다.
- ZebraLogic (Lin et al., ICML 2025)은 탐색 공간이 커질수록 LLM의 직접 추론이 붕괴함을 보인다("curse of complexity").

이 연구들은 *API 오용*을 별도의 실패 원인으로 분리하는 경우가 드물다. 우리는 API 오용이 해결되기 전까지는 솔버가 직접 추론보다 나빠 보이게 만들 수 있음을 보인다.

**선택과 검증.**
- 자기 일관성(self-consistency, Wang et al., 2023)과 테스트 기반 선택(예: CodeT)은 샘플링된 출력 중에서 하나를 고른다.
- 메타모픽 검사(metamorphic testing)는 변환된 입력들 사이의 알려진 관계를 출력이 지키는지 확인하므로 정답 레이블이 필요 없다.
- 계산기하에서 퇴화 입력에 대한 견고성과 정확 산술(exact arithmetic)은 고전적인 문제다(Kettner et al., "Classroom examples of robustness problems in geometric computations", 2008).
- LLM 코드 견고성에 관한 연구들은 견고성 결함의 대부분이 조건 검사 누락임을 발견했다.

우리는 메타모픽 검사와 샘플링을 결합해 기하 코드를 위한 레이블 없는 선택기(selector)로 사용한다.

**공백.** 우리가 찾아본 한, 다음을 연구한 선행 연구는 없다.
- 알고리즘 코드에서 맥락 내 *헬퍼 함수와 솔버 문서*를 방해 요소로 다루는 것;
- 그 피해가 헬퍼의 사용을 필요로 하는지 여부;
- 그것이 도메인(기하 vs 최적화)에 따라 어떻게 다른지;
- 언제 과제 불문 해결책(사실 명시 vs 검증 샘플링)이 과제별 도구 선택을 대체할 수 있는지.

## 3. 동기

1. **실용적 동기.** 코드 어시스턴트는 점점 더 큰 도구 카탈로그, 문서 덤프, "유용한" 유틸리티 라이브러리를 받는다. 그럴듯하지만 불필요한 도구가 조용히 프로그램을 악화시킨다면, "모델에게 전부 주라"는 것은 잘못된 기본값이다. 실무자는 무엇을 넣고 무엇을 뺄지 알아야 한다.
2. **과학적 동기.** 알고리즘 코드에는 정확하고 자동화된 정확성 검사가 있다. 정확한 기하 술어(predicate), 증명된 최적해가 그것이다. 따라서 프롬프트 내용의 작은 변화를, 개방형 NLP 과제에서는 거의 불가능한 규모와 엄밀성으로 정밀하게 측정할 수 있다.
3. **파일럿 연구에서 이미 놀랍고 큰 효과를 발견했다** (4.2절):
   - 실행 환경을 명시한 한 문장("only the Python standard library is available")이 우리 기하 과제 모음에서 14B 모델을 79에서 100으로, Llama-3.1-8B를 83에서 99로 끌어올렸다.
   - 올바르지만 불필요한 기하 헬퍼 8개가 모든 모델 크기에서 17–29점의 손실을 냈다.
   - 대부분의 헬퍼가 불필요하다고 모델에게 알려줘도 피해는 사라지지 않았다.
   - 반면 추가 문서는 최적화 코드에 사실상 아무 영향도 주지 않았다. 이러한 도메인 간 차이는 설명이 필요하다.
4. **실현 가능하고 범위가 잘 정해져 있다.** 모든 실험은 A100 4장에서 vLLM으로 로컬 서빙하는 오픈 가중치 모델(Qwen3 1.7B–32B, Llama-3.1/3.3, Gemma-3, Granite)을 사용한다. 문제와 참조 정답은 프로그램으로 생성한다.

## 4. 실험 설계

### 4.1 설정

**과제.**
- *계산기하* (핵심 5개 + 보류(held-out) 2개):
  - 핵심: 볼록 껍질 꼭짓점 수, 다각형 면적의 두 배, 점-다각형 포함 판정, 선분 교차 개수, 최근접 쌍 거리;
  - 보류: 볼록성 판정, 삼각형 내부에 엄밀히 포함된 점.

  각 인스턴스에는 정확한 정수 오라클(oracle)이 있다. 또한 각 인스턴스는 **8개의 동치 버전**(평행이동, 회전, 대칭, 순열, 스케일, 약 10^9만큼의 오프셋, 그리고 퇴화 변형)으로 주어지며, 프로그램은 8개 모두에서 맞아야만 정답으로 집계된다.
- *조합 최적화* (핵심 4개 + 보류 2개):
  - 핵심: 0/1 배낭 문제, TSP, 그래프 채색, makespan 스케줄링;
  - 보류: bin packing, 최소 정점 덮개(minimum vertex cover).

  정확한 또는 최선으로 알려진 참조값은 DP, Held–Karp, CP-SAT으로 구한다. 지표는 참조값의 1% 이내에 드는 인스턴스의 비율이다.

**접근 방식.** 모델이 Python 프로그램을 작성하고, 이를 샌드박스(CPU, 메모리, 시간 제한)에서 실행한다. 최적화 프로그램은 OR-Tools를 사용할 수 있으며, 오류 피드백을 받아 최대 2회까지 수정할 수 있다. 직접(코드 없는) 답변을 베이스라인으로 삼는다.

**개입 (독립 변수).**
- 환경 사실(표준 라이브러리 문장);
- 헬퍼 도구 상자: 없음, 과제 맞춤형(캡슐화) 술어, 또는 과제 맞춤형에 K ∈ {0, 2, 4, 8}개의 관련/무관 방해 요소 추가;
- 헬퍼 전달 방식: 복사 삽입(copy-in) vs 사전 정의(pre-defined);
- 도구 상자 머리말 문구("should use" vs "most are not needed");
- API 계약 문장;
- 문서: 없음, 전체 OR-Tools 치트시트, 또는 문제별 스니펫(± K개의 불필요한 API 줄, ± 다른 문제들의 스니펫);
- k ∈ {1…5}의 검증 샘플링: 기하는 메타모픽 일관성 필터와 투표, 최적화는 실행 가능성과 최선의 목적함수 값;
- 추론 모드(thinking) 켬/끔.

**모델.** Qwen3 1.7B / 8B / 14B / 32B-AWQ; Qwen2.5-72B; Llama-3.1-8B; Llama-3.3-70B; Gemma-3-27B; Granite-4.1-8B.

**통계.**
- 그리디 디코딩과 T=0.7(시드 2–3개);
- 기하 조건당 프로그램 300개, 최적화 인스턴스 252개(보류 108개);
- 인스턴스 단위 쌍체 클러스터 부트스트랩(paired cluster-bootstrap) 95% 신뢰구간;
- 모든 이상치는 저장된 프로그램을 재실행해 점검했으며, 이를 통해 하네스의 교란 요인(confound) 여러 개를 잡아냈다.

### 4.2 이미 수행한 소규모(파일럿) 실험

**T1. 환경 사실** (계산기하(computational geometry), greedy 디코딩, 100개 중 8개 버전 모두에서 정답인 프로그램 수):

| 모델 | 표준 라이브러리 문장 없음 | 있음 |
|---|---|---|
| Qwen3-14B | 79 | **100** |
| Llama-3.1-8B | 83 | **99** |

문장이 없을 때의 실패는 설치되지 않은 기하 라이브러리(shapely)를 import한 경우였다.

![T1: 환경 사실](figs/fig1_environment_fact.png)

**T2. 무관한 헬퍼의 용량-반응(dose-response)** (기하, n = 300, T=0.7). 관련은 있지만 불필요한 헬퍼 8개를 추가했을 때의 변화:
- 8B: **−17.7** [−23.0, −12.7]
- 14B: **−29.0** [−34.3, −23.7]
- 32B: **−17.0** [−22.7, −11.7]
- Qwen3-1.7B: **−35.7** [−41.7, −29.7]; Llama-3.1-8B (2 seeds): **−39.3** [−43.8, −34.7]로, 측정된 것 중 가장 큰 피해다.
- Llama-3.3-70B (3 seeds, 쌍을 이룬 프로그램 900개): −0.8 [−3.8, +2.1].
- 즉 피해는 **모델 계열이 아니라 능력**을 따른다. 약한 모델(Qwen3 8B–32B, Llama 8B)은 피해를 입고, 시험한 가장 강한 모델은 무관한 헬퍼를 무시한다.
- **작은 추론 예산으로 충분하다:** 추론(thinking) 토큰을 최대 1,024개로 강제하면 추가 헬퍼 8개가 있어도 92–95로 회복된다 (0 토큰: 62–75; 4,096 토큰 ≈ 전체 추론).
- **추론이 피해를 없앤다** (2 seeds, 각 쌍 프로그램 200개): 같은 Qwen3 모델이 추론을 켜면 손실은 −1.5 [−4.5, +1.5] (8B), −0.5 [−2.5, +1.0] (14B), −3.0 [−5.5, −1.0] (32B)에 그친다. Qwen3-1.7B조차 추론을 켜면 −4.3 [−9.3, +0.7]만 잃고(3 seeds; 추론 없이는 −35.7), 추론 증류 모델인 DeepSeek-R1-Distill-Llama-70B는 0.0 [−3.0, +3.0]을 잃는다. 컨텍스트 내 무관한 도구에 대한 강건성은 추론 또는 높은 능력과 함께 나타난다.

![그럴듯한 헬퍼에 대한 강건성이 나타나는 지점](figs/fig7_distractor_by_model.png)

발견:
- 피해는 K에 따라 꾸준히 커진다 (8B: 98 → 87 → 81 → 74.5).
- 길이가 비슷한 *무관한(unrelated)* 헬퍼 6개는 4–7점만 깎고 거의 호출되지 않는다.
- 헬퍼를 미리 정의해 두어 복사할 필요가 없게 해도 피해는 남는다 (8B −12.3, 32B −15.0). 피해는 의미적이다: hull, area, closest-pair 로직이 과잉 설계된다. 14B의 경우 원래 하락분(위의 −29.0 포함)의 대부분은 복사 실패이며, 헬퍼를 미리 정의한 조건으로 다시 채점하면 −7.7 ("사용해야 함") 및 −0.3 (중립 헤더)이다.
- "대부분은 필요 없다"는 헤더는 헬퍼 사용을 40–65% 줄이지만 정확도는 0–5점만 회복시킨다.
- 프롬프트, 헬퍼, 실패한 프로그램의 실제 예시는 부록 B에, 메커니즘 분석(그럴듯한 헬퍼가 왜 해로운가)은 부록 B.4에 있다.

따라서 샘플링과 사실 명시는 상호 보완적이다:
- 샘플링은 *독립적* 오류(기하의 퇴화 사례)를 고친다;
- 사실 명시는 *체계적* 오류(API 오해)를 고친다.

**T6. 추론 모드(thinking)** (헬퍼와 문서를 T4/T5와 같이 고정; 방해 요소 하에서의 추론은 T2 참조).
- 기하에서는 대체로 중립이다(±3점). 남은 오류는 퇴화 사례 버그다.
- 최적화에서는 8B의 TSP 바닥을 깨는 유일한 수단이다(0 → .58).
- 보류 문제에서는 bin packing을 고친다: 스니펫이 있을 때 8B는 .17 → .87, 14B는 .48 → .96이 된다(전체 .58 → .94, .74 → .98).
- 8B에서는 추론을 켜도 스니펫이 여전히 중요하다(전체 시트 .71 대비 .94).
- 따라서 추론은 소형 모델의 *체계적* 오류를 위한 수단이다. *독립적* 오류는 검증된 샘플링이 더 저렴하게 처리한다.

**T7. 더 어렵고 현실적인 기하 과제** (리뷰 항목 3에 대응해 추가; 추론 없음, 과제당 프로그램 60개, 8개 변형 모두에서 정답):
- `lattice` (다각형 내부에 엄격히 포함되는 정수점 개수; Pick의 정리 또는 경계를 고려한 전수 탐색)와 `rectunion` (직사각형 합집합의 넓이; 스위프 라인). 둘 다 추론 없이는 어렵다: 8B/14B는 60개 중 1–12개, 32B는 22–44개.
- **정확하지만 부호가 있는 헬퍼는 함정이다.** 필요한 헬퍼 `polygon_area2`는 *부호 있는* 넓이를 반환한다. 이를 주면 모델은 `abs` 없이 사용하고, 그러면 Pick의 공식이 시계 방향 입력에서 실패한다. 32B는 60개 중 44개에서 9개로 떨어지며, 변환에서만 생기는 실패는 전부 이 버그다.
- **"방해 요소"가 최선의 도구일 수도 있다.** 추가 헬퍼 8개 중 `point_in_polygon`은 경계점을 정확히 판별한다. 대부분의 프로그램이 이를 이용한 전수 세기로 전환하고 정확도가 급등한다(8B 2 → 47, 14B 1 → 37–46). 헬퍼가 무관한지는 과제에 달려 있다: 모델이 아는 이디엄에서 벗어나게 하면 해롭고, 모델이 틀리기 쉬운 기본 연산을 제공하면 이롭다.
- 어떤 헬퍼도 도움이 되지 않는 `rectunion`에서는 32B에서 피해가 다시 나타난다(22–29 → 7–12).
- 검증된 샘플링(3개 샘플 + 메타모픽 검사(metamorphic check))은 여전히 도움이 된다: 32B 120개 중 62–72 → 96. 정확도가 낮을 때 검사는 틀린 프로그램을 고르기보다 대부분 판정을 유보한다.
- **함정의 인과 검증:** 헬퍼가 절댓값을 반환하도록 바꾸면 32B는 60개 중 46–49개로 회복된다(8B 2 → 15). docstring 경고("시계 방향이면 음수; abs() 사용")는 32B에서 충분하지 않다(17–19): 모델이 "까다로운" 헬퍼를 버리고 버그가 있는 전수 탐색으로 넘어간다. 위험을 문서화하기보다 도구 자체의 계약을 고쳐야 한다.
- **추론은 두 어려운 과제를 모두 해결한다** (8B/14B/32B: 60개 중 56–60, 추론 없이 1–44 대비). 추가 헬퍼 8개가 있어도 마찬가지이며(손실 ≤ 3), 프로그램당 약 8k 토큰이 든다.
- **다각형 클리핑(정확한 유리수 교차 넓이), 가장 어려운 과제:** 비추론 Qwen/Llama는 어떤 조건에서도 180개 중 0–2개만 푼다. 낮은 effort의 gpt-oss-20b는 60개 중 14개를 풀고, 해결책들이 합성된다: 한 문장 힌트를 더하면 44개, 힌트 + 레이블 없는 메타모픽 검사를 곁들인 3개 샘플이면 총 ≈2.8k 토큰으로 **60개 중 59개**다(검사가 틀린 프로그램을 고른 적은 한 번도 없다). 지배적인 버그는 입력이 반시계 방향이라고 가정하는 것이며, 힌트가 이를 짚고 검사가 이를 잡아낸다.
- **계열을 넘는 추론:** DeepSeek-R1-Distill-Llama-70B는 도움 없이 두 어려운 과제를 모두 푼다(60개 중 57개, 54개). Llama-3.3-70B는 0–1개다. 그러나 도구 상자가 주어지면 부호 있는 넓이 함정에 빠진다(lattice 57 → 42; 방향 관련 실패 16건 모두 `abs` 누락). 추론은 불필요한 헬퍼로부터는 보호하지만, 숨은 계약을 가진 필요한 헬퍼로부터는 안정적으로 보호하지 못한다. 추론을 켠 Qwen3는 대체로 이를 처리한다(부호 있음 vs 부호 없음, 60개 중 32B 59 vs 59; 8B 52 vs 60). 부호 없는 헬퍼는 모든 모델에서 문제를 없앤다.
- **또 다른 계열:** 쉬운 과제에서 강건한(−0.8) Llama-3.3-70B는 도움 없이 두 어려운 과제 모두에서 60개 중 0–1개를 맞히며, 경계를 정확히 판별하는 `point_in_polygon`이 추가 헬퍼에 포함되면 `lattice`에서 45–46개로 급등한다. 쉬운 과제에서의 능력이 더 어려운 과제에서의 강건성이나 기량을 의미하지는 않는다.

**T8. 검색(RAG)이나 텍스트 힌트로 고쳐지는가?**
- **최적화, 제목이 붙은 스니펫 라이브러리에 대한 BM25 검색:** top-1 검색은 손으로 쓴 스니펫과 맞먹는다(32B .97 vs .96; Llama-70B .85 vs .87; 8B .68 vs .67). 청크 3개를 검색하면 비슷하지만 틀린 항목이 섞여 단일 문제에서 최대 26점을 잃는다(32B bin packing .93 → .67, CVRP .83 → .57). 약한 코드 전용 검색기조차 문서 없음보다 낫다(8B .21 → .61, 32B .67 → .90).
- **기하, 헬퍼 코드 대신 한 문장짜리 알고리즘 힌트:** Pick의 정리는 lattice 세기를 60개 중 55–59개로 끌어올린다(Llama-70B 0 → 55). 해로운 헬퍼 옆에 "Andrew's monotone chain"을 명시하면 Qwen 8B/32B의 hull이 4/3에서 60개 중 58/52로 회복되고(3 seeds: 7 → 94%, 5 → 88%, +83~+87점), `polar_sort`는 더 이상 호출되지 않는다. 이는 헬퍼가 알고리즘 선택을 바꿈으로써 피해를 준다는 인과적 증거다. Llama-70B는 계속 헬퍼를 따른다(28 → 33).
- **오라클이 아닌 힌트:** 모델이 먼저 스스로 알고리즘을 명명하게 하면, 올바른 알고리즘을 알 때만 도움이 된다(Qwen은 Pick의 정리를 명명: lattice 8B 12 → 44, 32B 44 → 55; Llama-70B는 그렇지 못함: 0 → 0). 이는 취약한 선택을 고착시킬 수도 있다(32B가 hull에 Graham scan을 계획하므로 `polar_sort`가 계속 해를 끼친다). *틀린* 검색 힌트는 파괴적이고(BM25가 lattice에 "ray casting"을 검색: 32B 44 → 3), 올바른 검색 힌트는 손으로 쓴 힌트와 맞먹는다(rectunion 8B 8 → 38). 검색 품질이 효과의 부호를 결정한다.

### 4.3 확장: LLM 효율성 × CG/CO (파일럿 진행 중)

사용자가 제안한 LLM 효율성과의 결합은 발견과 직접 맞닿아 있다. 우리의 해결책은 연산량(샘플, 추론 토큰)이나 정밀도를 정확성과 맞바꾸므로, 자연스러운 질문은 **고정된 추론 예산을 어디에 쓸 것인가**이다:

| ID | 질문 | 설계 (파일럿) |
|---|---|---|
| X1 | **연산 최적 해결책:** 같은 토큰 수에서 k개 프로그램 샘플링 + 검사, 예산 B의 추론, 더 큰 모델 중 무엇이 나은가? | **파일럿 (8B, 추가 헬퍼 8개, 토큰 집계):** 같은 토큰 수에서 예산 제한 추론이 best-of-k를 압도한다(≈1.6k 토큰: 87 vs 81; ≈2.5k: ≳90 vs 84; 전체 추론 5.8k에서 97). 체계적 오류가 있으면 추가 샘플은 같은 실수를 반복한다. **깨끗한 프롬프트에서는 순서가 뒤집힌다:** MR best-of-3는 ≈0.9k 토큰에서 100, 전체 추론은 5.5k에서 91이다(예산 256/1024: 88/87). 규칙: 독립적 오류 → 샘플링 + 검사; 프롬프트가 유발한 체계적 오류 → 추론. **최적화도 일치한다:** 8B(체계적 API 오해) best-of-3 .72 vs 추론 .87; 14B/32B best-of-3는 추론 토큰의 ≈⅓로 1.00/.99에 도달한다. 다만 최적화는 기하보다 훨씬 많은 추론이 필요하다: 256/1k/2k 토큰 예산에서 TSP는 0에 머물고 bin packing은 .11/.37/.59에 그친다(전체 추론 ≈6k에서 .87). 어려운 기하(T7)는 쉬운 기하처럼 동작한다: ≈1k 추론 토큰으로 8B/14B의 lattice 세기가 60개 중 1–12개에서 58개로 오르며, 같은 토큰 수의 best-of-3 샘플링을 이긴다(120개 중 97 vs 44). 네이티브 추론 모델은 프런티어 전체를 이동시킨다: 낮은 effort의 gpt-oss-20b는 ≈0.4–0.9k 토큰에서 ≈99%에 도달하지만(헬퍼 유무와 무관), 높은 effort는 폭주한다(프로그램의 27%가 24k 토큰 초과). |
| X2 | **저정밀도가 perplexity가 시사하는 것보다 알고리즘 코드를 더 망가뜨리는가?** | **파일럿:** fp8 가중치는 모든 곳에서 bf16과 일치한다(기하 272 vs 272, 방해 요소 포함 227 vs 228, 최적화 .714 vs .702, 추론을 켠 보류 최적화 .935 vs .935). fp8 KV 캐시는 이 vLLM 빌드에서 실행되지 않는다. 다음: 4-bit/3-bit 가중치(AWQ/GPTQ, 예: 팀의 양자화 도구 사용)와 HF-transformers 경로를 통한 KV 양자화. |
| X3 | **소형 모델 + 검증기 vs 대형 모델:** 정답 하나당 비용 | 샘플링 + 레이블 없는 검사를 쓴 Qwen3-1.7B/8B vs 단일 샷 32B, 토큰과 메모리를 함께 집계. |
| X4 | **압축 하의 강건성:** 양자화가 모델을 그럴듯한 방해 요소에 *더* 민감하게 만드는가("능력" 저하 → 피해 증가, 4.2절 T2)? | fp8 / 4-bit vs bf16에서의 용량-반응 (K = 0/8). |

### 4.4 계획된 실험 (전체 프로젝트를 위한 팀 작업)

| ID | 실험 | 목적 |
|---|---|---|
| E1 | T1–T5를 더 많은 모델 계열에서 재현. Llama-3.3-70B 파일럿: 최적화 스니펫 효과는 강하게 재현되고(보류 bin packing에서 전체 시트 .07 대비 .96) 검증된 샘플링도 재현되지만, **기하 방해 요소 피해는 나타나지 않는다**(쌍 프로그램 900개에서 −0.8 [−3.8, +2.1]). Llama-3.1-8B는 가장 큰 피해(−39.3)를 보이므로 효과는 계열이 아니라 능력을 따른다. 다음: 더 많은 크기로 능력 곡선 작성(환경 수정 후 Mistral/Gemma, 그리고 비공개 API 모델 하나 추가) **세 번째 계열 (OpenAI gpt-oss 20b/120b, 네이티브 추론):** 모든 effort 수준과 두 크기 모두에서 추가 헬퍼 8개에 강건하고(20b와 120b: 2 seeds에서 −1.0~+0.7점, 120b가 피해를 입은 것처럼 보이게 했던 코드 추출 버그 수정 후; 낮은 effort에서 프로그램당 ≈430–880 토큰), 어려운 과제를 풀며(60개 중 56–60), 부호 있는 넓이 함정을 피한다. 문서 없이도 OR-Tools를 잘 알지만(.93–1.00), 스니펫이 여전히 1.00으로 끌어올린다(CVRP .67–.87 → .93–1.00). | 레시피의 어느 부분이 보편적이며, 무관한 도구에 대한 강건성은 어디서 나타나는가? |
| E2 | 발견 *이후* 설계한 보류 과제 확장. 파일럿 `overlap`(두 볼록 다각형이 교차하는가; 접촉도 포함)은 모든 기하 주장을 재현한다: 캡슐화된 술어 8B 58 → 100, 32B 47 → 100; 메타모픽 필터를 쓴 검증된 샘플링이 투표보다 우수; 방해 요소 피해(32B −15.0); 추가 헬퍼 8개에서 추론 100%. 다음: 기하 과제 2–3개와 최적화 문제 2개 추가(bin packing과 vertex cover는 이미 재현됨, 4.2절) | 결과가 일반화인가, 우리 과제 모음에 대한 과적합인가? |
| E3 | 자동 도구 범위 지정. 파일럿: 모델의 자기 선택은 격차의 약 절반을 회복한다. 단순 어휘 검색은 과제 이름이 일치할 때 캡슐화된 술어를 찾지만(point-in-polygon 20/20) 한 번의 잘못된 선택이 과제를 망친다(hull 1–2/20). 따라서 정밀도가 병목이다. 유보(abstention)를 포함한 임베딩 검색, 후보 도구 집합에 대한 메타모픽 검사 기반 선택을 비교 | 손으로 고른 도구를 대체할 배포 가능한 대안 |
| E4 | 메커니즘 분석: 어떤 헬퍼 토큰이 복사되거나 주의(attention)를 받는가; 피해가 헬퍼–과제 의미 유사도와 상관되는가? | 그럴듯한 헬퍼가 기하에는 해롭고 최적화에는 해롭지 않은 *이유* 설명 |
| E5 (도전 과제) | 검증된 해답이 달린, 방해 요소가 많은 프롬프트로 소형 모델(Qwen3-1.7B/8B)을 LoRA 미세조정 | 무관한 도구에 대한 강건성을 *학습*할 수 있는가? **파일럿 완료:** 추론 모델로부터의 자기 증류(검증된 프로그램 600개, LoRA r=16)는 추가 헬퍼 8개 하에서 추론 없는 8B를 76.0에서 **97.7**로 끌어올린다(+21.7 [+17, +26]). ≈6k 대신 ≈350 토큰으로 추론 수준의 정확도다. 같은 크기의 깨끗한 프롬프트 LoRA는 이득이 없으므로(−0.7) 방해 요소가 많은 프롬프트가 필수다. 그러나 전이되지 않는다: 보류 과제에서 K8 58.6 → 52.2 (2 seeds, −6.4 [−12.2, −0.6])이고, 과제 하나를 뺀(leave-one-task-out) LoRA는 K8 하의 미학습 과제에 거의 도움이 되지 않으며(통합 77.0 → 80.8) 때로는 **깨끗한 프롬프트에서 오히려 손상을 준다**(hull 97 → 34: 모델이 monotone chain에서 벗어나 Graham scan과 임시방편 루프로 이탈). 강건성은 과제별로 학습되며, 좁은 미세조정은 다른 곳의 정확도를 대가로 치를 수 있다. 4개 대신 9개 과제로 학습해도 해결되지 않는다(미학습 hull 깨끗한 프롬프트에서 97 → 28; convex K8 68 → 34). 학습한 과제 내에서는 이득이 처음 보는 프롬프트 형식에서도 유지된다(중립 헤더 +19, 헬퍼 10개 +21, 미리 정의된 헬퍼 +18). 더 가벼운 학습은 손상을 없애지만 이득도 없앤다(r=4: hull 온전, 과제 내 81 vs 기준 91). 어느 설정도 한쪽만 얻게 해주지 않았다. |

**기대 기여.**
1. 알고리즘 코드에 대한 컨텍스트 내 방해 요소 효과의 통제된 측정: 용량-반응, 전달 방식 통제, 도메인 대비 포함.
2. 각 구성 요소가 언제 적용되는지에 대한 근거를 갖춘, 과제에 독립적인 실용 레시피: 환경 및 API 사실을 명시 → 도구 표면을 최소로 유지 → 프로그램을 약 3개 샘플링하고 레이블 없는 검사로 선택. 도구를 줄일 수 없는 경우, 추론 모드는 소형 모델(Qwen3 1.7B–32B)까지도 그럴듯하지만 무관한 헬퍼에 거의 면역이 되게 한다.
3. 방법론적 교훈: 우리 파일럿에서 겉보기 "능력" 격차 몇 가지는 하네스 교란 요인으로 판명되었다. 누락된 라이브러리, 샌드박스 스레드 제한, 수정 피드백 문구, 서버 포트 충돌이 그것이다.

**위험과 완화책.**
- *Qwen에 특유한 효과.* E1로 완화(환경 사실을 명시하면 Llama 파일럿 점검 결과가 이미 일치함).
- *작은 과제 모음.* E2와 조건당 프로그램 n = 300으로 완화.
- *"프롬프트 엔지니어링"이라는 비판.* 단일 최적 프롬프트가 아니라 통제 변수(용량, 전달 방식, 도메인)와 메커니즘(E4)을 중심으로 서술하여 완화.
- *공유 GPU에서의 연산 자원 경합.* 작고 재개 가능한 실행(각 ≤ 1시간)으로 완화.

## 5. 파일럿에 대한 비판적 검토 (건설적 비판)

우리 파일럿에서 발견한 문제를 결론을 바꿀 수 있는 정도가 큰 순서로 정리한다. 각 문제에는 계획된 해결책을 함께 적었다.

| # | 우려 사항 | 중요한 이유 | 이미 확인한 내용 | 본 프로젝트에서의 해결책 |
|---|---|---|---|---|
| 1 | **선택과 평가가 같은 변환을 공유한다.** 메타모픽 검사(metamorphic check)는 8-변형 점수가 사용하는 것과 *동일한* 인스턴스의 사본을 쓴다. | 검증된 샘플링(verified sampling)이 실제보다 좋아 보일 수 있다. | **해결됨:** 선택된 프로그램을 검사가 한 번도 보지 않은 *새로운* 인스턴스 5개 × 변형 8개로 채점하면 98.2 / 97.7 / 93.9 (8B / 14B / 32B)로, 단일 샘플 91.7 / 96.2 / 85.4와 과제 맞춤 술어(predicate) 95.0 / 97.0 / 93.7보다 높다. 누출(leakage)은 없다. | 모든 선택 방법에 대해 새 인스턴스 평가를 기본 지표로 유지한다. |
| 2 | **툴박스 헤더가 "should use"라고 지시한다.** | 피해의 일부는 헬퍼 자체가 아니라 지시를 따르는 데서 올 수 있다. | **해결됨 (06:40 정정):** 중립 헤더에서는 원시(raw) 하락폭이 더 커 보였으나(8B −12.7, 14B −18.3, 32B −29.0), 상당 부분은 **복사 실패**였다. 중립 헤더는 "헬퍼를 복사하라"고 말하지 않으므로 모델이 정의되지 않은 헬퍼를 호출한다(NameError). 저장된 모든 프로그램을 제공된 헬퍼를 미리 정의한 상태로 재채점하면(`poc/rescore_prelude.py`) **should-use** 8B −14.3, 14B −7.7, 32B −13.3, **neutral** 8B −11.7, 14B −0.3, 32B −16.3이다. 8B/32B의 의미적 피해는 지시와 무관하며, 14B의 피해는 대부분 패키징 문제다. | 복사 실패와 의미적 피해가 분리되도록, 헬퍼를 미리 정의한(prelude) 중립 헤더를 기본값으로 쓴다. |
| 3 | **작은 합성 과제 모음.** 기하 과제 5 + 3개(n ≤ 20점), 최적화 문제 4 + 2개(≤ 80개 항목). | 효과가 현실적인 코드로 전이되지 않을 수 있다. | **부분 해결:** 5배 큰 인스턴스(50–100점, 꼭짓점 40–70개 다각형)에서 모든 주장이 재현된다: 술어 32B 82.5 → 99.5, 검증된 샘플링 93–99, 그럴듯한 헬퍼 −11 ~ −29. 발견 이후에 설계한 보류(held-out) 과제에서도 재현된다. **T7:** 더 어려운 다단계 과제 두 개(격자점 개수, 직사각형 합집합)에서 메커니즘(헬퍼가 알고리즘을 결정함)은 유지되지만, 부호는 과제에 따라 달라진다. 모델에 없는 정확한 프리미티브는 도움이 되고(8B 2 → 47), 미묘한 계약(부호 있는 면적)을 가진 필요한 헬퍼는 해가 된다(32B 44 → 9). | 최적화 측: 용량 제약 차량 경로 문제(CVRP, 정확한 참조해)에서는 문제 특화 스니펫이 결정적이며(14B .20 → .73–.80, 32B .23 → .77–.90; best-of-3 1.00), 불완전한 참조(용량 없는 TSP 경로)는 32B에서 없는 것보다 나쁘다(.07 vs .23). **이후 추가:** 다각형 클리핑(수정책이 합성된다: gpt-oss-20b는 힌트 + 검증된 샘플링으로 60개 중 14 → 59, 비추론 모델은 180개 중 0–2)과 시간 창이 있는 VRP(정확한 스니펫만 통한다: Llama-70B 0 → .60–.77, best-of-3 .93; 근접 오답인 CVRP 스니펫과 전체 시트는 0). 미해결: Delaunay 검사. |
| 4 | **많은 셀이 단일 시드, n = 60–100이다.** | CI가 넓고(예: overlap 14B Δ −8.3 [−23.3, +6.7]), 과제별 수치가 ±10 pts 흔들린다. | 핵심 효과는 2–3개 시드와 n = 300(기하) / 252(최적화)에서 쌍체(paired) CI로 재현되었다. | 주요 대비를 사전 등록하고, 모든 곳에서 ≥ 3 시드를 실행하며, 인스턴스*와* 시드에 대한 클러스터 부트스트랩을 쓰고, 다중 비교를 보정한다. |

### A.4 주의 사항과 진행 상황

- 초기 기하 실행에는 표준 라이브러리 줄이 없었다. 최종 표는 이를 사용한다. 14B/72B의 초기 수치는 부분적으로 shapely 인공물이었다(FINDINGS.md에서 정정).
- 14B 모델은 툴박스 헤더 문구에 민감하므로 과제별로 보고한다.
- 표준 라이브러리 줄을 넣은 Qwen2.5-72B 실행은 끝내 돌리지 못했다(외부 작업이 GPU를 점유). pipeline-parallel 시도는 잘못된 출력을 내어 격리했다(`*_pp3_INVALID`).
- **교차 계열 재현 (Llama-3.3-70B, 완료):**
  - 최적화 스니펫 ≫ 전체 시트 (.87 vs .55);
  - 검증된 샘플링이 작동한다 (k = 3: 92.7, 메타모픽 필터가 투표 대비 +6.7);
  - **그러나** 기하 방해 요소의 피해는 작고 유의하지 않으므로(−4.0), 방해 요소 민감도는 모델에 따라 다르다.
  - Granite-4.1-8B(채팅 템플릿이 없는 base 모델)와 Gemma-3-27B(flash_attn 빌드가 vLLM과 비호환)는 이 서버에서 실행할 수 없었다.
- 이것은 **파일럿** 결과다. 코스 프로젝트에서 팀은 하네스를 이해하고, 최종 실험을 재실행하며, 계획된 확장(4.4절의 E1–E5)을 수행해야 한다.
## 부록 B. 도구 목록과 실제 예시

아래 예시는 모두 파일럿 실행에서 나온 실제 모델 출력이다. 길이를 줄였으며, 생략한 줄은 `…`로 표시했다.

### B.1 제공되는 것

**기하 헬퍼 풀(geometry helper pool)** (`poc/geo_distractors.py`). 검증을 거친 정확한(exact) 헬퍼 함수들로, 프롬프트에 붙여 넣어 모델이 자신의 프로그램에 복사해 쓰도록 한다.

| 헬퍼 | 기능 |
|---|---|
| `orient(a, b, c)` | 외적의 부호: 좌회전 / 우회전 / 공선(collinear) |
| `on_segment(a, b, p)` | 점 p가 선분 ab 위에 있는지 |
| `segments_intersect(a, b, c, d)` | 닫힌 선분 ab와 cd가 점을 공유하는지 |
| `point_in_polygon(poly, q)` | `'inside'` / `'outside'` / `'boundary'` (정확한 회전수(winding number)) |
| `dist2(a, b)` | 거리의 제곱 |
| `bbox(points)` | 경계 상자(bounding box) |
| `collinear(a, b, c)` | 세 점이 한 직선 위에 있는지 |
| `polar_sort(points, o)` | o를 중심으로 한 각도순 정렬 (정확, atan2 미사용) |
| `is_convex(poly)` | 다각형이 볼록한지 |
| `polygon_area2(poly)` | 부호 있는 넓이의 2배 |
| `convex_hull(points)` | 볼록 껍질(convex hull) 꼭짓점 (단조 체인(monotone chain)) |
| `closest_pair_sq(points)` | 점 쌍 간 최소 거리의 제곱 |

**과제별 구성.** 필요한 헬퍼는 항상 제공한다. 과제를 곧바로 풀어 버리는 헬퍼는 절대 제공하지 않는다. 방해 헬퍼(distractor)는 나머지에서 뽑는다.

- "견고하게, 퇴화 사례를 처리하라"는 지시가 정확도를 오히려 *낮췄다*(8B 96 → 84, 32B 89 → 73).

추론을 하면 모델이 먼저 어떤 헬퍼가 관련 있는지 판단하므로 자신의 관용 표현을 유지한다. 더 큰 모델(Llama-70B)은 이를 암묵적으로 하는 것으로 보인다. 최적화에서는 모델이 잘 아는 표준 정식화를 작성하고 추가 텍스트는 무시한다.

**아직 분석하지 않은 것 (E4):**
- 헬퍼가 어디서 복사되는지에 대한 어텐션 또는 토큰 수준 증거;
- 피해가 헬퍼와 과제의 의미적 유사도에 비례하는지 여부(대부분의 헬퍼가 포함되는 K=8보다 낮은 K 용량 수준이 유무 대비를 더 크게 준다).

### C.2 관용 표현 이탈 문제: 10^9에서의 부동소수점 (Qwen3-8B, 다각형 넓이)

*문제.* 프로그램이 정수를 부동소수점으로 파싱한다. 그러면 신발끈 합이 10^9 오프셋 변형에서만 정밀도를 잃는다(기본 정답 920, `big`에서 오답).

```python
x = float(x_str); y = float(y_str)          # integers read as floats
area += (x1 * y2) - (x2 * y1)               # products ~1e18 exceed float precision
print(int(2 * area))
```

*해결.* 정확한 정수 연산 지시, 또는 **검증 샘플링(verified sampling)**. 메타모픽 검사(metamorphic check)가 이 프로그램을 `big`에서 비일관적이라고 표시하고, 나머지 두 샘플(정수 연산)은 일치하므로 선택기가 올바른 프로그램을 반환한다.

### C.3 검증 샘플링의 성공과 한계 (Qwen3-32B, 점의 다각형 내부 판정)

같은 인스턴스에 대한 샘플 3개. 8개 변형에서의 출력(정답: `degen` = `no`를 제외하고 모두 `yes`):

| 샘플 | identity | translate | rot90 | mirror | permute | scale | big | degen | 메타모픽 검사 |
|---|---|---|---|---|---|---|---|---|---|
| 1 (엡실론을 쓰는 부동소수점 광선 투사) | yes | yes | **no** | **no** | yes | yes | yes | no | ❌ 기각 (비일관) |
| 2 | **no** | **no** | **no** | **no** | **no** | **no** | **no** | **yes** | ✅ 일관적이지만 전부 오답 |
| 3 | yes | yes | yes | yes | yes | yes | yes | no | ✅ 일관적이고 정답 |

- **성공:** 샘플 1의 회전·거울상 버그를 레이블 없이 잡아낸다.
- **한계:** 샘플 2는 *불변이지만 틀렸으므로* 검사가 오류를 보지 못한다. 서로 다른 답을 내는 일관적 후보가 2개이면 투표는 동률이 된다. 더 많은 샘플이나 두 번째 검사(예: 작은 입력에 대한 브루트포스 참조)가 필요하다. 이 때문에 크래시형 오류가 사라지고 나면 메타모픽 필터의 기여가 줄어든다(4.2절, T5).

### C.4 최적화: 전체 치트 시트는 목적 함수를 빠뜨리고, 스니펫은 이를 되살린다 (Qwen3-8B, 그래프 색칠)

전체 치트 시트를 주면 프로그램은 순수한 실행 가능성(feasibility) 모델이 된다. 최적이 4인데 색을 6개 쓴다.

```python
colors = [model.NewIntVar(0, n-1, f'color_{i}') for i in range(n)]
model.Add(colors[a] != colors[b])            # per edge
status = solver.Solve(model)                 # no objective: any proper colouring is accepted
```

문제별 스니펫을 주면 프로그램은 가장 큰 색 번호를 최소화하여 최적(4)에 도달한다.

```python
max_color = model.NewIntVar(0, n - 1, 'max_color')
model.AddMaxEquality(max_color, colors)
model.Minimize(max_color)
```

### C.5 추가 헬퍼 8개에서의 사고 트레이스 (Qwen3-32B, 껍질; B.2의 프롬프트)

모델이 코드를 쓰기 전 추론의 발췌이다. 전체 트레이스는 `results/example_thinking_32b_hull_k8.txt`에 있다.

> "First, I remember that the convex hull can be computed using algorithms like Graham's scan, Andrew's monotone chain algorithm, or Jarvis's march. … Looking at the helper functions provided, there's a polar_sort function which sorts points around a given origin. Also, there's the orient function … These might be useful … Let me think about Andrew's monotone chain algorithm … during this process, colinear points that are in the middle of the line are removed … So maybe the standard convex hull algorithm already takes care of that … `if … cross(lower[-2], lower[-1], p) <= 0: lower.pop()` … if cross is 0, then the three points are colinear. In that case, the condition is true (<=0), so the previous point is removed."

모델은 방해 헬퍼(`polar_sort`)를 알아차리고 대안들을 저울질한 뒤 **잘 아는 알고리즘을 선택하며**, 왜 `<= 0`이 이미 공선점을 처리하는지 명시적으로 추론한다. 사고가 없으면 이 단계가 생략된다: 32B 껍질 프로그램의 45%가 곧바로 polar-sort 스캔으로 가고 공선점을 과잉 처리한다(부록 B.3–B.4).

### C.6 틀린 헬퍼 하나로 충분하다 (선택 예시)
